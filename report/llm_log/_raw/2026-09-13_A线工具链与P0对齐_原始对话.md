## 第 5 轮（2026-09-13）

### 【用户】

> 现在使用什么fps比较好

### 【AI 回答】

先指出项目里"fps"是三个不同的东西，别混：**采集/录制帧率**（契约冻结）、
**逻辑时间基**（`ts = frame_id / fps_nominal`）、**实时处理吞吐**。

**为什么是 30 且不能随便改**：降不了——`min_close_frames: 3` 对 100~400 ms 的眨眼，
30 fps 下一次眨眼是 3~12 帧刚好够去抖，掉到 15 fps 会系统性漏检；
升不动——FIR 系数与全部黄金参考都锚在 fs=30，改等于重做系数 + 重生成黄金参考 + 改契约。

**本机能不能实时跑 30 fps**（实测）：用 matplotlib 自带的公开样图 `grace_hopper.jpg`
（478 点全部检出）测整条链路 → **13.7 ms/帧 → 73 fps 上限**，30 fps 预算 33.3 ms，
占用约 41%，余量 2.4 倍。**瓶颈不在算法侧。**

**顺手挖到一个坑**：把同一段视频转成 15 fps 再跑，管线报：

```
帧源   : file:_smoke_15fps.mp4  15.0fps  47 frames
逻辑帧率: 30.0 fps
处理帧数  : 47（逻辑时长 1.57s）
```

47 帧的 15 fps 视频真实时长 3.13 s，管线却按 30 fps 解释成 1.57 s，**且没有任何警告**。
后果：眨眼率、`long_close_ms` 的长闭眼判定、`yawn_min_duration_ms` 的去抖全部失真；
而 **PERCLOS 反而免疫**（它是"闭眼帧数 / 有效帧数"，是帧比例）。建议加"采集帧率 ≠
`fps_nominal` 时告警"。

## 第 6 轮（2026-09-13）

### 【用户】

> C的fps改为多少效果比较好

### 【AI 回答】

**结论：C 线的图像流 fps 不要改，保持 30。** 真正该讨论的是"喂给 FIR 的**时间序列采样率**"。

用 C 线自己的 `design_fir_coeffs.py`（加 `--no-write`，**不覆盖冻结系数**）跑了对照，
同样 63 阶、0.7~3.5 Hz 带通：

| 时间序列 fs | 实测 −3 dB 点 | 低阻带最差 | int32 累加器 |
|---|---|---|---|
| 60 Hz | 0.710 / 3.402 | **−4.5 dB** | 安全 |
| **30 Hz（当时冻结）** | 0.698 / 3.504 | −9.5 dB | 安全 ✅ |
| 20 Hz | 0.709 / 3.490 | **−15.9 dB** | 安全 ✅ |
| 15 Hz | 0.698 / 3.502 | −22.9 dB | 溢出 ❌ |
| 10 Hz | 0.705 / 3.495 | −52.8 dB | 溢出 ❌ |

**三条结论**：① **升 fps 是负收益**（fs=60 时低阻带只有 −4.5 dB，比 30 的 −9.5 dB 还差），
因为过渡带 `Δf ≈ 3.3/(2πN)·fs` 与 fs 成正比；② 降才有收益，但 `Σ|h|` 变大会撞 **int32
累加器上限**；③ PL 吞吐不是瓶颈（640×480@30fps = 9.2 M 样本/s，II=1@100MHz = 100 M 样本/s）。

**呼吸带那条路有坑（回填给 C 线）**：契约说"降到 2 Hz 再用同名 IP 的第二组系数"，
实测 `Σ|h| = 70247 → |acc| ≤ 2.30e9 > 2³¹` **溢出**，且 63 阶 @2 Hz 群延迟 **15.5 秒**，
−3 dB 自动搜索也没收敛。即"同一份 RTL、换一组系数"在呼吸带上不成立。

## 第 10 轮（2026-09-15）

### 【用户】

> 改正github的问题，怎么做才能继续开发

### 【AI 回答】

**根因一：git 不走系统代理。** 本机用 `127.0.0.1:7890` 的本地代理（注册表 `ProxyEnable=1`）。
**Python 会读注册表代理，`git.exe` 不会**，于是出现极误导的现象：同一个 github.com，
python urllib 返回 200，git 报 `Recv failure: Connection was reset`；而且**时好时坏**
（直连偶尔也能成），很容易被误判成"网络不好"去调超时。

**根因二：本机没有 GitHub 凭据。** 没有 `~/.git-credentials`，Windows 凭据管理器里也没有
github 条目；PortableGit 默认的 `credential.helper=helper-selector` 会弹窗让用户选助手，
在无交互终端里直接报 `could not read Username for 'https://github.com'`。

**修法（均为仓库级，不动全局配置）**：

```powershell
git config http.proxy http://127.0.0.1:7890
git config credential.helper manager        # PortableGit 自带 Git Credential Manager 2.9.1
```

**顺序很关键：先配代理、再配凭据助手。** GCM 自己也要走代理，顺序反了它的诊断会报
