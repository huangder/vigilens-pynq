## 1. 先决条件（缺一不可）

- [ ] micro-USB 是**数据线**（不是纯充电线），直插主机、**不经过 hub**
- [ ] 相机**没停在 bootloader**：**绿灯呼吸 = 停在 bootloader**（固件没跑，也连不上）；白/蓝常亮 = 固件在跑
- [ ] **相机盘上的文件先备份** —— 刷 UVC 会连带擦除内部 FAT
- [ ] **决定这次要哪个（不可兼得）**：

| 这次要 | 走哪条 | 代价 |
|---|---|---|
| **网页看画面**（演示） | 刷 UVC，本页 §2–§4 | 刷完**跑不了** `openmv_capture_test.py`（任务 C 的能力矩阵做不了） |
| **能力矩阵**（任务 C） | **别刷**，保持 MicroPython 固件，用 OpenMV IDE 跑 `openmv_capture_test.py` | 网页里**看不到**画面 |

> ⚠️ **建议顺序：先把能力矩阵做完，再刷 UVC 做演示。**
> 因为缺数据的正是能力矩阵（JPEG 字节数等），而演示随时可以做。

## 2. 刷 UVC

> 🔴 **IDE 是按【文件名】校验的**（2026-09-26 实测，用户截图原文）：
>
> ```
> 所选文件"_uvc_openmv4.bin"与 OpenMV Cam H7 的任何固件接口都不匹配。
> OpenMV Cam H7 接受名为：
>     firmware.bin
>     romfs.img
>     romfs0.img
> ```
>
> ⇒ **不管你文件内容对不对，名字不是 `firmware.bin` 就会被拒**。
> 所以**必须把裸镜像改名成 `firmware.bin`** —— 我们已经替你备好了两套（见下表）。

**操作**：

1. micro-USB 接笔记本，打开 `D:\OpenMV\bin\openmvide.exe`，连上相机；
2. 菜单 **工具 / Tools → Run Bootloader (Load Firmware)**（v4.7.0+ 里叫 **Load Custom Firmware**，快捷键 **`Ctrl+Shift+L`**）；
3. 选 **`metrics\logs\_flash_UVC\firmware.bin`** ← **就是它**（名字必须是 `firmware.bin`）；
4. 按提示让 IDE 把相机切进 bootloader/DFU 模式并刷写（可能要求确认**擦除内部 FAT**）；
5. **拔插一次 micro-USB**，等 Windows 识别 —— 它应该从「COM 口」变成「摄像头」。

**两套材料（都已改成 IDE 认得的文件名）**：

| 目录 | 文件名 | 大小 | sha256 | 用途 |
|---|---|---|---|---|
| `metrics\logs\_flash_UVC\` | `firmware.bin` | 115668 B | `6fbc7bbe03abb439415256c86755ddf9cc0784c792f67c204818655347461804` | **刷成 UVC 摄像头** |
| `metrics\logs\_flash_MICROPYTHON\` | `firmware.bin` | 1737476 B | `1e4e1a51d0a3d68d4d4b91f19f5cc8e7c611f3e881299876ef1003f19eb6b13e` | **回滚成 MicroPython** |

来源：`https://github.com/openmv/openmv/releases/download/v4.6.20/firmware_v4.6.20.zip`
（zip 也在 `metrics\logs\_v4.6.20_firmware.zip`）。上面两个 raw 镜像分别取自该 zip 的
`OPENMV4/uvc.bin`（115668 B）与 `OPENMV4/firmware.bin`（1737476 B）。取完**先核对 sha256 再刷**。

> ⚠️ **zip 里还有 `.dfu` / `.elf`**（`uvc.dfu` 115981 B、`firmware.dfu` 1737789 B、`bootloader.dfu` 22701 B）——
> 那些是**给命令行/DFU 工具用的容器格式**，**IDE 不认（名字不符）**，**别拿它们去刷**。
> ⚠️ 为什么不用 IDE 里的"官方 `uvc.bin`"：官方从 **IDE v4.7.0 起已下架**预编译 UVC 固件
> （本机 IDE 是 v5.0.0，release 里没有这个资产）—— 只能回到 v4.6.20 取。
> ⚠️ **命令行直刷走不通**（09-25 实测）：`dfu-util -l` / STM32CubeProgrammer 都报"没有 DFU 设备"，
> 因为相机停在正常模式；**让相机进 DFU 模式的可靠手段是 IDE**（或跳线短接 BOOT+RST）。

## 3. 刷完**先量，再演示**（这一步产出证据，别跳过）

```powershell
# 1) 它现在应该是标准 UVC 摄像头了，先找序号（会与笔记本自带摄像头区分）
python metrics/scripts/run_demo.py --list

# 2) 量它的真实能力 —— 把下面的 0 换成上一步打印的序号
python board/openmv/host_capture_test.py --list
python board/openmv/host_capture_test.py --device 0 --seconds 10 --probe 640x480,320x240
```

**判据**：

| # | 判据 | 不合格说明什么 |
|---|---|---|
| 1 | `--list` 出现一个**新的**序号 | **没有就说明没刷成**（这一步失败不是故障，是"还没刷"） |
| 2 | JSON 里有 `actual_width/height`、`fps`、`distinct_frames`、`first_frame_latency_ms` | 工具没跑对 |
| 3 | **`distinct_frames` ≈ `frames`** | `== 1` 表示拿到的是**冻结画面**，那个"帧率"是假的（工具会打 ⚠️） |

**产物**落 `metrics/logs/`（JSON + CSV）。⚠️ **这一步的数据是 A 线旁路画面带宽预算的输入**，
拿到后要回填 `fpga/report/`（那是硬件证据目录）。

> ⚠️ UVC 走的是 **USB full-speed（12 Mb/s）**，高分辨率只能靠 **MJPEG 压缩** ——
> 到底能给多大/多快，**以这一步实测为准**，不要引用官方页面上的数字。

## 4. 看画面（一条命令）

```powershell
# --source 0 换成 §3 找到的序号；--video-hz 是旁路画面的推送节奏
python metrics/scripts/run_demo.py --source 0 --seconds 60 --video-hz 25
```

浏览器会**自动打开脚本打印的那个网址**（服务端口是自动挑的空闲端口，**以打印的网址为唯一入口**）。

> 🔴 **一定要给 `--seconds`。** 不给就是"跑完整个源"，而活摄像头**永不结束**。
> 09-25 就留下了一份 **1.01 GiB / 4,640,214 行** 的 `metrics/csv/demo_metrics.csv`（大小与行数是我今天实测的；
> **【推测】成因多半是没给 `--seconds` 或在 `--loop` 下跑了很久**，我无法确认当时的具体命令）。
> 想长时间演示用 `--loop`（脚本会自动偏移 `frame_id`，保证契约要求的单调递增），**不要靠不给 `--seconds`**。

**两个通道，别搞混**（画面**不进**契约帧）：

| 通道 | 入口 | 去向 | 网页上是什么 |
|---|---|---|---|
| **指标**（契约） | `POST /api/ingest` | `/ws` → WebSocket | 数字 / 曲线 / 状态灯 / 事件 |
| **画面**（旁路） | `POST /api/frame`（JPEG 字节） | `GET /video.mjpg`（MJPEG） | **真实画面区** |

`--video-hz` / `--video-quality` / `--video-max-width` 可临时覆盖 `config.yaml` 的
`video_push_hz` / `video_jpeg_quality` / `video_max_width`，**不必去改三人共用的 `config.yaml`**。

**判据（四条，缺一不可）**：

| # | 判据 | 怎么确认 |
|---|---|---|
| 1 | 网页上有**真实画面**（不是占位网格） | 画面区有实时图像 |
| 2 | 网页上**数字/曲线/状态**在动 | 走契约通道 |
| 3 | **`distinct_frames ≈ frames`** | §3 第 2 条命令的输出 |
| 4 | 指标里 **`landmark_source` 是 `mediapipe`** | 看 `run_demo` 那个终端里 `run_pipeline` 结尾打印的"本次数据来源"。**是 `stub` 的话，这批数据的 EAR/MAR 不得作为算法结果引用** |

> 想要**落盘成证据**的 `landmark_source`：单独跑 `board/openmv/README.md` §T1.1 第 3 步那条命令
> （`backend/run_pipeline.py ... --summary metrics/logs/openmv_summary.json`）——
> `run_demo.py` **不传 `--summary`**，所以它只把来源打印到终端、不写文件。

**要交回的**：两条命令的完整输出 + 网页截图（截图放 `metrics/evidence/`，那是正式证据目录）。

> 📌 **测量一结束，画面会被判为"过期"并自动隐藏** —— 刻意设计（**不显示冻结的旧画面**），不是 bug。
> 这段由 `check_video_bypass.py` 的 T6 钉死。

## 5. 回滚（刷回 MicroPython）

要做任务 C 的能力矩阵、或相机行为异常时：

1. 相机进 bootloader 模式（绿灯呼吸；IDE 一般会自动切）；
2. IDE → **`Ctrl+Shift+L`** → 选 **`metrics\logs\_flash_MICROPYTHON\firmware.bin`**
   （1737476 B，sha256 `1e4e1a51d0a3d68d4d4b91f19f5cc8e7c611f3e881299876ef1003f19eb6b13e`）；
   ⚠️ **同样必须是 `firmware.bin` 这个名字**（原因见 §2 的红字）；
3. 拔插一次 micro-USB。

**回滚判据**：① 设备管理器里出现 **COM 口**（不是摄像头）；②
`python board/openmv/offline_check.py` 仍是 **28/28**；③ 能在 IDE 里跑 `openmv_capture_test.py` 的 `MODE="probe"`。

> 🔴 **更正（2026-09-26）**：本操作单早先写的"选 `_firmware_openmv4_rollback.dfu`"**是错的** ——
> `.dfu` 是 **DFU 容器格式**，而且**名字也不符合 IDE 要求**，两条都会让回滚失败。
> **正确做法是用 `_flash_MICROPYTHON\firmware.bin`（raw 镜像）**。
> （zip 里 `firmware.bin` 1737476 B 与 `firmware.dfu` 1737789 B 是**两个不同文件**，已实测比对确认。)
> ⚠️ 只有在 **bootloader 本身坏了**时，才考虑门路更硬的 DFU 手段（`bootloader.dfu` + 命令行）—— 平时别碰。

## 6. 红线（踩了就返工）

| ❌ 不要 | 为什么 |
|---|---|
| 把画面塞进契约帧 | 契约 §1 只允许那 9 个顶层字段，塞图像就是非法帧（`check_video_bypass.py` 的 T9/T10 会红） |
| 说"上板验证过了" | `board/bitstream/` 为空，**Mizar 从未上电**；UVC 画面只到 PS，**PL 根本看不到画面** |
| 靠"不给 `--seconds`"长时间演示 | 会写出 GB 级 CSV（09-25 实测 1.01 GiB），用 `--loop` |
| 引用没跑出来的分辨率/帧率 | 铁律 1：数字必须来自真实运行输出，不引用官方页面 |
| `pip install csi` / `sensor` / `omv` | 这些包**不存在**，是相机固件里的模块 |
| 在相机盘上存/编辑脚本 | H7 板载盘极小（43 KB 级就报 `Not enough disk space`），FAT 挂载失败会**自动格式化整个盘** |
| 同时刷 UVC 和跑 MicroPython 脚本 | 互斥，先决定这次要哪个 |

## 7. 这一页的诚实边界

- **写它的人（AI）没有跑过任何硬件**：OpenMV、Mizar 都不在这台机器上。所有硬件数字来自人类回贴的真实输出。
- **【已验证】**（本机真实运行）：§2 两个 raw 镜像的 sha256 与 zip 源条目一致；IDE 路径存在；
  相机盘已逐字节备份到 `board/openmv/flash_backup_20260926/`。
- **【已验证，2026-09-26 由用户截图确认】IDE 的刷机文件是**按文件名**校验的**：
  只接受 `firmware.bin` / `romfs.img` / `romfs0.img` ⇒ **`.dfu` / `.bin` 等名字一律被拒**
  （所以 §2 给出了改名后的 `_flash_UVC\firmware.bin`）。**原先"不确定吃 dfu 还是 bin"的疑问已闭合。**
- **这条路能证明什么**：只证明「相机 → 分析 → 网页」**软件链路**通了。
- **这条路不能证明什么**：**一个像素都不进契约帧**；与 HLS IP / DMA / Block Design / 上板**毫无关系**；
  且 UVC 像素**只到 PS，PL 看不到画面**（`docs/10` §采集分工）→ 它是**脱板演示**手段，
  **不是 M3 的正解**（M3 正解是 Mizar 自带的 **MIPI CSI + 树莓派摄像头**）。
- 本页所有判据数字（28/28、1.01 GiB、4,640,214 行）都是**当时的真实运行**，不是永久承诺；
  **跑出不同结果先报告事实，不要改期望值去凑绿。**
