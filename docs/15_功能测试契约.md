## 0. 这份文件是什么、**不是什么**（先读，防混淆）

| | 说明 |
|---|---|
| ✅ **是** | 把"**每个功能怎样才算通过**"固定下来，让测试方与修复方**引用同一条标准**，避免"这算 bug 还是设计如此"的争论 |
| ⚠️ **是** | 它是**测试契约**，需要 A/B/C 三方会签才生效（一方单独改 = 单方面改判据） |
| ❌ **不是** | **不是 `docs/interface.md` 那份接口契约**。本文件**不改变**任何字段/枚举/寄存器/算法口径 |

> 没有出处的判据**不许写进来** —— 那是"编造标准"，与铁律 1 同性质。

## 1. 判定三分类（**本契约的核心**）

测试发现的任何偏差，按下面顺序判定，**结论只能落在这三类之一**：

```
发现一个偏差
   │
   ├─ ①「预期行为」？ ── 在 §4 白名单里 → 不是缺陷（记为"确认，非缺陷"）
   │
   ├─ ②「待前提」？ ── 缺素材 / 缺硬件 / 缺标定 / 缺会签 → 不是缺陷
   │                     （记为"未验证"，**且不得写成"已通过"**）
   │
   └─ ③ 与 §3 的通过标准不符 ──→ 缺陷 → 进 `docs/16_测试问题台账.md` 立卡片
```

| 类别 | 定义 | 处理 |
|---|---|---|
| **缺陷** | 违反了 §3 里**有出处**的通过标准，且不属于下面两类 | 立卡片、定级、分工修复 |
| **预期行为** | 设计如此，**已在 §4 白名单声明** | 记"非缺陷"，**但可在台账里登记为"文档需澄清"** |
| **待前提** | 缺素材/缺相机/缺 bitstream/缺标定/缺会签 | 记"未验证"，写清缺什么 |

> ⚠️ **最容易犯的错**：把第 ② 类写成"通过"。比如"rPPG 端到端 ✅"是**错的**，
> 正确写法是"链路已验、**真实视频端到端未验证**"。

## 5. 证据标准（**什么算"有证据"**）

| 级别 | 什么算 | 能支撑什么结论 |
|---|---|---|
| **E-1 可复现命令 + 原始输出** | 完整命令 + 未改动的 stdout/JSON | 可写"已验证"，可进报告 |
| **E-2 脚本化检查** | `check_*.py` 通过、pytest 通过、自检 N/N | 同上，且能防复发 |
| **E-3 截图/录屏** | 界面截图存 `metrics/evidence/` | 可写"界面上可见" |
| **E-4 人类回帖的硬件原始输出** | 真机 stdout 原样回贴 | 可写"真机实测"，**必须注明是哪块板/哪个固件** |
| ❌ 不算证据 | 口头描述、AI 的推测、"应该没问题"、官方页面数字 | **不能支撑任何结论** |

**归档位置**：界面证据 → `metrics/evidence/`；硬件测量 → `fpga/report/`；运行产物 → `metrics/logs/`（不入库）。

## 7. 本契约的变更流程

1. **谁都不能单方面改判据**：改 §3 的通过标准 = 改判据，必须 **A/B/C 三方确认**；
2. 改判据的理由必须是"**发现原判据与 `docs/interface.md` 或 `config.yaml` 不符**"，**不许**是"改完好让它通过"；
3. 每次修改在本节下登记：**日期 / 版本 / 谁 / 改了什么 / 为什么**；
4. **改了通过标准，必须回头重判已登记的卡片**（`docs/16`）。

## 9. 本文件的诚实边界

- 起草者（AI）**没有跑过任何硬件**；硬件数字全部来自人类回贴的真实输出。
- 本文件中的**【已验证】**标记，指的是 **2026-09-26 本机实跑**得到的结果；**跑出不同结果先报告事实**。
- 本文件**不替任何人拍板**：判定"这是不是缺陷"的权利在**测试者 + 对应线的负责人**，
  AI 只做原因分析与归档。
