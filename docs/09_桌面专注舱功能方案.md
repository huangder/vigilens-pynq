> 项目：知倦 / VigiLens（AMD FPGA 创新设计赛道 3.3，自主选题初级组）
> 文档性质：产品功能与实现设计草案；不是接口契约，不代表已经实现或上板验证。
> 日期：2026-09-23
> 相关文档：`docs/interface.md`、`config.yaml`、`backend/decision.py`、`frontend/README.md`、`board/README.md`

> **请 A 线、C 线队友一起集思广益：**这份文档提出“疲劳趋势触发、用户确认后切换桌面休息场景，并保存任务锚点”的功能构想，当前只是讨论稿，不是分工或实现决定。请重点补充：这个功能是否有吸引力、演示闭环是否合理、A 线能提供哪些可信触发证据、C 线现有 FPGA/板卡条件怎样支撑可见反馈，以及你们认为应该删掉或替换的部分。先在本文件“待团队拍板”处记录意见；涉及冻结接口时仍按 `docs/interface.md` 的会签流程执行。

## 1. 目标与定位

### 1.1 功能目标

把知倦从“观察状态并显示提示”扩展为“在用户确认后，帮助调整桌面环境并保留当前任务上下文”。系统发现疲劳风险持续存在且输入质量合格时，提出进入休息模式；用户确认后，环境控制器执行预先授权的低风险动作，并保存当前学习任务锚点。用户休息后可以一键恢复原来的任务。

### 1.2 一句话体验

> 知倦发现你可能需要休息，先询问；你确认后，它调好桌面环境并替你记住做到哪里，回来时一键接上。

这项功能的产品亮点是**从状态感知走到可撤销的人机协作**：提出建议、用户确认、环境改变、上下文保存、用户恢复。它不是自动判断用户“必须休息”，不作健康诊断，也不以灯光变化替代有效的疲劳判断。

### 1.3 首版范围

首版采用可控、适合桌面演示的范围：

- 疲劳风险持续满足后，在网页和实体控制器上提出休息建议；
- 用户按确认键后，启动 3 分钟休息计时；环境设备执行一个预设场景；
- 保存用户当前选择的任务锚点，例如课程链接、时间戳、章节名或手工输入的一行任务；
- 休息结束时提醒用户，可选择“恢复任务”“再休息一会儿”或“结束”；
- 提供实体“暂停/撤销”键；传感器状态不可靠、程序断连或控制链路故障时，禁止自动动作并回到安全状态。

首版不承诺仅凭摄像头准确识别学习进度、理解课程内容、判断用户是否听懂，也不自动移动鼠标键盘、锁定设备、控制市电插座或启动机械机构。

## 2. 使用场景与交互流程

### 2.1 典型场景

用户在电脑前学习，前端运行知倦；系统通过视频分析行为趋势。用户可在“任务栏”手动选择当前课程或输入“正在做：线性代数第 3 讲”。当系统得到持续疲劳风险且质量门控通过，生成休息提议。用户确认后，进入短休息模式；任务锚点被保存。休息结束，用户确认恢复，页面重新打开或定位到锚点。

### 2.2 状态流程

```text
正常工作
  │ 持续疲劳风险 + 质量通过
  ▼
休息建议待确认 ── 用户拒绝/稍后 ──▶ 正常工作（进入冷却期）
  │ 用户确认
  ▼
保存任务锚点 → 环境切换 → 休息计时
  │ 用户提前结束 / 计时结束
  ▼
恢复选择 ── 恢复任务 ──▶ 任务锚点打开 → 正常工作
          ├─ 再休息 ───▶ 休息计时
          └─ 结束 ─────▶ 正常工作

任何阶段：质量不可靠 / 断连 / 控制器故障 → 禁止新动作，提示原因，允许用户手动继续
```

### 2.3 页面与实体交互

前端提供窄而清楚的“专注舱”区域：

- 当前任务：标题/链接/定位信息和“保存当前锚点”；
- 建议卡：建议原因、触发证据、质量状态；
- 明确操作：“休息 3 分钟”“稍后提醒”“忽略本次”；
- 休息状态：剩余时间、设备状态、提前结束；
- 恢复卡：任务锚点与“继续学习”“再休息”“结束”；
- 控制器连接状态及手动暂停/复位。

实体端首选 USB 串口微控制器（例如 ESP32 / RP2040）驱动低压 LED 灯带或桌面灯模块，并接一个确认/取消按钮。网页和实体端对同一会话状态给出反馈：屏幕显示动作，灯光用预先定义的颜色/闪烁表示待确认、休息中、恢复中和故障。灯光只作环境氛围与状态提示，不承担警报或安全功能。

## 3. 产品规则与安全约束

### 3.1 建议规则

- 只有 `fatigue_risk` 且质量门控有效时，才允许创建休息提议；`unreliable`、`adjust_posture`、`disconnected` 和 `done` 都不能触发设备动作。
- 休息提议必须经过用户确认；默认不自动调灯、不暂停应用、不强制锁屏。
- 同一疲劳事件最多提出一次；用户选择“稍后提醒”后进入冷却期，避免连续弹窗。冷却期、持续判定时长、休息时长等参数必须进入 `config.yaml`，实施时需要 A/B/共享文件负责人按项目分工协调。
- 若用户未响应，保持原环境，界面可轻提示但不重复打断。
- 休息结束只发提示，不强制恢复或关闭任何程序。
- 任何质量下降或系统断连都只影响建议资格；不得把“不可靠”转换成“疲劳”。

### 3.2 安全默认值

- 控制对象仅限可安全失效的低压 LED/兼容智能灯场景；原型优先 USB 供电。不要裸露接线控制市电，不要用继电器切断主照明、电脑电源或风扇等关键负载。
- 硬件断电、串口断开、服务崩溃时，设备应停止接收新命令并保持低风险状态；恢复连接后必须重新同步会话状态，不重放过期命令。
- 控制消息带单调递增 `command_id`、会话 ID、动作白名单和过期时间；控制器拒绝未知动作、重复命令与过期命令。
- 保存最少必要的任务上下文，默认只保存在本机；用户能查看、覆盖和清除。不得保存或上传原始人脸视频作为任务锚点。
- 用户始终可以通过实体取消键或网页按钮立即退出休息模式。

## 4. 系统结构与职责

```text
摄像头 → 现有 A 线分析/质量门控 → 现有 status + triggers
                                  │
                                  ▼
                         专注舱会话控制器
                         ├─ 规则/状态机
                         ├─ 本地任务锚点存储
                         ├─ 用户确认与冷却期
                         └─ 设备动作白名单
                           │                 │
                      前端网页          USB 串口
                       显示/交互          微控制器
                                           ├─ 按钮输入
                                           └─ 低压 LED 输出

PL：继续提供确定性图像预处理；首版不让 FPGA 直接控制灯具或发起休息动作。
```

### 4.1 软件模块建议

新增功能宜先作为独立模块实现，避免把会话、副作用和现有帧判定耦合在一起：

- `FocusSessionController`：消费已验证帧和判定证据，产生提议/会话状态；
- `TaskAnchorStore`：本机保存当前任务标识和定位信息；
- `DeviceAdapter`：定义 `propose_scene`、`set_scene`、`safe_off` 等窄接口；
- 串口实现：将经过白名单校验的命令发给微控制器；
- Mock 实现：比赛开发与离线演示时模拟设备，输出同样的状态事件。

设备控制器不直接读取视频，也不自行判断疲劳；它只接受来自会话控制器、经过用户确认的有限动作。控制器故障不得导致视频处理服务或现有指标管线崩溃。

### 4.2 FPGA 在该功能中的位置

现有 FPGA IP 负责像素/时间序列预处理。专注舱首版不需要为灯光或任务恢复新增 HLS IP；新增控制属于低带宽、强交互逻辑，放在 PS/前端/微控制器更合适。比赛演示可把现有 PL 输出用于画面质量/运动质量判据，并明确展示“质量不足则不提出建议”。上板闭环仍要按 `board/README.md` 的 C8~C10 实测门限执行。本文件不宣称已有板卡或专注舱硬件验证。

## 5. 通信与契约边界

`docs/interface.md` 是唯一冻结契约。首版不得给 A→B 指标帧增加字段或扩大 `status` 枚举。现有 B 线已建立通过 `/api/status` 旁路传输阈值与判定证据的做法；会话状态可沿用独立 REST/WebSocket 控制资源或本地服务，不混入测量帧。

可先采用以下控制消息草案（**不是冻结契约**，实现前由负责线确认并评审）：

```json
{
  "session_id": "local-generated-id",
  "command_id": 12,
  "action": "set_scene",
  "scene": "rest",
  "expires_in_ms": 3000
}
```

允许动作只包括经过产品确认的有限枚举，例如 `set_scene:focus`、`set_scene:rest`、`safe_off`；不得接受任意 GPIO 编号、任意 shell 命令或用户提供的设备脚本。状态反馈需包含会话 ID、命令 ID、确认/失败和时间戳，便于识别过期响应。若选择新增 API 路由或持久化 schema，先复用项目已有服务结构并补相应测试。

任务锚点建议用版本化 JSON 存本机，例如：

```json
{
  "schema_version": 1,
  "task_title": "数字电路课程",
  "resource_uri": "https://example.invalid/course/lesson-3",
  "position_seconds": 812,
  "saved_at_session_seconds": 1540
}
```

实际实现应校验 URL scheme、长度和本地路径范围；不从摄像头推断网页内容或阅读位置。视频播放器的精确恢复需要播放器提供当前播放时间接口；普通浏览器跨站页面通常无法被另一个网页读取进度，首版提供可编辑的任务名/链接与手动位置即可。

## 6. 硬件与物料

### 6.1 首选原型

| 项目 | 用途 | 选择原则 |
|---|---|---|
| PYNQ-Z2 | 现有 FPGA/PS 平台 | 运行视觉预处理与主系统；状态以实测为准 |
| 普通 USB RGB 摄像头 | 现有输入 | 使用本机/板端可稳定获取的摄像头 |
| 笔记本/显示器 | 运行网页与课程任务界面 | 能展示休息前后任务恢复 |
| ESP32 或 RP2040 开发板 | USB 串口桥、按钮与 LED 控制 | 选队伍已有、可稳定供电与通信的开发板 |
| 低压 RGB LED 灯带/桌面灯 | 休息/专注场景反馈 | 使用额定电压匹配的成品模块与独立供电；不直接接开发板 GPIO 供大电流 |
| 2 个按钮 | “确认休息”与“取消/恢复” | GPIO 上拉/下拉与去抖；失效时软件按钮仍可用 |
| USB 线、面包板/端子、限流/驱动模块 | 原型连接 | 按灯具电流选驱动，不让 MCU 引脚直接驱动负载 |
| 桌面支架/遮光板（可选） | 固定摄像头并改善取景 | 不遮挡散热与板卡接口 |

若暂时没有微控制器或灯具，第一阶段完全可用软件 Mock 完成交互。后续硬件只承担已确认的灯光状态；不能让缺少外设阻断主系统开发。

### 6.2 可选而非首版必需

- 环境光传感器：自动选择灯光场景前可测量环境照度；需配置标定并评估放置位置。
- 旋钮/小屏：离线调试与无需看网页的交互。
- 智能插座：仅使用有认证的成品产品及其明确支持的接口；首版不控制台灯市电或电脑电源。
- 振动/蜂鸣反馈：容易造成打扰，需作为用户主动选择项，默认关闭。

物料采购前先盘点队伍已有设备、板卡与电源规格；本文不给价格或性能承诺，价格和兼容性以实际采购与实测记录为准。

## 7. 前端演示设计

专注舱应作为现有仪表盘中的一个可操作工作区，而不是再做一套孤立的营销页面：

1. **工作中**：展示当前任务、质量是否允许提议、设备当前场景；
2. **提议休息**：说明证据来自哪些现有触发项，给出“休息 / 稍后 / 忽略”；不显示 stub 数值为算法结果；
3. **休息中**：显示可撤销倒计时、灯光状态及已保存任务锚点；
4. **恢复**：展示锚点与“继续/再休息/结束”操作；
5. **不可用**：灯具断连、质量不足或服务中断时说明原因，网页交互仍可继续。

页面强调任务上下文和环境动作。不要把闪烁动画、多个大数字或长篇说明作为主视觉；动作应稳定、可预测，并支持离线 Mock。

## 8. 比赛演示流程

建议控制在约 60~90 秒，数字/事件以现场真实运行结果为准：

1. 打开一个本地课程/任务页，在专注舱录入任务标题与当前位置。
2. 展示正常状态下专注灯场景；确认界面显示当前数据源和质量状态。
3. 通过可重复的行为/预先准备的标注视频触发 fatigue-risk 场景；先展示“原因与证据”，系统只提出建议，不自动改变设备。
4. 用户按实体确认键；页面显示保存锚点和休息倒计时，低压灯切换到休息场景。
5. 用户按取消键提前恢复，或在计时完成后选择恢复；页面重新显示保存的课程锚点，灯光回到专注场景。
6. 可选展示故障边界：断开 USB 控制器或降低视频质量，系统标注控制器/信号不可用且不继续发新命令；网页手动继续仍可用。

现场必须有无硬件备用路径：设备适配器切到 Mock，网页与状态流程照常演示，并清楚标出模拟输出。不得把 Mock 灯状态说成真实硬件响应，也不得把 `landmark_source=stub` 的指标作为真实算法结果。

## 9. 验收与证据

验收数字须在真实试验后填写；以下是需要执行的检查项，不是已经达到的性能结论：

| 检查项 | 判据 | 证据建议 |
|---|---|---|
| 状态准入 | 只有有效质量下的 fatigue-risk 能生成提议；不可靠/断连不得生成 | 单元测试与事件日志 |
| 用户确认 | 未确认不发设备动作；拒绝/稍后均不发动作 | Mock 设备命令记录、视频演示 |
| 幂等与过期 | 重复/过期 command_id 不重复执行 | 串口协议测试 |
| 手动取消 | 休息提议与休息状态均能被取消，设备回到预设安全场景 | 实物录像、串口日志 |
| 任务恢复 | 保存后服务重启/页面刷新仍可读；用户能编辑、清除锚点 | 本机回归测试 |
| 故障降级 | 设备断连不会崩溃主流水线；不重放旧命令；页面可继续手动操作 | 故障注入测试 |
| 硬件电气 | 电源电压/电流符合模块规格；GPIO 不直接承载灯带电流 | 接线图、器件规格和实测记录 |
| 端到端 | 从有效提议到用户确认、灯光反馈、任务恢复流程闭合 | 可复现脚本与现场记录 |

建议保留 `metrics/logs/` 供本地临时试验；正式证据按仓库约定放入经负责人确认的证据目录。证据包含软件版本、配置、数据源类型（真实/Mock/stub）、设备固件版本、命令日志和失败案例。不得编写尚未执行的“通过”结果。

## 10. 开发分期与分工

本功能横跨 A/B/C/共享边界，需先由团队确定负责人；本文件本身不替队友会签，也不授权跨线改代码。

### 阶段 0：范围确认与 Mock 交互

- 决定休息时长、灯光动作、任务锚点字段和谁负责每条线；参数来源集中到 `config.yaml`。
- B 线用 Mock 设备完成“建议—确认—休息—恢复”交互；不改冻结指标 schema。
- 验收：正常/疲劳/不可靠/断连路径都可交互，且不可靠路径不能触发建议动作。

### 阶段 1：会话控制器与本机锚点

- 由 A/B 线按各自边界实现规则消费、会话状态机和本地最小持久化。
- 补事件记录、冷却期、重复确认和服务重启测试。
- 验收：同一逻辑输入可确定性复现；持久化内容可检查和清除。

### 阶段 2：USB 微控制器和低压灯光

- C 线/指定硬件负责人实现 MCU 协议、按钮、灯光驱动和故障安全状态；PS 侧实现串口适配器。
- 先用 LED 单灯验证协议，再接额定合适的灯带/灯具；写接线图、固件版本和真实日志。
- 验收：命令确认、重复/过期拒绝、断线恢复、实体取消均通过。

### 阶段 3：与真实数据及 PYNQ 闭环

- 确认 A 线 landmark 来源为真实实现，且 P4 标定/项目现行回归检查真实通过。
- 板卡到位后，先按 `board/README.md` 和 `fpga/report/m3_system_budget_v1.md` 完成 C8~C10，再接入现有质量/事件输出；灯光控制仍由 PS/MCU 执行。
- 在无板卡开发机、无 MCU、断网等条件下分别跑保底演示。

具体负责人、日期和依赖在团队确认后填入项目任务管理处；本文件不虚构队伍排期或已有器件。

## 11. 风险与决策

| 风险 | 影响 | 应对 |
|---|---|---|
| 现有视觉指标仍是 stub 或阈值未标定 | 建议时机不可信，外设动作失去可信基础 | 阶段 0/1 可用明确标注的 Mock；阶段 3 前完成 A 线真实 landmark 和场景验证 |
| 新功能过度打断用户 | 体验变差 | 默认只提议一次；稍后/忽略进入配置冷却期；实体取消随时可用 |
| 灯具/串口故障 | 演示动作缺失或重复 | 设备适配器隔离故障、幂等命令、Mock 保底；不依赖灯具才能使用任务锚点 |
| 控制市电或危险设备 | 人身/设备风险 | 首版限低压 LED；不触碰市电与关键负载 |
| 浏览器无法恢复第三方课程位置 | “自动续播”无法实现 | 首版用手工任务锚点；仅对自有/受控播放器接精确时间戳恢复 |
| 过度扩展偏离 FPGA 赛道 | 核心硬件工作不可见 | 灯光是用户体验闭环；赛道证据仍由 HLS IP、C 仿真/综合、上板软硬件逐点对拍提供 |
| 自动休息暗示诊断或强制管理 | 合规与用户信任风险 | 统一用“趋势提示/辅助建议/实验室原型”；确认权交还用户 |

### 11.1 待团队拍板

1. 首版只做低压灯光 + 任务锚点，还是只做其中一项？
2. 休息动作具体控制哪类灯，队伍已有 MCU/LED/电源是什么？
3. 任务锚点首版支持课程网页、视频播放位置，还是仅任务标题/手工时间点？
4. 实体按钮的角色、固件和串口链路由谁负责？
5. 如何与现有 B 线证据旁路和 A 线触发项接合，是否需要单独控制 API？

## 12. 当前仓库事实与结论标注

- 【已核对】`docs/interface.md` 的指标 schema 与 6 值 `status` 枚举已冻结；本功能可先作为独立会话/控制面实现，不扩展帧契约。
- 【已核对】`config.yaml` 是阈值唯一来源；新增长度、持续时间、冷却期和串口超时参数实施时需要走共享配置变更。
- 【已核对】现有 `backend/decision.py` 已提供规则触发项；B 线有判定证据旁路，但最新仓库说明仍要求 A 线接入触发项。实施前应核查当前集成提交。
- 【已核对】`board/README.md` 将 bitstream、C8/C9/C10 上板验证标为待办/未验证；不得在比赛材料中写成已上板。
- 【已核对】`backend/README.md` 说明真实 MediaPipe 运行需核对 `landmark_source`；stub 运行数据不能作为算法结果。
- 【设计建议】专注舱 MCU/灯光是新增外围设备，不要求写进 FPGA 冻结 IP 契约，也不应为了它新增 HLS IP。
- 【待验证】具体 USB 串口协议、LED 电气连接、会话 API 与真实数据下的触发体验，需要原型实现与团队评审后验证。
