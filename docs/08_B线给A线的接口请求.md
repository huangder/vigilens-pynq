## 1. 接口现状（A 线核对过的事实，附出处）

### 1.1 B 线服务已经对外的接口（出处：`backend/api.py` 第 4~7 行与其实现）

| 端点 | 方法 | 作用 | 返回要点 |
|---|---|---|---|
| `/api/status` | GET | 最新一帧 + 总线状态 | `ok` / `source`（`mock` 或 `ingest`）/ `published` / `subscribers` / `frame` / `server_time` |
| `/api/metrics` | GET | 最新一帧 + 最近 N 帧历史（趋势曲线用） | `count` / `latest` / `history[]`：`ts` `frame_id` `blink_rate_per_min` `perclos` `hr_bpm` `quality_overall` `status` |
| `/api/events` | GET | 状态迁移日志（事件列表用） | `count` / `events[]`：`ts` `frame_id` `from` `to` `advice` `reason` `source` |
| `/api/ingest` | POST | **M2 集成点**：把契约帧推进来即广播 | 合法 → `{"ok": true, "published": N}`；不合法 → **HTTP 422** + `errors[]` |
| `/ws` | WebSocket | 逐帧推送 | 推裸帧（`/api/status` 的 `frame` 多包一层）；数据中断后的行为见 §3 的 N-2 |
| `/` | GET | 托管 `frontend/`（省掉跨域与 `file://`） | 仪表盘页面 |

### 1.2 A 线侧已经提供的数据通道

| 通道 | 命令 / 位置 | 适用场景 |
|---|---|---|
| **跨进程推送（M2 正式通道）** | `python backend/run_pipeline.py … --post auto` → 逐帧 `POST /api/ingest` | 网页显示 A 线真实数据（P5 已验证） |
| 离线回放 | `python backend/websocket.py --mode file --file metrics/logs/stream.jsonl` | 不跑管线也能演示（用 A 线产出的流） |
| 进程内总线 | `backend/hub.py` 的 `HUB` | **只在同一进程内有效**，跨进程无效（见 §3 的 N-3） |
| 快照文件 | `metrics/logs/last.json`（最新一次**测量**帧）、`stream.jsonl`（逐帧流） | 事后分析 / 回归比对；`logs/`、`csv/` 按约定不入库 |

### 1.3 B 线前端实际消费的字段（出处：`frontend/app.js` 的 `CARD_DEFS` 等）

`behavior`：`ear_left` `ear_right` `blink_state` `blink_count` `blink_rate_per_min` `perclos` `long_close_count` `mar` `yawn_count`
`face`：`visible` `bbox` `pose.yaw` `pose.pitch`
`quality`：`overall` `light_score` `motion_score`
`vital`：`hr_bpm` `hr_conf` `rr_per_min` `rr_conf`（门控不通过时显示"暂不出数/已锁定"）
顶层：`ts` `frame_id` `status` `advice` `reason`

> 以上均为契约 §1 已冻结的字段，**A 线的真实输出必须全部齐全**（`vital.*` 允许 `null`）。
> P5 实测：这些字段在真实浏览器里逐字段对上了（见 `backend/A_LINE_DEV_STEPS.md` §4 的复验记录）。

## 3. A 线 → B 线：需要配合或知悉的事项（每条都有出处）

| 编号 | 事项 | 出处 / 证据 | 希望 B 线做什么 |
|---|---|---|---|
| N-1 | 仪表盘地址栏默认 `ws://127.0.0.1:8765`（`websocket.py` 的端口）。用 `api.py` 托管页面时（`http://127.0.0.1:8000/`），地址要手改成 `ws://127.0.0.1:8000/ws` | `frontend/index.html` 的 `id="wsUrl"` 默认值；P5 复验时实测 | 视情况把默认值改成"同源自动推导"（属 `frontend/`，A 线不代改） |
| N-2 | **服务端 `/ws` 在数据中断后不发兜底 `disconnected`**：`api.py` 的 ws 循环里 `HUB.latest` 一旦非空，队列空就 `continue`，不再走兜底分支。**网页不受影响**（`app.js` 有 3 秒客户端看门狗），但第三方消费者（未来的前端重构、脚本客户端、`--mode bus`）会静默等不到 | 实测：连上 `/ws` → 推一帧 → 静默 7 秒（> `ws_disconnect_timeout_s=3.0`）→ 一个帧都没收到；代码位置 `backend/api.py` 的 `ws_endpoint`。另：`backend/hub.py::iter_subscription()` **已经实现**超时兜底，但 `api.py` 没用它 | 建议 ws 循环改用 `iter_subscription`（或补一条超时分支）。属 B 线文件，A 线不代改 |
| N-3 | M2 正式通道是 `POST /api/ingest`，**不是**进程内 `hub.HUB` | 见 §2 的 R-002 | 把 `websocket.py --mode bus` 的用途描述更新为"仅同进程场景"，避免下一个人照着走弯路 |
| N-4 | **同一时刻只允许一个 A 线推送源**：同时跑两个 `run_pipeline --post`，B 线历史里的 `frame_id` / `ts` 会交错，违反契约 §1 的单调递增 | P5 复验实测（A 线自己起两个推送进程复现） | 若 B 线做集成测试需要多段数据，请**顺序**跑，后段由 A 线加 `--frame-id-offset` |
| N-5 | A 线推送节奏是**逻辑时间** 1 帧/秒（契约 `ws_push_hz: 1.0`）。回放比实时快几十倍 → 网页看着像"快进"（30 秒回放 1.6 秒内推完 31 帧） | P5 复验实测 | 若 B 线需要"逐秒跳动"的实时观感，告知 A 线，A 线加按视频帧率节流的选项。**契约没要求**，属演示效果 |
| N-6 | A 线**不会私自**扩大契约：任何字段/枚举/节奏的增改都先改 `docs/interface.md` 第 6 节变更记录 + 群公告 | `AGENTS.md` §4 | 请 B 线在提"要新字段/新接口"时顺带说明**是否接受走契约流程**，否则 A 线只能答复"需三方确认" |
