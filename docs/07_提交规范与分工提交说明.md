## 1. 一句话总则

> **只对契约开发；提交前跑自检；提交信息写清「哪条线 + 为什么改 + 怎么验证的」。**

三条具体含义：

1. **只对契约开发**：任何字段名、寄存器偏移的改动，先改 `docs/interface.md` 再改代码（§7）。
2. **提交前跑自检**：§6 那 5 条命令全绿才算"完成"，不接受"我屏幕上跑了一下"。
3. **提交信息有正文**：评审会看 commit log。只写"update"、"fix"的提交等于没写。

## 2. 每人开工前的一次性配置（每人只做一次）

### 2.1 提交身份（**必须做**，否则你的贡献不计入你名下）

GitHub 靠**提交邮箱**把提交绑定到账号。用错邮箱，即使代码是你写的，Contributors 名单里也不会有你。

```bash
cd <你的仓库目录>
git config user.name  "<你的 GitHub 用户名>"
git config user.email "<数字ID>+<你的用户名>@users.noreply.github.com"
```

数字 ID 去哪找：浏览器打开 <https://github.com/settings/emails>，
勾选"Keep my email addresses private"后显示的那串地址就是标准答案（形如 `268549999+pig-pigking@users.noreply.github.com`），直接抄。

> ⚠️ 注意用 `git config`（**不加 `--global`**）：只对本仓库生效，不会污染你其他项目的身份。
> ⚠️ 2017-07-18 之前注册的老账号，noreply 地址是 `用户名@users.noreply.github.com`（不带数字 ID），以 <https://github.com/settings/emails> 显示为准。

验证方式：提交后打开 <https://github.com/huangder/vigilens-pynq/graphs/contributors>，
或者看提交详情页作者头像是否可点击跳转到你的主页。

### 2.2 仓库权限（协作者）

仓库是 huangder 的个人仓库，**写权限只能由他授予**：

1. huangder 操作：`Settings → Access → Collaborators and teams → Add people → 搜你的用户名 → 角色选 Write → Add`
2. **你必须点接受**，否则照样 403：<https://github.com/huangder/vigilens-pynq/invitations>
3. 验证：`git push` 能成功即为通过

### 2.3 本机 git 环境

用 Steam++ / Watt Toolkit 加速 GitHub 的同学，**第一次 push 前必看附录 A**，
否则会遇到 `schannel: SEC_E_NO_CREDENTIALS` 这个极具误导性的报错。

## 3. 分支策略（三人小组，目录不重叠）

我们的三条线**目录天然不重叠**，这是可以直推 `main` 的前提：

| 情况 | 做法 |
|---|---|
| 只改自己那条线的目录（见 §5） | **直接推 `main`** —— 三人小组走 PR 太慢，收益不抵成本 |
| 改契约 `docs/interface.md` | **必须先群公告 + 另两人确认**，再推（§7） |
| 改根文件（`README.md` / `config.yaml` / `.gitignore` / `requirements.txt`） | 建议开分支或先说一声，这是三人共用的文件 |
| 实验性/可能推翻的改动 | 开分支：`a-line/xxx`、`b-line/xxx`、`c-line/xxx` |

> 为什么不做强制的 PR 流程：三人的写区互不重叠，PR 只会增加等待成本。
> 真正的耦合点是**契约**，所以把纪律压在契约上（§7），而不是压在 PR 上。

## 4. 提交信息格式

```text
<线>: <一句话主题，动词开头，≤50 字>

为什么改：
改了什么：
怎么验证的：（必须贴真实命令 + 真实结果）
```

**线标签**（这是三人分工在 git 历史里最直接的体现）：

| 标签 | 归属 |
|---|---|
| `A:` | A 线（算法/后端） |
| `B:` | B 线（前端/可视化） |
| `C:` | C 线（FPGA/HLS/上板） |
| `shared:` | 三方共享（`config.yaml`、`metrics/`、`skill/`） |
| `contract:` | 接口契约（`docs/interface.md` 及其两侧实现） |
| `docs:` | 文档（`docs/`、各 `README.md`） |
| `repo:` | 仓库基建（`.gitignore`、`.gitattributes`、`pytest.ini`） |

**规则**：

- 主题用中文，但**技术名词保留英文**（EAR / PERCLOS / AXI-Stream / HLS / DMA），便于检索；
- 一个提交只做一件事：不要把"加 IP"和"改阈值"塞进同一个提交；
- **"怎么验证的"这一栏不许空**，这是《05》铁律 1（数字必须来自真实运行）在 git 历史里的落地。

## 6. 提交前自检（5 条命令，全绿才能提交）

```bash
python -m pytest                                     # 契约与可复现性测试
node frontend/mock.js --selftest                     # JS 侧契约自检
python metrics/scripts/check_frontend_wiring.py      # app.js 引用的 DOM id 是否都存在
node frontend/mock.js --limit 6 > metrics/evidence/js_frames.jsonl
python metrics/scripts/check_frontend_contract.py metrics/evidence/js_frames.jsonl   # 跨语言契约
git status --short                                   # 只应出现你本线的改动
```

| 命令 | 期望输出 | 失败了说明什么 |
|---|---|---|
| `pytest` | `65 passed`（**只增不减**） | 契约被改坏、引入了非确定性（时间戳/随机数泄漏进指标），或新增功能没带测试 |
| `--selftest` | `"ok": true` | JS 的 mock 与校验器不自洽 |
| `check_frontend_wiring` | `通过` | `app.js` 引用了不存在的 DOM id（症状：页面不报错但区域空白） |
| `check_frontend_contract` | `通过` | **A 的 Python 与 B 的 JS 对同一份契约判断不一致** —— M2 集成必炸 |
| `git status` | 只有你本线文件 | 你碰了别人的目录，或误提交了生成物 |

## 7. 契约变更的强制流程（唯一能让三人一起返工的路径）

> 契约是三条线**唯一的耦合点**（《02》4）。改它的成本远高于改代码，所以单独定流程。

1. **先改 `docs/interface.md`**，并在第 6 节「变更记录」里写清：日期 / 版本号 / 谁 / 改了什么；
2. **同步两套实现**：`backend/contract.py`（Python 侧）与 `frontend/mock.js`（JS 侧）——
   只改一边，另一边的校验器就会把合法帧判成非法；
3. **跑跨语言检查**（§6 第 4 条）；
4. **群公告**，等另两人确认「收到、不冲突」再提交；
5. **会签升级版本号**：`docs/interface.md` 已于 2026-09-11 **冻结为 🔒 v1.0**（由 C 线发起；
   第 5.1 节 5 项已核销并附证据；**第 5.2 节 6 项中，B 线第 3 项已于 2026-09-13 补签（见契约 5.2.1），
   A 线 5 项仍待书面表态 —— 契约里未代签**）。
   认可即补签 5.2；有异议按本节流程提变更，走完出 **v1.1**。

**改契约的提交必须是 `contract:` 前缀**，且正文写清"影响哪条线、需要谁配合改什么"。

## 附录 A：Steam++ / Watt Toolkit 下 git 连不上 GitHub 的修法

**症状**：`git push` 报 `schannel: AcquireCredentialsHandle failed: SEC_E_NO_CREDENTIALS (0x8009030e)`。
**这是极具误导性的报错**——它看起来像证书问题，实际是这个环境里 **schannel 拿不到加密凭据**。
证据：`curl.exe`（同样走 schannel）报同一个错，即使加了 `-k` 也一样；而 Python（走 OpenSSL）能正常请求。

**根因**：Steam++ 用 **hosts 模式**把 `github.com` / `api.github.com` 等指向 `127.0.0.1`，
自己在本地 443 端口做反向代理并替换证书（`CN=SteamTools Certificate`）。
浏览器信任它（它把根证书装进了 Windows 证书库），但 git 不认。

**修法：把 git 的 TLS 后端换成 OpenSSL，并把 Steam++ 的根证书并进 CA bundle**（不要用 `sslVerify=false`）：

```powershell
# 1) 导出 Steam++ 根证书
$certDir = "$env:USERPROFILE\.git-certs"
New-Item -ItemType Directory -Force -Path $certDir | Out-Null
$cert = Get-ChildItem Cert:\CurrentUser\Root | Where-Object { $_.Subject -match 'BeyondDimension' } | Select-Object -First 1
$pem = "-----BEGIN CERTIFICATE-----`r`n" + [Convert]::ToBase64String($cert.RawData, 'InsertLineBreaks') + "`r`n-----END CERTIFICATE-----`r`n"

# 2) 合成 bundle = Git 自带公共 CA + Steam++ 根证书（保留校验）
$combined = "$certDir\ca-bundle-with-steamtools.crt"
[System.IO.File]::WriteAllText($combined, ([System.IO.File]::ReadAllText('D:\Git\mingw64\etc\ssl\certs\ca-bundle.crt')).TrimEnd() + "`r`n" + $pem)

# 3) 写进 git 全局配置
git config --global http.sslBackend openssl
git config --global http.sslCAInfo "$combined"

# 4) 验证：能列出远程分支就通了
git ls-remote --heads origin
```

**验证**：`git ls-remote --heads origin` 退出码为 0 即通（此时 TLS 与 HTTP 都正常，只剩身份认证）。

**注意事项**：

- Steam++ 根证书 **2027-05-07 到期**，续期后需重新导出并重建 bundle；
- 不用 Steam++ 时这个配置**不会**有害：bundle 里含公共 CA，直连 GitHub 也正常；
- 首次 push 会弹 GCM 授权窗口，**如果看起来"卡住不动"，先去任务栏找那个窗口**（它经常被挡住或最小化）。
