## 2. 本轮由"离线算术"得到的三条结论

### 2.1 三档口径与传感器能力的核对（【已验证】本机自检 79 项覆盖）

| 档位 | 测量口径 | fps | 抽取比 | 灰度工作尺寸 | 由哪个读出模式供像素 |
|---|---|---|---|---|---|
| 640×480 | 640×480 | 30 | 3/5 | 384×288（110592） | `640x480`（binned，1280×960 crop，206.65 fps）✅ |
| **720p60（主）** | 1280×720 | 60 | 3/8 | 480×270（129600） | ❌ **未确定**（见 §2.2） |
| **1080p45（备）** | 1920×1080 | 45 | 1/4 | 480×270（129600） | `1920x1080`（**非** binning，680,692 crop，47.57 fps）✅ |

- 三档的**抽取相位都完备**（`w % den == 0`、`h % den == 0`），**RAW10 整行都完备**（`w % 4 == 0`）。
- 三档灰度像素数都 **≤ 2¹⁷ = 131072** ⇒ `motion_quality` 片内帧缓存**都是 64 个 BRAM18**。
- 三档像素率（124.4 / 55.3 / 20.7 Mpixel/s）都 **≤ IMX219 上限 280 Mpixel/s**；
  RAW10 数据率（933 / 553 / 92 Mbps）都 **< Mizar 板 2-lane 可用 1344 Mbps**。

> 📌 **一条自我纠错**：本轮第一版自检里我写了"真机四个模式的像素率之和 < 280"，实测 **417.9 Mp/s**
> ⇒ 自检报 FAIL。**错的是那条断言**，不是数据：binned 模式下传感器是 **2×2 模拟合并读出**，
> 真正的像素率不是 `out_w×out_h×fps`（合并在电荷域做），而且四个模式本就是**互斥档位**、不该相加。
> 该断言已删除，并把这段说明留在代码里（`imx219_sccb_check.py` §4），免得下一个人再写一次。

### 2.2 【本轮最重要的发现】真机模式列表里**没有 1280×720**

| 事实 | 证据 |
|---|---|
| 真机 4 个模式：640×480 / 1640×1232 / 1920×1080 / 3280×2464 —— **没有任何一档直接输出 1280×720** | §1.2 的 `--list-cameras` 原文 |
| 而 `docs/19` §1.2 的结论是"2-lane 上**装得下** 720p60" | 那是**链路带宽**结论 |

⇒ **这是两件事**："带宽够" ≠ "传感器有这个模式"。
`docs/20` 与 `docs/24` 把 720p60 当作已落地的**主档**，其 IP 链路（`rgb2gray` 3/8、`motion_quality`）
确实已 csim+csynth+cosim 全绿 —— 但**"像素从哪来"这一环从未有过出处**。
本文件把它作为**阻塞项**显式列出（`board/imx219_driver.py` 的 `BLOCKERS`，键 `TIER_720P60_READOUT`）。

**三条可行的收口路径**（都需要人决策，属会签范畴）：

| # | 做法 | 代价 |
|---|---|---|
| ① | 查规格书 §5-2 的 mode example 表，确认有无 1280×720 的读出/裁切组合 | 最低，但本机读不到规格书 |
| ② | 改用**已核实的 `1640x1232` binned 模式**供像素，档位帧率按 **41.85** 而非 60 | **要改契约 §0**（会签）；好处是相位无风险、且有真机出处 |
| ③ | 在 PL 侧新增一档 `frame_scale`（1640×1232 → 1280×720） | `frame_scale.cpp` 现是 1280×720→640×480，比例不同，需新增一档黄金参考 |

### 2.3 Bayer 相位：把"不需要硬件的那一半"做掉了

`docs/20` §4.3 / `docs/26` §6.3 挂着"**720p Bayer 相位核实**"，标注需要 IMX219 test pattern 或上板打图。
**本文件用纯算术做掉了其中一半**：

**推导**：Bayer 相位由**全局坐标** (x,y) 的奇偶决定；读出时把裁剪窗口左上角 (x0,y0) 当作新帧的 (0,0)。
⇒ 若 x0 为奇，新帧 (0,0) 实际取到的是全局奇列，新帧的 (0,0) 变成 Gr/Gb
⇒ **整帧相位平移一格，`bayer_demosaic` 冻结的 RGGB 口径失效**。
⇒ **判据：裁剪窗口的 x0 与 y0 必须都是偶数**（与是否 binning 无关）。

**实测核对（四个模式全部通过）**：

| 模式 | crop 原点 | 是否偶数 | 结论 |
|---|---|---|---|
| 640×480（binned） | (1000, 752) | ✅ | 相位按算术可保持 |
| 1640×1232（binned） | (0, 0) | ✅ | 同上 |
| 1920×1080 | (680, 692) | ✅ | 同上 |
| 3280×2464 | (0, 0) | ✅ | 同上 |

> ⚠️ **仍然需要真机的另一半**：上表只证明"**裁剪原点**不会平移相位"。
> **binning 对相机内 Bayer 处理管线的实际影响未经真机确认**（`docs/20` §4.3 的原始疑问），
> 所以 `bayer_phase_warning()` 对两个 binned 模式**仍然给出告警文案**，而不是判为无风险。
> 真正的闭环方式不变：**上电首测用 IMX219 内置 test pattern 打竖条，抓一帧 raw 核对相位**
> （规格书 §6-1 有内置 test pattern 发生器）——**那一步本机做不了**。

## 3. 交付物与用法

### 3.1 `board/imx219_driver.py`

| 内容 | 说明 |
|---|---|
| 证据台账 | `EVIDENCE_SENSOR_MODES` / `EVIDENCE_BAYER_PHASE` / `EVIDENCE_REJECTED`，每条带 `source` 与 `status` |
| 读出模式 | `READOUT_MODES`（真机 4 行逐字落地）+ 派生属性（`crop_origin_even` / `fits_array` / `raw10_line_ok`） |
| 三档口径 | `TIERS`（与 `board/regmap.py` 的 `_TIERS` **同一组数**，由自检交叉核对） |
| 阻塞项 | `BLOCKERS`（3 条，键 `REG_TABLE` / `TIER_720P60_READOUT` / `SCCB_ADDR`） |
| SCCB 线上层 | `Imx219Sccb`（写事务 = 地址 2B + 值 1B；读事务 = 先发地址再读 1B）；`FakeSccbTransport` 供离线逐字节验证 |
| **安全阀** | `write_table()` 在**表为空**或**含未核实项**时抛 `NotProgrammableError`，**拒绝下装** |
| 覆盖度 | `verification()` 报"已核实 / 未核实 / 阻塞项 / 可否下装" |

**安全阀为什么是核心**：寄存器值写错**不报错、不崩**，只让相机不出图或出一张相位错位的马赛克，
而且**没有 csim 可以对拍**。所以本文件宁可"没有东西可写"，也不填未核实的值；
并且**空表也拒绝下装**（"一个寄存器都没写"绝不能返回成功）。

### 3.2 `board/imx219_sccb_check.py` —— 79 项离线自检

| 段 | 验什么 |
|---|---|
| 1 传感器几何 | 4 个模式的尺寸/裁剪/帧率逐字对齐；裁剪落在阵列内；相位原点偶数；**含 2 条反例自证**（挪一格必须判坏，防恒真断言） |
| 2 三档几何 | 尺寸/抽取比/相位完备/RAW10 完备/灰度尺寸/pixel/2¹⁷ 台阶/BRAM 估值/RAW10 数据率 |
| 3 与 regmap 交叉核对 | **真 import** `board/regmap.py`（每档一个子进程）逐项比对，不是抄一份 |
| 4 链路预算 | 像素率 ≤ 280 Mpixel/s；32 800×2464 非 binned 模式的像素率；1920×1080 的 47.57 fps ≥ 45；带宽占比 |
| 5 SCCB 线上层 | 从地址 0x10/0x20/0x21；地址 big-endian；写事务线上恰好 3 字节；读事务地址字节与读回长度；往返；默认值；越界拒绝；读回长度不符必须报错 |
| 6 安全阀 | 空表拒绝；含未核实项拒绝；**拒绝时一个寄存器都没写出去**；逃生门可用；形状不认识必须抛 TypeError |
| 7 证据与告警 | 台账 3 条、被否决项标 UNVERIFIED、binning 模式必须给告警、无模式触发"相位平移"硬告警 |

## 6. 顺带修掉的两个真缺陷（同一类：**崩在 PASS 之后**）

| 文件 | 现象 | 根因 | 验证 |
|---|---|---|---|
| `board/dma_test.py` | `--selftest` 打印 `RESULT: PASS` 之后**退出码仍是 1** | 收尾的 `print("\u26a0\ufe0f ...")` 在 **GBK 控制台**编不出 `⚠️` ⇒ `UnicodeEncodeError` 崩掉，**发生在 PASS 之后** | 修后 `--selftest` **exit 0**；`check_all` 该项由 FAIL 变 PASS |
| `board/hw_sw_compare.py` | 同上 | 同上 | 同上 |

- **为什么算真缺陷**：报 FAIL 而人眼看着 PASS，会让人**去查错的东西**；同时它让 `check_all` 长期带假红。
- **改法**：两处都加 `console_utf8()`（`sys.stdout/stderr.reconfigure(encoding="utf-8", errors="replace")`），
  与仓库既有做法一致（`backend/console.py`、`board/analyze_board_log.py`、`metrics/scripts/*` 都是这么做的）。
  **`errors="replace"` 的要点**：万一还有编不出的字符就显示成 `?`，**而不是让程序崩**。
- 这两项**都不是本轮引入**：`docs/26` §5 记录的"12/12 通过"是在**能显示 UTF-8 的终端**里得到的；
  本会话的 shell 是 GBK 代码页，于是它们才暴露出来。
