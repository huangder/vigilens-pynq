## 1. 1080p@60 的判定过程（不是"我觉得"，是三条硬约束）

### 1.1 证据（全部来自厂商官方文档，2026-09-29 实读）

| 来源 | 原文 / 数值 |
|---|---|
| MicroPhase《Mizar-Z7 Reference Manual》MIPI CSI 节 | "The MIPI CSI-2 bus is connected to the ZYNQ PL IOs … tested to operate at up to **672 Mbps per channel**. Up to 950 Mbps per Lane based on Zynq-7000 chip specifications." |
| Sony《IMX219PQH5-C》规格书 Features | "**Max. 30 frame/s in all-pixel scan mode**"；"Pixel rate: **280 Mpixel/s** (All-pixels mode)"；"**180 frame/s @720p with 2x2 analog (special) binning**, **60 frame/s @1080p with V-crop**"；"Data rate: Max. 755 Mbps/lane(@4lane), **912 Mbps/Lane(@2lane)**" |

15-pin 树莓派相机接口 = **2 data lane + 1 clock lane** ⇒ 可用线速按**最保守的 Mizar 实测值**取 **2 × 672 = 1344 Mbps**。

### 1.2 判定表（`link_budget.py` 的真实输出，链路效率假设 0.85）

| 组合 | 载荷 Mbps | 每 lane | 乐观占比 | **含余量** | 像素率 | 判定 |
|---|---|---|---|---|---|---|
| **1080p RAW10 @60** | 1244.2 | 622.1 | 93% | **109%** | 124.4 | ❌ **不通过** |
| 1080p RAW10 @45 | 933.1 | 466.6 | 69% | 82% | 93.3 | ✅ |
| 1080p RAW10 @30 | 622.1 | 311.0 | 46% | 54% | 62.2 | ✅ |
| **720p RAW10 @60** | 553.0 | 276.5 | 41% | **48%** | 55.3 | ✅ **选用** |
| 480p RAW10 @60 | 184.3 | 92.2 | 14% | 16% | 18.4 | ✅ |
| 640×480 RGB888 @60 | 442.4 | 221.2 | 33% | 39% | 18.4 | ✅ |

> "乐观占比"不含 CSI-2 协议开销与行/帧消隐；"含余量"按 672 × 0.85 折算。
> **那个 0.85 是【推测】的工程裕量，不是厂商给的数** —— 所以脚本把两列都打出来，
> 让判定不依赖这个假设：即使完全不扣开销，1080p@60 也已占 **93%**，没有任何余地。

### 1.3 三条独立理由，任何一条都足以否决 1080p@60

1. **带宽**：净载荷 622.1 Mbps/lane 已是 Mizar 实测上限 672 的 **93%**，加消隐/协议开销即越界。
2. **传感器模式特殊**：规格书给 60fps 的前提是 **"with V-crop"**（垂直裁切），
   而**全像素扫描模式上限是 30 frame/s**。也就是说"完整 1080p @60"这颗传感器**根本没有**。
3. **片内放不下**：若把整条流水线抬到 1080p，`motion_quality` 存"上一帧"需要
   **512 个 BRAM18 = 器件的 183%**（同一个 2 的幂台阶规律，`fpga/report/c4` 第 5 节）。

> 📌 **顺带纠正一个常见的误传**：网上说"IMX219 只有 640×480 支持 60fps"——
> 那是 **Raspberry Pi 的 libcamera 模式表**的局限，不是传感器的。规格书明确写了
> 720p 2×2 binning 可达 **180 fps**。**在 Mizar 上传感器由我们自己用 SCCB 配置，
> 不受树莓派驱动表约束** —— 但受规格书和 Mizar 链路约束。

### 1.4 为什么不是 480p@100 而是 720p@60

| 选项 | 链路占用 | 像素数 | 结论 |
|---|---|---|---|
| 640×480 RAW10 @100 | 27% | 307k | 像素最少；但 IMX219 的 480p 模式在树莓派侧是常用档，生态最稳 |
| **1280×720 RAW10 @60** | **48%** | **922k** | 🥇 **选用**：3 倍像素余量 + 满足 60fps + 链路仍宽裕 |
| 1920×1080 RAW10 @45 | 82% | 2.07M | 像素最多但只有 45fps；作为**备选档**保留（与已会签的 v1.1 口径一致，回退成本最低） |

## 2. 720p60 落地方案

### 2.1 链路

```
 Raspberry Pi Camera Module 2 (IMX219, 15-pin FPC)
        │  MIPI CSI-2, 2 lane, RAW10, 1280x720 @ 60fps   ← 链路占用 48%
        ▼
 ┌──────────────── Mizar-Z7020 · PL ────────────────┐
 │ [1] MIPI CSI-2 RX（Xilinx IP, AXI4-Stream）       │
 │ [2] raw10_unpack     5 字节 -> 4 个 10bit 像素     │  docs/19 已实现
 │ [3] bayer_demosaic   RGGB -> RGB888（1280x720）   │  docs/19 已实现
 │ [4] frame_scale      1280x720 -> 640x480          │  **本文新增**
 │        ▼                                          │
 │   既有四 IP（契约 §3，**一行不改**）                │
 │   roi_statistic → rgb2gray → motion_quality → fir │
 └───────────────────────┬──────────────────────────┘
                         │ AXI DMA / VDMA
                         ▼
                  PS：DDR3 1GB → OpenCV
```

### 2.2 `frame_scale`（新增 IP）的冻结口径

```
横向：只取 x ∈ [crop_x0, crop_x0+crop_w)，且 (x-crop_x0) % 3 < 2
纵向：只取 y，且 y % 3 < 2
参数：1280x720，crop_x0=160，crop_w=960  ->  640x480
反向映射（两条独立实现都用它复算）：out(ox,oy) <- in(crop_x0+ox+ox//2, oy+oy//2)
```

**为什么是 3:2 + 中心裁剪，而不是"横向 2:1 平均 + 纵向 2/3"**：

| 方案 | 横向比例 | 纵向比例 | 几何 | 判定 |
|---|---|---|---|---|
| 横向 2:1 平均 + 纵向 3:2 抽取 | 2:1 | 3:2 | 16:9 **被硬拉成 4:3**，纵向拉伸 **1.333×** | ❌ EAR 等比值虽仍可比，但头部姿态/几何全失真 |
| **先裁 960×720（4:3）再双轴 3:2** | **3:2** | **3:2** | **无畸变** | ✅ **选用** |

- 代价：横向只覆盖传感器 **75%** 视场（中心裁切），纵向覆盖 **100%**。
- 好处：剩下那 320 列留着，将来做"跟随人脸的 ROI 平移"时直接移动 `crop_x0`
  （云台已搁置，这是**纯软件**的替代路径）。
- ⚠️ **点采样会保留混叠**（与既有 `rgb2gray` 的 3/5 抽取同一个已知性质）。
  运动/光照统计影响不大；若实测发现对 rPPG 有影响，可改为"先 [1,2,1] 低通再抽取"
  —— **那要换黄金参考，属契约级改动**。
- 资源：本 IP **不需要任何 BRAM**（纯逐像素判定，无行缓冲/帧缓冲）。

### 2.3 三档帧率的最终分工

| 档位 | 主/备 | 传感器模式 | 缩放 | MIPI 占用 | FIR `fs` | 系数 |
|---|---|---|---|---|---|---|
| **60 fps** | 🥇 **主档** | **1280×720 RAW10** | frame_scale → 640×480 | 48% | 60 Hz | ❌ **待设计** |
| 45 fps | 🥈 备选 | 1920×1080 RAW10（官方 1080p45） | frame_scale（改 crop_w=1280、双轴 2:3 不成立 ⇒ 需另一套参数或直接 2:3 抽取） | 82% | 45 Hz | ✅ 已有 |
| 30 fps | 🥉 备选 | 1920×1080 RAW10 | 同上 | 54% | 30 Hz | ✅ 已有 |

> ⚠️ 45/30 档若用 1080p，`frame_scale` 的参数需重新推（1920×1080 → 640×480 是 3:1 与 2.25:1，
> **不是同一个比例，会失真**）。**更简单的做法**：45/30 档也用 720p（链路只要 31%/16%），
> 只是帧率降低 —— 这样三档**共用同一套缩放参数**。建议按此执行。

## 3. 视频处理链路选型：除了 OpenCV 还有什么更合理的做法

### 3.1 先实测：时间到底花在哪（本机 AMD64 真实运行）

命令与产物：

```powershell
.\.venv\Scripts\python.exe metrics\scripts\bench_video_ops.py --iters 30
# 素材：data/raw/blink.mp4 的**真实帧**（含人脸，否则 landmark 阶段会被跳过、测出偏低的假数）
```

| 环节 | 中位耗时 | 说明 |
|---|---|---|
| `cv2.cvtColor BGR→RGB` (640×480) | 0.181 ms | 契约要求 RGB 顺序，这一步**不可避免**（除非在 PL 做） |
| `cv2.cvtColor BGR→GRAY` (640×480) | 0.089 ms | 已在 PL 做 → **可省** |
| `cv2.resize 1280×720→640×480 INTER_AREA` | 0.402 ms | 本次下沉到 PL → **可省** |
| numpy 整数灰度 `(77R+150G+29B+128)>>8` | 3.606 ms | PL 的软件等价物；**比 cv2 慢 40 倍** ⇒ 别在 PS 里重现 PL 口径 |
| numpy 3:2 双轴抽取 720p→480p | 1.731 ms | 同上 |
| **Haar 级联人脸检测**（OpenCV 自带） | **19.796 ms** | 老牌基线 |
| **MediaPipe FaceMesh 478 点** | **2.811 ms** | **本项目当前实际使用的** |
| `cv2.VideoCapture` 连续 `read()` | 0.156 ms | 已打开的句柄 |

**预算占用（本机）**：固定开销合计 0.672 ms + 关键点 2.811 ms = **3.483 ms**
→ 30fps 预算的 **10.4%**、60fps 预算的 **20.9%**。

> ⚠️ **这些是 AMD64 笔记本数字，不得当作 Cortex-A9 的结论。** 但它足以做**相对**判断。

### 3.2 实测**推翻**了一个很常见的优化建议

> 常见说法："MediaPipe 太重，Cortex-A9 跑不动，应该换成更轻的检测器。"

**本机实测：Haar 级联 19.8 ms vs MediaPipe FaceMesh 2.8 ms —— MediaPipe 快 7 倍。**
所以"换成更轻的检测器"这条建议在本项目里**现阶段不成立**，不要凭印象先换掉它。

**但**：A9 是 ARMv7（只有 NEON，没有 ARMv8 的 dot-product 等指令），
MediaPipe 走 TFLite XNNPACK，**XNNPACK 在 A9 上是否启用优化路径完全未知**。
⇒ **必须在板上实测**（计划见 §4），实测前不要下"PS 跑不动"的结论。

**备选（若板上实测确实太慢）**：`cv2.FaceDetectorYN`（YuNet，OpenCV 内置，
论文标题即 *"YuNet: A Tiny Millisecond-level Face Detector"*），ONNX 模型、
可用 `cv2.dnn` 的线程数控制，是 A9 上比 MediaPipe 更可控的后备。

### 3.3 真正有效的四类手段（按性价比排序）

**① 把计算下沉到 PL —— 这是本项目最根本、也最符合赛题的做法**

- **已经下沉**：灰度 + 缩放（`rgb2gray`）、ROI 像素统计（`roi_statistic`）、
  帧间运动量（`motion_quality`）、FIR 带通（`fir_filter`），
  本次新增 **RAW10 解包（`raw10_unpack`）、去马赛克（`bayer_demosaic`）、缩放（`frame_scale`）**。
- **还可以下沉、且硬件基础已经具备的**：**光照质量评分**。
  `rgb2gray` 已经在输出 `sum_gray`（本帧灰度累加和）—— `quality.light_score` 所需的
  均值/亮度分布**已经在 PL 里算出来了**，PS 侧不必再来一次全图遍历。
- **PL 的延迟优势**：整条链路是**流式、无帧缓冲**的，延迟 ≈ 几行 + 几个流水级。
  以 640×480@60fps 算，一行时间 ≈ 16.67 ms / 480 ≈ **34.7 µs**（【算术】），
  即 PL 侧延迟在**几十微秒**量级，相对 PS 侧毫秒级计算可以忽略。**不需要为 PL 做延迟优化。**

**② 用 AMD 官方的 `Vitis Vision` 库替代自研 HLS（如果 PL 里还要做更复杂的图像处理）**

AMD 官方文档对 Vitis Vision Library 的描述原文：
*"a set of select OpenCV functions optimized for **Zynq-7000**, Zynq UltraScale+ MPSoC, Versal VEK280, Alveo U200, and U50 devices"*，
且 **L1 库可直接走 Vitis HLS 流程**（含 `Resize`、`demosaicing` 等）。

- 好处：省掉自己写 + 自己对黄金参考的工作量。
- ⚠️ 代价：**它的算法口径与你自研的不一样**，引入即等于换黄金参考 ——
  而本项目"逐点严格相等（容差 0）"的验证体系正是建立在自研口径上的。
  ⇒ **建议：只有当某个功能自研成本明显过高时才引入，并单独走一次契约变更。**

**③ PS 侧减少 OpenCV 的"隐性开销"**

- **零拷贝**：DMA 缓冲直接 `np.frombuffer(buf, ...)`，不要经过 `VideoCapture` → numpy 的拷贝。
- **不要每帧分配**：预分配输出缓冲并复用（`out=` 参数、`cv2.UMat`）。
- **不要在 PS 重现 PL 口径**：上表已证明 numpy 整数灰度比 `cv2.cvtColor` 慢 **40 倍**。
- **关键路径用 C++**：Python 的解释器 + GIL 开销在 A9 上是纯浪费；
  OpenCV 的 C++ API 可直接调。
- **降频 + 帧间跟踪**：人脸检测/关键点每 N 帧跑一次，中间用 ROI 跟踪
  （`docs/10` §5 的"追踪/锁定/测量"分时状态机就是为这个设计的）。
  ⚠️ 但注意：**眨眼与闭眼时长依赖逐帧 EAR**，关键点降频会直接损害核心指标 ——
  要按指标分别决定哪些帧必须全量算。

**④ 传感器/采集侧**

- 60fps 本身就把帧间隔从 33.3 ms 压到 **16.7 ms**，这是**最大的端到端延迟收益**。
- 光照不足时曝光时间会被拉长 → 运动模糊 + 延迟增加。**这是 60fps 也救不了的**，
  要靠补光（`quality.light_score` 已经是现成的门控信号）。
- 时间戳继续用 `frame_id / fps` 而非墙上时钟（项目已有确定性纪律，换 fps 时记得同步）。

### 3.4 明确**不要**做的（避免走弯路）

| 不要 | 原因 |
|---|---|
| **指望 DPU / Vitis AI 做神经网络加速** | **Zynq-7000 不在 Vitis AI 的官方支持范围**（社区明确："Zynq-7000 is not officially supported since version 1.4"）。XC7Z020 只有 220 个 DSP、4.9 Mb BRAM，也不是跑 DPU 的料 |
| 把带人脸的原视频上传任何云服务 | `docs/05` 隐私红线：铁律 4 |
| 把 PL 降级成纯 DMA 搬运、图像处理全交给 PS+OpenCV | `docs/01` §4.2 点名的致命短板："FPGA 不是转发器" |
| 为了"用上 OpenCV"而把已经在 PL 做对的事搬回 PS | 上表实测：numpy 整数灰度比 `cv2` 慢 40 倍，且 PL 是流式零延迟 |

### 4.3 一个必须做的**板级**验证（不要跳过）

`crop_x0` 这个参数的存在前提是"传感器的 720p 读出行/列相位与假设一致"。
上板第一件事应该是：**用 test pattern（IMX219 有内置 test pattern 发生器，规格书 §6-1）
打出竖条/斜条，抓一帧 raw，核对 Bayer 相位与读出行相位**。
这比拿真实场景调参快得多，也能一次性把"相位对不对"和"链路通不通"分开验证。

## 6. 结论标注

- 【已验证】**1080p@60 不可用**：净载荷占 Mizar 实测 lane 速率的 **93%**（含余量 109%）——
  三条独立理由（带宽 / 传感器"60fps @1080p with V-crop" + 全像素扫描上限 30fps / 片内 BRAM 183%）
- 【已验证】IMX219 规格书：720p（2×2 binning）可达 **180 fps**、全像素扫描上限 **30 fps**、
  2-lane 数据率上限 **912 Mbps/lane** —— 来源：Sony《IMX219PQH5-C》规格书（2026-09-29 实读）
- 【已验证】`frame_scale` 的算法与 Python/NumPy 黄金参考**逐位相同**（5 帧，本机真跑）
- 【已验证】本机实测：MediaPipe FaceMesh **2.811 ms/帧**，Haar 级联 **19.796 ms/帧**
  —— **推翻**"MediaPipe 太重、换轻量检测器"的直觉（见 §3.2）
- 【已验证】本机实测：numpy 整数灰度 **3.606 ms** vs `cv2.cvtColor` **0.089 ms**（慢 40 倍）
- 【算术，非实测】§2.2 的 PL 延迟量级（34.7 µs/行）
- 【推测】链路效率 0.85（协议开销与消隐的工程裕量假设）
- 【未验证】新 IP 的 csim/csynth/cosim 与全部资源/时序数字；720p 的 Bayer 相位；
  与 Xilinx RX 的握手；Cortex-A9 上的真实耗时；相机在 Mizar 上能否出图
- 【未做】60 Hz FIR 系数、BD、bitstream、上板
