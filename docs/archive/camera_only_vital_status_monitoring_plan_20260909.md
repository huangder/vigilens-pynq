# 基于摄像头的无接触状态与生命体征趋势监测系统

## 整体方案与分阶段实施计划

> 适用方向：全国大学生嵌入式/FPGA 创新设计竞赛 AMD 赛道·自主选题初级组  
> 建议项目名称：**基于摄像头与 FPGA 实时视觉处理的无接触状态监测终端**  
> 项目定位：健康趋势与疲劳风险提示原型，不是医疗诊断设备  
> 第一版目标：摄像头输入、实时指标提取、网页展示、后台综合判断、FPGA 硬件加速、完整测试与复现

---

## 1. 先把想法说清楚

你们想做的事情可以概括为：

> **只使用摄像头采集人的面部、上半身和运动信息，通过视觉算法得到眨眼、闭眼、打哈欠、头部姿态、呼吸趋势等指标，再由后台进行综合分析，通过网页展示结果；在比赛版本中，把视频预处理和部分时序计算放到 FPGA，证明硬件的实时性和低延迟优势。**

这个方向是可行的，但必须区分三件事：

1. **摄像头能直接观察到的行为指标**：眨眼、闭眼时长、打哈欠、头部转动、面部是否在画面中。
2. **摄像头可以估计但受条件影响的生理趋势**：呼吸率、心率。
3. **普通 RGB 摄像头不能可靠测量的指标**：真正意义上的血氧饱和度、血压、血糖和疾病诊断结果。

因此项目不能写成“通过眨眼频率判断一个人是否健康”，更准确的表达是：

> **通过多项视觉可观测指标评估疲劳、注意力下降和测量信号质量，并在满足条件时给出心率/呼吸率趋势估计。**

输出应该是“正常、建议休息、请重新测量、信号不可靠”等提示，而不是“你患有某种疾病”。

---

## 2. 推荐的项目主线

### 2.1 主场景

建议把场景定为：

> **面向长时间学习、驾驶模拟或实验室值守的无接触疲劳与生命体征趋势监测。**

第一版建议只选其中一个答辩场景，例如“长时间学习/值守人员状态监测”。驾驶可以作为扩展，不要同时包装成医疗、驾驶和课堂管理三个产品。

### 2.2 最终演示

被测人员坐在摄像头前，网页实时显示：

- 当前视频画面和人脸框；
- 左眼/右眼状态；
- 眨眼次数和眨眼频率；
- PERCLOS（统计窗口内闭眼时间比例）；
- 打哈欠次数或张口持续时间；
- 头部姿态和大幅运动状态；
- 当前信号质量；
- 可选心率和呼吸率趋势；
- 综合状态：正常、疲劳风险升高、测量无效或请调整姿势。

网页同时显示最近一段时间的趋势曲线和事件日志。系统不必给出“医学结论”，而是给出可解释的提示：

```text
检测到闭眼比例上升、连续打哈欠，并且信号质量良好
=> 疲劳风险升高，建议休息
```

## 3. 指标分层：哪些是主线，哪些是备选

### 3.1 第一层：必须完成的稳定指标

这些指标只使用普通摄像头，技术风险相对可控。

| 指标 | 计算方式 | 作用 | 可行性 |
|---|---|---|---|
| 眨眼次数/频率 | 根据眼睛关键点的 EAR 阈值和闭眼事件计数 | 基础行为指标 | 高 |
| 单次闭眼时长 | 从闭眼开始到睁眼的帧数换算 | 识别长时间闭眼 | 高 |
| PERCLOS | 窗口内眼睛闭合帧数/有效帧数 | 疲劳风险指标 | 高 |
| 打哈欠次数 | 嘴部纵横比 MAR 和持续时间 | 辅助疲劳指标 | 中高 |
| 头部姿态 | 人脸关键点估计 yaw/pitch/roll | 识别低头、转头和姿势异常 | 高 |
| 大幅运动/遮挡 | 人脸框位移、关键点稳定性、图像质量 | 判断数据是否可靠 | 高 |

### 3.2 第二层：建议完成的增强指标

| 指标 | 计算方式 | 作用 | 可行性 |
|---|---|---|---|
| 呼吸率趋势 | 胸部/肩部 ROI 的低频运动，或面部信号调制 | 增加生命体征维度 | 中 |
| 心率趋势 | 面部 ROI 的 rPPG：颜色均值 + 滤波 + 频谱峰值 | 增加生理信号亮点 | 中低 |
| 信号质量评分 | 光照、运动、脸部可见率、波形周期稳定性融合 | 防止乱报数值 | 中高 |

### 3.3 第三层：明确不作为 MVP 目标

- 普通 RGB 摄像头直接测量准确血氧；
- 通过眨眼判断疾病、心理状态或医学健康等级；
- 仅凭单个视频帧判断心率；
- 无控制环境下保证所有肤色、光照和运动条件下都准确；
- 依赖云端 API 的人脸或医疗模型；
- 训练大型神经网络并部署到 PYNQ-Z2。

## 4. 系统总体架构

### 4.1 推荐的比赛架构

```text
摄像头
  |
  | HDMI/MIPI/可验证的视频输入
  v
PYNQ-Z2 PL
  - 视频格式转换
  - 缩放/灰度化
  - ROI 裁剪或统计
  - 帧差/运动量计算
  - 时间窗口缓存
  - 可选信号滤波
  |
  | DDR + AXI DMA + Ethernet
  v
PYNQ-Z2 PS / 外部 PC 后台
  - 人脸/关键点检测
  - EAR/MAR/PERCLOS 计算
  - rPPG/呼吸率算法
  - 多指标融合与规则判断
  - REST API/WebSocket
  |
  v
网页前端
  - 视频画面
  - 实时数值
  - 波形和趋势
  - 状态提示
  - 事件日志和报告导出
```

### 4.2 开发阶段和比赛阶段可以不同

开发时可以先用电脑 USB 摄像头和 Python 完成算法验证；最终比赛演示必须让 PYNQ-Z2 上的自研 PL 模块承担明确功能。

建议采用两种运行模式：

**模式 A：开发/算法模式**

```text
电脑摄像头 -> Python 后台 -> 网页
```

用途是快速验证眨眼、打哈欠和 rPPG 算法。

**模式 B：比赛/硬件模式**

```text
摄像头 -> PYNQ-Z2 PL 预处理/时序计算 -> PS/后台 -> 网页
```

用途是展示 FPGA 的硬件价值和测量数据。

如果摄像头接入 PYNQ-Z2 的链路暂时不稳定，可以先使用固定视频帧序列完成 PL 验证，再把真实摄像头接入作为现场演示入口。不能让 HDMI 或 USB 驱动问题阻塞所有工作。

### 4.3 软硬件功能划分

| 功能 | 推荐归属 | 原因 |
|---|---|---|
| RGB/YUV 转换、缩放、灰度化 | PL | 每帧每像素处理，适合流水线 |
| ROI 区域平均值/统计量 | PL | 可并行累加，给 rPPG 或运动分析提供数据 |
| 帧差、运动量、图像质量初筛 | PL | 低延迟、固定时延，帮助判断信号是否有效 |
| FIR/IIR 滤波 | PL | 明确的硬件加速点，便于资源/时序对比 |
| FFT 或频率峰值分析 | PL/IP 或 PS | 第一版可调用 FFT IP，后期再优化关键部分 |
| 人脸/关键点模型 | PS/外部 PC | 模型和内存压力较大，初级组不宜硬塞进 Zynq-7000 |
| EAR、MAR、PERCLOS | PS | 关键点得到后计算量小、逻辑易迭代 |
| 多指标融合和告警规则 | PS | 需要配置和解释，便于网页调整 |
| 网页、日志和报告 | 外部 PC 或 PS | 方便开发和演示 |

FPGA 不能只负责把摄像头数据转发到电脑。至少要有两个自研硬件模块，例如：

1. `roi_statistic`：对指定面部/胸部区域做像素统计；
2. `motion_quality`：计算帧间变化量并生成运动质量分数；
3. `fir_filter`：对时间序列做带通/低通滤波；
4. `peak_estimator`：完成周期峰值候选检测。

### 4.4 “各个方向”怎么落地

“获取人的各个方向数据”可以理解为多视角观察，但不建议第一版就做四面摄像头。多路视频会同时增加同步、带宽、遮挡、标定和网页布局的复杂度。

建议分三阶段：

| 阶段 | 摄像头数量 | 用途 | 是否进入比赛 MVP |
|---|---:|---|---|
| 第一阶段 | 1 个正面摄像头 | 眨眼、嘴部、头姿、面部 ROI | 是 |
| 第二阶段 | 2 个，正面 + 侧面 | 正面遮挡时补充姿态/上半身运动 | 可选 |
| 第三阶段 | 3 个或更多 | 多方向覆盖、遮挡分析、跨视角融合 | 不建议作为初期目标 |

多视角版本的融合逻辑应是“质量加权”，而不是简单拼接画面：

```text
正面视角 -> 人脸关键点、眨眼、嘴部
侧面视角 -> 头部转动、胸部起伏、姿态
          -> 各自计算信号质量
          -> 选择/加权可信视角
          -> 后台生成统一指标
```

如果使用两个摄像头，必须记录：

- 摄像头编号和安装角度；
- 时间戳或同步方式；
- 两路帧率和分辨率；
- 视角切换条件；
- 某一路失效时的降级行为。

比赛答辩时可以把双视角说成扩展能力，但第一版只要一台摄像头完成稳定闭环即可。

## 5. 前端网页方案

### 5.1 推荐技术栈

为了降低大二团队的开发量，建议：

- 后端：Python FastAPI；
- 实时通信：WebSocket；
- 前端：原生 HTML/CSS/JavaScript，或已有 React 经验时使用 React；
- 曲线：轻量 Chart.js 或 ECharts；
- 视频：开发期使用浏览器 `getUserMedia`，比赛硬件模式使用后台转发的视频帧或 HDMI 输出；
- 数据格式：JSON，时间序列日志保存为 CSV。

### 5.2 页面布局

```text
+----------------------------------------------------------+
| 无接触状态监测终端        连接状态 | 设备状态 | 测量时间 |
+----------------------+----------------------+------------+
|                      | 当前指标             |            |
|   实时视频画面       | 眨眼频率             |            |
|   人脸框/关键点       | PERCLOS              |            |
|   ROI/姿态提示        | 打哈欠次数           |            |
|                      | 心率/呼吸率趋势(可选) |            |
+----------------------+----------------------+------------+
| 信号质量：良好/较差  | 综合状态：正常/建议休息/无效 |
+----------------------------------------------------------+
| 时间趋势曲线：眨眼 | PERCLOS | 心率 | 呼吸率 | 运动量      |
+----------------------------------------------------------+
| 事件日志：时间、事件、指标、建议、置信度                |
+----------------------------------------------------------+
```

### 5.3 页面必须有的状态

- `正常`：指标在当前测试规则范围内，信号质量良好；
- `疲劳风险升高`：PERCLOS、长闭眼和打哈欠等组合条件触发；
- `请调整姿势`：脸部出框、过度转头或遮挡；
- `信号不可靠`：光照过暗、运动过大或 rPPG 周期不稳定；
- `连接中断`：摄像头、FPGA 或后台连接异常；
- `测量完成`：一个时间窗口已完成，显示汇总结果。

网页上不要只显示一个没有解释的“健康分数”。每个建议都应能追溯到输入指标。

## 6. 后台处理方案

### 6.1 后台数据流

```text
视频帧
  -> 图像质量检查
  -> 人脸/人体 ROI
  -> 关键点与像素统计
  -> 时间序列缓存
  -> 指标计算
  -> 置信度评估
  -> 多指标规则融合
  -> 建议和事件
  -> WebSocket 推送
```

### 6.2 模块划分

```text
backend/
├── capture.py              # 摄像头或视频源
├── face_landmark.py        # 人脸框和关键点
├── behavior_metrics.py     # EAR、MAR、PERCLOS、头姿
├── rppg.py                 # 可选心率/呼吸率
├── quality.py              # 光照、运动、遮挡和波形质量
├── decision.py             # 规则融合和建议
├── fpga_client.py          # Overlay、DMA、寄存器访问
├── api.py                  # FastAPI REST 接口
├── websocket.py            # 实时推送
└── storage.py              # CSV/SQLite 日志
```

### 6.3 眨眼指标

使用人脸关键点计算眼睛纵横比 EAR：

```text
EAR = (两组垂直距离之和) / (2 × 水平距离)
```

不要用单个固定帧阈值直接决定“健康/不健康”，应采用状态机：

```text
OPEN -> CLOSING -> CLOSED -> OPEN
```

需要设置：

- 闭眼阈值；
- 连续闭眼最短帧数；
- 去抖时间；
- 统计窗口，例如 30 秒；
- 有效帧比例。

输出：

- 每分钟眨眼次数；
- 平均闭眼时长；
- 最大闭眼时长；
- PERCLOS；
- 长闭眼事件数。

### 6.4 打哈欠指标

通过嘴部纵横比 MAR 和持续时间判断张口事件。要过滤说话、咳嗽和大幅转头造成的误判，可增加：

- 最小持续时长；
- 嘴部区域稳定性；
- 头部姿态约束；
- 与连续眨眼/闭眼指标的联合判断。

### 6.5 心率 rPPG 可选方案

流程为：

```text
面部 ROI
  -> 每帧 RGB 平均值
  -> 去直流/归一化
  -> 0.7-3.5 Hz 带通滤波
  -> 频谱或自相关
  -> 主频 -> BPM
```

必须配套信号质量判断：

- 人脸是否连续可见；
- ROI 是否发生大幅移动；
- 光照是否过暗或饱和；
- 主频峰值是否明显；
- 连续窗口的 BPM 是否跳变过大。

输出形式建议为：

```text
心率趋势：72 BPM
置信度：0.78
状态：实验条件下可用
```

而不是：

```text
心率：72 BPM，健康正常
```

### 6.6 呼吸率可选方案

优先使用上半身 ROI 的低频运动或亮度变化：

```text
胸部/肩部 ROI
  -> 帧间位移或平均亮度
  -> 0.1-0.5 Hz 低通/带通
  -> 周期检测
  -> 呼吸次数/分钟
```

如果摄像头只拍到脸部，呼吸率估计的可靠性下降，应标记为拓展功能，不要作为 MVP 的唯一指标。

## 7. 综合判断逻辑

### 7.1 第一版使用可解释规则，不急着训练 AI

建议先使用规则和加权评分，把结果做稳定：

```text
if face_visible_ratio < 0.7:
    status = "请调整姿势"
elif signal_quality < threshold:
    status = "信号不可靠"
elif perclos > PERCLOS_LIMIT and yawn_count >= YAWN_LIMIT:
    status = "疲劳风险升高"
elif long_close_count >= CLOSE_LIMIT:
    status = "需要休息"
else:
    status = "正常"
```

阈值必须写入配置文件，而不是散落在代码里：

```yaml
window_seconds: 30
ear_close_threshold: 0.21
min_close_frames: 3
perclos_warning: 0.25
yawn_min_duration_ms: 800
quality_min_score: 0.60
```

### 7.2 AI 的合理位置

AI 可以分三阶段加入：

**阶段 1：开发助手**

- 解释算法和接口；
- 生成测试脚本和网页骨架；
- 分析日志和 Vivado 报告；
- 帮助整理复现文档。

**阶段 2：轻量信号质量模型**

输入特征可以是：

- 人脸可见率；
- 光照均值和饱和比例；
- ROI 位移；
- rPPG 主峰突出度；
- 波形周期稳定性；
- EAR/MAR 数据完整率。

输出只做：`可靠`、`需调整`、`无效`。这比直接训练一个“健康诊断模型”更容易解释。

**阶段 3：多指标状态分类**

如果数据量足够，可用决策树、逻辑回归或小型 MLP 判断“正常/疲劳风险升高/数据无效”。必须与规则基线比较，不能只报 AI 模型的准确率。

### 7.3 AI 使用边界

- AI 生成的代码必须经过你们自己的仿真、综合和板级测试；
- AI 不能替代医学结论和数据标注；
- 报告中记录使用了什么模型、提示词、修改过程和验证结果；
- 所有指标数字必须来自真实测试，不允许让 AI 编造；
- 不上传可识别个人身份的原始视频到不必要的外部服务。

## 8. 创新点设计

建议把创新点收敛为下面四个，答辩时不要平均用力。

### 创新点 1：多指标而不是单一眨眼频率

把眨眼频率、PERCLOS、打哈欠、头部姿态和信号质量结合起来，避免“眨眼多就不健康”的片面判断。

### 创新点 2：运动和测量质量联合判断

系统先判断“数据是否可信”，再决定是否给出心率/呼吸趋势。这是 rPPG 方案的关键工程价值。

### 创新点 3：FPGA 负责确定性视觉/时序处理

让 PL 完成 ROI 统计、运动量、滤波或时间窗口处理，用实测数据证明：

- 处理延迟更低或抖动更小；
- CPU 占用降低；
- 连续输入时吞吐更稳定；
- 资源占用在可接受范围。

### 创新点 4：可解释的健康趋势报告

后台输出“触发了哪些指标、数据是否可信、建议是什么”，而不是只给一个黑盒分数。

## 9. 逐步实施步骤

### 第 0 步：冻结项目定义（半天）

完成以下决定：

1. 主场景只选“学习/值守疲劳监测”或“驾驶模拟疲劳监测”之一；
2. MVP 指标定为眨眼、PERCLOS、打哈欠、头姿和运动质量；
3. 心率、呼吸率标为增强项；
4. 不把血氧写进 MVP 承诺；
5. 确认摄像头、PYNQ-Z2、电脑和显示设备；
6. 分配 PL、PS/后端、前端、测试/文档职责。

**产出：** `docs/project_charter.md`。  
**通过标准：** 每个成员能用一句话说清项目输入、核心输出和 FPGA 作用。

### 第 1 步：做设备和数据可行性检查（第 1 天）

1. 确认摄像头可以稳定输出至少 15-30 fps；
2. 记录分辨率、色彩格式和连接方式；
3. 检查 PYNQ-Z2 能否启动、联网、访问 Jupyter；
4. 确认开发电脑可以运行 Python、OpenCV 和关键点模型；
5. 录制 3 段短视频：静止、眨眼/打哈欠、转头/遮挡。

**产出：** `data/raw/`、设备清单和环境截图。  
**通过标准：** 视频可回放，脸部清晰，数据能被 Python 逐帧读取。

### 第 2 步：先做纯软件 MVP（第 2-5 天）

1. 摄像头读取和人脸检测；
2. 人脸关键点或眼嘴关键点提取；
3. 实现 EAR、MAR、头姿和人脸可见率；
4. 实现眨眼状态机和 PERCLOS；
5. 实现打哈欠事件检测；
6. 输出 JSON 和 CSV；
7. 用回放视频重复测试，固定黄金结果。

**产出：** `backend/behavior_metrics.py`、`data/golden/`、`metrics/software_baseline.csv`。  
**通过标准：** 同一视频重复运行结果一致，能正确统计至少一段眨眼和打哈欠视频。

### 第 3 步：先做网页骨架（第 1 周）

1. 建立 FastAPI 服务；
2. 增加 `/api/status`、`/api/metrics`、`/api/events` 接口；
3. 用假数据驱动前端曲线；
4. 加入 WebSocket 实时推送；
5. 显示视频占位区、指标卡、趋势图和事件日志；
6. 增加连接中断、数据无效和加载状态。

**产出：** `frontend/`、`backend/api.py`、网页截图。  
**通过标准：** 浏览器能连续显示每秒更新的数据，断开后台时有明确提示。

### 第 4 步：接入真实后台和网页（第 2 周）

1. 将软件指标接入 WebSocket；
2. 显示实时人脸框和关键点；
3. 显示眨眼频率、PERCLOS、打哈欠和头姿；
4. 加入规则判断和文字建议；
5. 记录事件时间、触发指标和置信度。

**产出：** 第一版可用网页和 3 段演示录像。  
**通过标准：** 从摄像头到网页端到端运行 10 分钟，不崩溃，数据与离线脚本一致。

### 第 5 步：定义 FPGA 第一个核心模块（第 2 周）

推荐从 `roi_statistic` 或 `motion_quality` 开始，不要一开始做完整人脸识别。

**方案 A：ROI 统计模块**

- 输入：像素流、ROI 坐标；
- 输出：ROI 内 RGB 累加值、像素计数、均值；
- 用途：为 rPPG 和图像质量评估提供时间序列。

**方案 B：运动质量模块**

- 输入：当前帧和上一帧的灰度像素；
- 输出：帧差总量、运动比例或二值运动掩码；
- 用途：检测大幅运动并屏蔽不可靠测量。

**产出：** 接口文档、HLS 顶层函数、C 仿真测试向量。  
**通过标准：** 边界、全零、全满、单点变化和随机输入都与软件参考一致。

### 第 6 步：完成 HLS C 仿真和综合（第 3 周）

1. 明确 AXI-Stream 数据结构、`TLAST` 和控制寄存器；
2. 编写 C++ 参考模型；
3. 编写 testbench；
4. 运行 C simulation；
5. 运行 C synthesis；
6. 记录 II、LUT、FF、BRAM、DSP、时钟和 WNS；
7. 用 AI 分析报告，但由你们确认每个修改。

**产出：** `fpga/src/`、`fpga/sim/`、`fpga/report/`。  
**通过标准：** 仿真结果与黄金参考一致，综合无 ERROR，目标时钟下时序可收敛。

### 第 7 步：封装 Overlay 并从 Python 调用（第 4 周）

1. 创建 Block Design；
2. 接入 Zynq PS、AXI DMA、AXI-Stream 自研 IP；
3. 生成 bitstream 和 hwh；
4. 在 PYNQ 上加载 Overlay；
5. 测试寄存器读写和 DMA；
6. 验证缓存 flush/invalidate；
7. 对 100-1000 个测试窗口进行回归。

**产出：** `.bit`、`.hwh`、`fpga_client.py`、DMA 日志。  
**通过标准：** Python 输入和 PL 输出稳定一致，无死锁和随机错误。

### 第 8 步：把 FPGA 结果接入后台（第 5 周）

1. 后台增加 FPGA 客户端；
2. 将 ROI 统计或运动质量结果作为后端输入；
3. 与软件计算结果逐窗口比对；
4. 在网页显示“硬件模式/软件模式”；
5. 记录 PL 计算耗时、DMA 耗时和端到端耗时。

**产出：** 硬件模式网页、软硬件一致性报告。  
**通过标准：** 同一视频下，硬件模式和软件模式的主要指标差异在预设容差内。

### 第 9 步：加入心率/呼吸率增强项（第 5-6 周）

只有当前面主线稳定后才做。

1. 先用 Python 记录面部 ROI 颜色序列；
2. 画出原始波形和滤波波形；
3. 在安静、光照稳定条件下验证 rPPG 心率；
4. 使用公开参考设备或人工计数进行对照；
5. 加入信号质量门控；
6. 只有在置信度足够时显示心率/呼吸率；
7. 运动、遮挡或光照异常时显示“暂不可用”。

**产出：** `backend/rppg.py`、`metrics/rppg_test.csv`、误差和失效条件说明。  
**通过标准：** 在受控场景下能稳定输出趋势；在不受控场景下能正确拒绝不可靠结果。

### 第 10 步：做一次可解释的优化（第 6-7 周）

三选一：

- FPGA ROI 统计替代 PS 逐像素扫描；
- FPGA 帧差/运动质量替代 Python 图像差分；
- FPGA 滤波替代 PS 时间序列滤波。

需要对比：

- 纯软件耗时；
- PL 计算耗时；
- DMA 和总耗时；
- CPU 占用；
- P50/P95/P99 延迟；
- LUT、FF、BRAM、DSP 和 WNS。

**通过标准：** 有优化前后对比表，测试条件、输入和版本完全一致。

### 第 11 步：稳定性和场景测试（第 7 周）

至少测试以下条件：

1. 正面静止；
2. 正常眨眼；
3. 连续打哈欠；
4. 低头和转头；
5. 戴眼镜或短暂遮挡；
6. 光照变暗；
7. 多人进入画面；
8. 摄像头断开或网络中断；
9. FPGA/后台重启后恢复。

**通过标准：** 每种情况都有预先定义的期望状态，系统不会在无效数据下给出确定性健康结论。

### 第 12 步：冻结 MVP 和准备参赛材料（第 8 周）

1. 冻结可演示版本；
2. 在干净环境重装并运行；
3. 生成 bitstream、hwh、脚本和配置文件；
4. 导出原始日志、CSV、资源和时序报告；

## 11. 测试指标与成功标准

### 11.1 行为指标

| 指标 | 建议测试 |
|---|---|
| 眨眼事件 F1 | 与人工标注的视频对比 |
| PERCLOS 误差 | 不同时间窗口和不同被测者 |
| 打哈欠事件召回率 | 正常张口、说话、打哈欠混合测试 |
| 人脸可见率 | 正面、转头、遮挡、出框 |
| 状态判断一致率 | 同一视频重复运行 |

### 11.2 rPPG 指标

| 指标 | 建议测试 |
|---|---|
| 心率 MAE/RMSE | 与指夹式设备作参考 |
| 呼吸率误差 | 与人工计数或参考传感器对比 |
| 有效输出比例 | 统计哪些窗口被质量门控拒绝 |
| 光照/运动下失效率 | 明确系统边界 |

### 11.3 FPGA 和系统指标

- PL 计算延迟；
- DMA 传输延迟；
- 端到端 P50/P95/P99/最大延迟；
- 持续处理帧率或窗口吞吐率；
- CPU 占用率；
- LUT、FF、BRAM、DSP；
- 时钟频率、WNS、TNS；
- 连续运行时间、错误次数和恢复时间。

### 11.4 建议的“完成率”定义

不要用“看起来能工作”作为成功标准。建议定义：

```text
MVP 工程完成：第一层指标全部通过，真实板卡运行，网页和后台闭环
增强功能完成：心率或呼吸率在受控条件下通过测试，并能识别无效场景
参赛版本完成：有 FPGA 资源/时序/性能对比，有可复现仓库和演示备份
```

## 14. 风险和降级方案

| 风险 | 可能后果 | 降级方案 |
|---|---|---|
| 摄像头接入 FPGA 不稳定 | 无法实时取帧 | 用固定视频序列验证 PL，真实摄像头走开发模式 |
| 人脸关键点受光照影响 | 眨眼误检 | 加图像质量门控，限定演示光照，保存失败案例 |
| rPPG 心率跳变 | 影响可信度 | 只显示趋势和置信度，运动/光照异常时拒绝输出 |
| 呼吸率不稳定 | 指标不可靠 | 改为扩展项，不影响行为指标 MVP |
| PYNQ-Z2 性能不足 | 网页或模型卡顿 | 模型在外部电脑运行，FPGA 保留真实预处理/滤波任务 |
| DMA 缓存错误 | 输出随机错误 | 固定缓冲区、降低分辨率、先做短数组和回环测试 |
| AI 生成代码不可用 | 调试时间失控 | 回退到最小人工实现，AI 只辅助解释和测试 |
| 医疗表述过度 | 答辩和合规风险 | 统一使用“趋势监测、辅助提示、实验室原型” |

## 17. 最终答辩时应该怎么讲

### 一句话

> 我们做的是一个基于摄像头的无接触状态监测原型。系统先判断视频和生理信号是否可信，再结合眨眼、闭眼比例、打哈欠、头部姿态和可选心率/呼吸趋势给出可解释的疲劳风险提示；FPGA 负责实时视频预处理、运动质量和时序信号处理，ARM/后台负责关键点分析、网页和上层决策。

### 三个必须展示的对比

1. 纯软件 vs FPGA：延迟、CPU 占用、吞吐和抖动；
2. 单一眨眼指标 vs 多指标融合：误报和漏报变化；
3. 正常测量 vs 光照/运动异常：系统能否识别并拒绝不可靠结果。

### 医疗表述边界

建议使用：

- 健康趋势监测；
- 疲劳风险提示；
- 非接触测量原型；
- 辅助筛查；
- 实验室条件下的心率/呼吸估计。

避免使用：

- 医疗诊断；
- 疾病识别；
- 医疗级准确率；
- 精确血氧测量；
- 仅靠眨眼判断健康状况。

## 18. 最终建议

你们的想法可以做，但建议按下面的优先级执行：

```text
第一优先：眨眼 + PERCLOS + 打哈欠 + 头姿 + 运动质量
第二优先：网页、后台、日志和可解释建议
第三优先：FPGA ROI 统计/运动质量/滤波硬件加速
第四优先：受控条件下的 rPPG 心率趋势
第五优先：呼吸率和轻量 AI 信号质量分类
```

**项目成功的最低条件**不是“把所有生命体征都测出来”，而是：

> 摄像头输入真实可用，核心行为指标稳定，后台判断可解释，网页完整，FPGA 有自研核心并且有实测对比，所有结果能复现。

只要第一层主线完成，心率做不稳定也不会导致项目失败；如果 rPPG 做出来，再把它作为有条件的增强功能，项目的创新性和展示效果会明显提高。
