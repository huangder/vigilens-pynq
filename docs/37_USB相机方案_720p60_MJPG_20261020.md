## 1. 一页结论（TL;DR）

| 问题 | 结论 |
|---|---|
| 为什么放弃 MIPI/IMX219？ | 板侧电气与总线全部正常、模组在树莓派上验证可用、**但相机 7bit 地址 `0x10` 连地址应答都没有**；`STEP_RISE` 总线负载测量显示**插拔排线时 SCL/SDA 的上升时间一拍未变** ⇒ 模组对这两根线没有任何电气负载 ⇒ 断点在**连接器/串阻/排线**这一级，不在软件。见 §2 |
| 换成什么？ | **USB UVC 免驱相机**，输出 **1280×720 @ 60 fps MJPG** |
| 60 fps 换来什么？ | ① 与 `docs/interface.md` **v1.5 主档（720p60）完全对齐**；② rPPG 每秒 60 个采样点，峰值定位更准；③ 眨眼/闭眼时长的帧分辨率翻倍（3 帧=50 ms 而不是 100 ms） |
| 60 fps 要付什么？ | **三笔硬账**：① `fir_filter` 必须按 60 Hz 重设计（契约 §3.5 变更）；② PS 解 MJPEG 的预算砍半到 **16.7 ms/帧**，**单核基本不可能**；③ 一堆"按帧计数"的阈值时间含义全部减半 |
| 最大技术风险 | **PS 侧 MJPEG 解码**（A9 @667 MHz 无 JPEG 硬解）：单核 20~37 ms/帧 > 16.7 ms 预算。**已定对策 = 双核帧级并行 + ROI-only 解码**（双核裸解仍卡在临界线，约 40~55 fps）；兜底 = 降 480p60 或如实上报实际帧率 |
| 最大流程风险 | 契约 **§0 + §3.5 一起改**，`face.bbox` 数值空间也变——三处不同步就是"两边各自合法、拼起来非法" |
| 最容易被忽略的风险 | 若实际只跑到 25 fps 却按 60 fps 换算时间轴，**心率会系统性偏移**（见 §8 R14） |
| 不做什么 | 不再调 MIPI、不上 HDMI、不做 1080p、不做 PL 侧 JPEG 硬解 |

## 2. 为什么换：MIPI 路线的证据链与终止判据

### 2.1 已经排除的（都是**真机实测**，不是推断）

| 环节 | 证据 | 出处 |
|---|---|---|
| 板卡上电 / JTAG | `TARGETS=.../Digilent/210241631901`，`DEVICES=<arm_dap_0 xc7z020_1>` | 本轮日志 |
| SCCB 主机与总线 | 板载 EEPROM(U18) 在 `0xA0/0xB0` 稳定 ACK | `docs/34` §13.1 |
| 相机 MCLK | 新位流下**在 pad 上量到 25.00 MHz**（`mclk_period=8192`）；改为常低/高阻时 `mclk_seen=0` ⇒ 这个数字是真波形，不是自证 | `docs/34`、本轮 `STEP_RISE` 位流 |
| 供电 | J11 `pin15` 对 GND = **3.3 V**；`pin11` 对 GND = **3V3**（`R33` 补焊后） | 用户万用表实测 |
| 模组 | 同一模组**在树莓派上刚跑过、能出图**；同一根 15-pin 排线 | 用户实测 |
| 串阻 | `R31`/`R32` 实测 0 Ω 在板 | 用户实测 |
| 扫描覆盖面 | 256 个 8-bit 写地址全扫，命中恒为 `{0xA0, 0xB0}` | `docs/31`、`docs/34` |

### 2.2 决定性的一条：`STEP_RISE` 总线负载测量【已验证】

原理：把 SCL/SDA 同时按住 10 µs，释放后在 20 µs 窗口里数"还有多少拍被采成低"（1 拍 = 20 ns）。

| 状态 | `rise_scl` / `rise_sda` |
|---|---|
| 排线**拔下** | 6 / 6 |
| 排线**插回**（两次独立抓取） | 6 / 6 |
| 重插一次后再抓 | 6 / 6 |

**四次抓取逐字节相同。** 结论：
- 排线本身的分布电容会让上升变慢（读数升高）——没出现；
- 模组自带上拉会让上升变快（读数降低）——也没出现；
- ⇒ **模组对 SCL/SDA 的电气贡献 < 5 pF**，等于"这两根线走到连接器就断了/没接触"；
- 坏器件也会加电容，所以**这组数据不支持"模组坏了"**，而是支持"没接通"。

### 2.3 终止判据（满足任一即停）

1. 连续 **3 轮**不同配置（pin11 高/低、pin12 驱动/常低/高阻、SCL 100 kHz/25 kHz、PWRUP 200 ms/1 s）均为 `CAMERA_NOT_ACK`；
2. `STEP_RISE` 在插/拔之间**无差异**；
3. 修复连接器需要动 BGA/换板级器件（超出本队工艺能力）。

**当前三条全部满足 ⇒ MIPI 主路径终止，转 USB。** 但 `board/cam_detect/`、`docs/31~36` **全部保留**（回退与答辩证据）。

## 3. 相机采购/验收规格

| 项 | 要求 | 理由 |
|---|---|---|
| 接口 | **USB 2.0 High Speed，UVC 免驱** | Linux 直接 `/dev/video*`，无厂商 SDK |
| 传感器 | 1/3" 级（≈4.8×3.6 mm），像素 ≤4 µm | 720p 需要 1 MP；3.75 µm 是常见档 |
| **分辨率/帧率** | **1280×720 @ 60 fps MJPG（硬性）** | 本方案的测量口径 |
| YUY2 @720p | 只作参考（多数模组 10 fps） | ⇒ **没有无压缩通路**，60 fps 只能走 MJPG 解码 |
| 镜头 | **3.9 mm / 无畸变（TV ≤2%）/ F2.0 / IR-cut / M12** | 见 §3.1 |
| 曝光控制 | **`exposure_time_absolute` 可手动锁定** | rPPG 第一杀手是自动曝光；60 fps 下曝光更短，锁不住就废 |
| 白平衡 / 增益 | `white_balance_temperature`、`gain` 可手动 | 同上 |
| 防闪烁 | 50/60 Hz 可选，**设 50 Hz** | 中国电网 50 Hz，与 60 fps 形成 **10 Hz 拍频** |
| 对焦 | 定焦或手动锁定 | 自动对焦拉风箱 = 全画面亮度波动 |
| 功耗 | ≤ 500 mA @5 V（标称 120 mA 最好） | USB Host 端口上限 |
| 线缆 | ≤1.5 m，**直连、不经 HUB** | 60 fps 更吃等时传输余量 |

### 3.1 镜头几何核算（1/3"、3.75 µm、720p 有效区 4.8×2.7 mm）

- 像素焦距 `f_px = 3.9 mm / 3.75 µm = 1040 px`
- 16:9 视场：水平 **63.2°**、垂直 **38.2°**、对角 **70.5°**
- 60 cm 处画面 **738 × 415 mm**；人脸 15 cm 宽 ≈ **260 px**（720p），降采样到 480×270 后 **≈97 px**
- 50 cm 处：脸 312 px；70 cm 处：223 px
- ⇒ **工作距离定 50~65 cm**。>70 cm 时 PL 侧 ROI 掉到 84 px，`motion_quality`/`roi_statistic` 的统计会变噪

> ⚠️ 卖家标的"75°"通常是**按 1/3" 4:3 全幅的对角**（`2·atan(3.0/3.9)=75.2°`）。下单前问清三句：
> **①对角还是水平 ②按 1/3" 还是 1/4" 标 ③TV 畸变具体 % 与测试靶面**。

## 4. 目标架构

### 4.1 现状（MIPI 路线，走不通）

```
IMX219(模块) ─MIPI CSI─▶ [空] ─▶ PL ─▶ DMA ─▶ PS
                            ▲
                       这一级从未实现（MIPI RX 没写）
```

### 4.2 目标（USB 路线）

```
UVC 相机 ──USB2.0 HS 720p60 MJPG──▶ PS: uvcvideo ──▶ V4L2 帧
                                                        │ libjpeg-turbo (NEON) ×2 核
                                                        ▼
                                                   Y 平面 (1280×720 灰度)
                                               ┌────────┴─────────┐
                                               ▼                  ▼
                                    PS 侧：人脸/关键点      PL 侧：rgb2gray 3/8
                                    (必须 ≥30 fps)         → 480×270
                                               │                  │
                                               │            roi_statistic /
                                               │            motion_quality
                                               ▼                  ▼
                                         behavior/quality ──▶ 指标融合（A 线）
                                                                  │
                                                            fir_filter @60 Hz
```

**两条硬约束**：

1. **像素只到 PS，到不了 PL 的输入端**——`docs/10` 与 `docs/19` 都记过这条架构代价。
   PL 的价值必须靠"拿到帧之后的确定性预处理 + 低抖动"重新论证。
2. **灰度进 PL**：720p60 若送 RGB888 是 `1280×720×3×60 = 165.9 MB/s`；送灰度只需 **55.3 MB/s**。

### 4.2.1 两条由压力分析逼出来的修正（2026-10-21）

**(a) 人脸关键点必须 ≥30 fps，不能降到 5~10 fps。**
眨眼持续 100~400 ms、`min_close_frames=3`；在 10 fps 下 3 帧 = 300 ms，**眨眼会被整段漏掉**，
`blink_count` / `perclos` 直接失真。而这两个指标是本项目的核心（疲劳趋势），比 rPPG 更硬。
⇒ 正确做法：**PL 把 480×270 灰度回写到 DDR**（VDMA S2MM，60 fps 仅 **7.8 MB/s**），
PS 在这个小图上跑关键点（关键点成本随像素数下降，480×270 比 720p 便宜约 7 倍），
**30 fps 可保**。rPPG 的 ROI 均值另走一条：双核 ROI-only 解码出的全分辨率行带。

**(b) RGB→灰度放 PL，PS 不做 `cvtColor`。**
两核已经被解码吃掉，PS 侧每帧 2~3 ms 的 `cvtColor` 正好是省不出来的余量。
代价是 VDMA 写侧 165.9 MB/s（DDR3 可承受），换来 CPU 留给关键点与管线。见 R7 / R17。

> ⚠️ 这两条把 §4.2 的原始简图从"一条单向通路"改成了"**PS↔PL 双向**"：
> 写（RGB888，165.9 MB/s）+ 读回（灰度 480×270，7.8 MB/s）。VDMA 需要两个通道，W6 的验收要相应加一项。

### 4.3 与现有 PL 档位的关系（本次口径**正好落在 v1.5 主档上**）

| 项 | 值 | 依据 |
|---|---|---|
| 测量口径 | 1280 × 720 **@ 60 fps** | v1.5 草案**主档**原值 |
| 灰度工作尺寸 | **480 × 270**（抽取 3/8） | 1280/8×3、720/8×3 |
| 片内像素数 | **129,600 ≤ 2¹⁷** | ⇒ `motion_quality` 仍是 **64 个 BRAM18**，§3.3 结构不变 |
| 链路余量 | 48% | v1.5 草案实测 |

⇒ **几何与帧率都与 v1.5 主档一致**，不需要新造档位；`config.yaml` 里 `tier_720p60_*` 三键（`width/height/fps`）**已经是 1280/720/60**，可直接用。
代价是 **§3.5 的 `fir_filter` 必须跟着从 30 Hz 走 60 Hz**（见 §6.2）。

## 6. 数据与性能预算

### 6.1 链路预算

| 项 | 计算 | 结果 | 判定 |
|---|---|---|---|
| MJPG 码率（720p60） | 0.92 MPix × 0.5~1.5 bit/px × 60 | **3.4~10.4 MB/s** | 占 USB2 HS 实用带宽（≈19 MB/s）**18~55%** ⚠️ 仍可行但不再宽松 |
| 单帧 MJPG 长度 | 同上 /60 | 58~173 KB | — |
| 解码算力【推测】 | A9 667 MHz + libjpeg-turbo NEON，25~45 MPix/s | **20~37 ms/帧** | 60 fps 预算 **16.7 ms** ⇒ **单核必然不够** ❌ |
| 双核帧级并行【推测】 | 2 × 单帧 | 10~19 ms/帧 | **仍卡在临界线上** ⚠️ |
| **双核 + ROI-only 解码【推测】** | 只解人脸所在 MCU 行（`jpeg_skip_scanlines`），按面积省 40~60% | **6~11 ms/帧** | ✅ **本方案采用**；但两核都被占满 |
| 降 480p60 对照【推测】 | 0.31 MPix | ~7~12 ms/帧 | ✅ 兜底方案 |
| PS→PL 带宽（RGB888） | 1280×720×3×60 | **165.9 MB/s** | ⚠️ 很占带宽，但**本方案选它**：省下 PS 的 `cvtColor`（见 R17） |
| PS→PL 带宽（灰度） | 1280×720×60 | **55.3 MB/s** | 仅当 PS 已产出灰度时用（不推荐：多花 2~3 ms/帧 CPU） |
| PL 片内像素 | 480×270 | 129,600 ≤ 2¹⁷ | **64 BRAM18**，与 v1.5 一致 ✅ |

### 6.2 FIR @60 Hz：我实跑过的设计数据【已验证】

命令（`--d 0.0` 是冻结口径，**不能省**，脚本默认会自动搜 `d` 从而悄悄改掉口径）：

```bash
python fpga/sim/design_fir_coeffs.py --fs 60 --taps 63  --d 0.0 --no-write
python fpga/sim/design_fir_coeffs.py --fs 60 --taps 127 --d 0.0 --no-write
python fpga/sim/design_fir_coeffs.py --d 0.0 --no-write          # 现行 63@30 对照
```

| 指标 | 63 阶 @30 Hz（现行冻结） | **63 阶 @60 Hz** | **127 阶 @60 Hz** |
|---|---|---|---|
| −6 dB 点 | 0.704 / 3.496 Hz | 0.643 / 3.526 Hz | 0.703 / 3.497 Hz |
| −3 dB 点 | 0.895 / 3.305 Hz | 1.043 / 3.161 Hz | 0.892 / 3.308 Hz |
| 通带 1~3 Hz 起伏 | 1.90 dB | **3.28 dB** | 1.87 dB |
| 低阻带 @0.35 Hz | −16.2 dB | **−8.4 dB** | −16.4 dB |
| 高阻带 @3.85 Hz | −16.0 dB | **−9.9 dB** | −16.2 dB |
| 直流抑制 | −31.3 dB | **−9.8 dB** | −32.7 dB |
| 群延迟 | 1033 ms | 517 ms | 1050 ms |
| Σ\|h\|（累加器上界） | 55073 | 43499 | 54949 |

**结论**：
- **63 阶 @60 Hz 会把滤波器质量砍掉一大截**：阻带抑制 16 dB → 8.4/9.9 dB，**直流抑制 31 dB → 9.8 dB**（光照缓慢漂移会直接漏进心率带）；
- **127 阶 @60 Hz 与现行 63 阶 @30 Hz 几乎完全等价**（起伏 1.87 dB、阻带 16.2/16.4 dB、直流 −32.7 dB），群延迟 1050 ms ≈ 现在的 1033 ms；
- 代价：乘法器 32 → 64，**DSP 约 26 → 52**（LUT 也大致翻倍），需重跑 csynth 确认。

⇒ **本方案按 127 阶写**。若坚持 63 阶，必须把"降级"写进契约和报告，不能当等价升级。

#### 6.2.1 资源：127 阶不需要多花 DSP【有既有实测支撑】

现行 `fir_filter` v1 的综合实测（`fpga/report/c5_fir_filter_v1.md`，45 fps 条件下）：

| 项 | 实测值 | 说明 |
|---|---|---|
| DSP | **25**（占 220 的 11%） | 全并行 `II=1`；63 个系数按对称折叠成 32 个乘法 |
| LUT / FF | 4077 / 6172 | 延迟线 63×16 bit 被完全分区成**寄存器**（约 1008 FF），不占 BRAM |
| Fmax | 146.97 MHz | 目标 10 ns |
| 四个 IP 合计 | DSP **32** / BRAM 64 / LUT 8255 | 即全设计只用了 **14.5% 的 DSP** |

**关键点：60 Hz 采样在 100 MHz 时钟下有 1.67 M 拍/样本的时间预算**，吞吐量根本不是约束。
所以 127 阶有两条等价路线：

| 路线 | DSP | 代价 | 建议 |
|---|---|---|---|
| 保持 `II=1`（全并行 64 乘） | 约 **50**（合计 57/220 = 26%） | 加法树 64 路，Fmax 可能从 147 掉到 100~130 MHz，需 csynth 确认 | 可用；余量仍够 |
| 改 `II=4`（MAC 折叠） | **约 25（不涨）** | 每样本 4 拍；一段 1800 样本多花 ~7 万拍（0.7 ms） | **更稳妥**；对 60 Hz 流无感 |

> 结论：**R11"资源翻倍"不再是实质风险**，只是"要不要多花 25 个 DSP"的选择题。
> C 线可先按 `II=1` 跑一次 csynth，若 Fmax < 100 MHz 再改 `II=4`（改一行 pragma + 重生成黄金参考，后者本来就要重生成）。

##### 6.2.1.1 ✅ 127 阶 `II=1` 实测（2026-10-23，推翻上表"约 50 DSP / Fmax 掉到 100~130"的估计）

`II=1` 全并行跑下来了，**不用改 `II=4`**。完整报告：[`fpga/report/t8_fir_127tap_60hz_20261023.md`](../fpga/report/t8_fir_127tap_60hz_20261023.md)。

| 项 | 127 阶 @60 Hz 实测 | 63 阶 @30 Hz 基线 | 比值 |
|---|---|---|---|
| csim（Layer 1 + Layer 2 黄金参考） | **8/8 + 17/17 PASS** | 8/8 + 17/17 | — |
| cosim（Verilog RTL，带数据目录） | **PASS**（1 min 26 s，`hls::stream` 峰值深度 512） | PASS | — |
| DSP | **43**（19 %） | 25 | 1.72× |
| LUT / FF | **7 814 / 11 750**（14 % / 11 %） | 4 075 / 6 172 | 1.92× / 1.90× |
| BRAM_18K | 0 | 0 | — |
| Fmax | **145.07 MHz** | 146.97 MHz | −1.3 % |

> ⚠️ **口径修正**：上表"LUT 也大致翻倍"与实测一致（1.9×），所以**不能说"资源不翻倍"**；
> 正确的说法是"**绝对数接近翻倍，但只占器件的 14 % LUT / 11 % FF / 19 % DSP，放得下**"。
> 原 `II=1 约 50 DSP` 的估计偏保守（实测 43）——HLS 把两级乘加打包进了 DSP48，不是一乘一 DSP。

#### 6.2.2 启动瞬态：127 阶必须由质量门控覆盖【新增约束】

契约 §3.5 规定"保留启动瞬态，输出前 N−1 个样本"。于是每次 `reset=1` 之后：

| 阶数 | 未收敛样本数 | 未收敛时长 | 占 30 s 滑窗 |
|---|---|---|---|
| 63 @30 Hz（现行） | 62 | 2.07 s | 6.9% |
| 63 @60 Hz | 62 | 1.03 s | 3.4% |
| **127 @60 Hz（本方案）** | **126** | **2.10 s** | **7.0%** |

⇒ **每次重连/重启后的前 2.1 秒，`vital.hr_bpm` 在数学上不可采信**（滤波器尚未收敛）。
处理方式（必须写进 A 线实现与验收）：这 2.1 s 内 `vital.*` 一律输出 `null`，且 `quality.overall` 相应扣分；
即"启动后 2.1 s 内不报数字"。这与产品承诺"先判断能不能测，再决定测出什么"一致，**不是妥协**。

| **R17** | **两核被解码占满**后无人跑人脸关键点/管线/预览编码；两核同时解帧抬高 DDR 带宽 | **高** | 大（整机调度断裂） | 板上 `top`/`perf` 看两核占用；DDR 带宽用 `devmem` 或计数器估 | ①关键点跑在 **PL 回写的 480×270 灰度**上（§4.2.1a），**不许降到 5~10 fps**；②**RGB→灰度放在 PL 做**，PS 不做 `cvtColor`（省 2~3 ms/帧）；③预览编码降质/降分辨率 |
| **R18** | **MJPG 编码器按帧调量化表**（VBR/码控）⇒ ROI 均值被编码器调制，rPPG 出现假峰 | **中高**（家用量产相机普遍 VBR） | **大**（心率被编码噪声污染，且看不出来） | 相机对**静止场景**连拍 10 s：算 ROI 均值序列与逐帧量化表；频谱里 0.5~3 Hz 只应有噪声、无离散峰；再与固定码率对比 | 采购验收加一项：**能锁 `bitrate`/`quant`（CBR 或固定 Q）**；不能锁就选码率高且稳定的档，并把"码率抖动"计入 `quality`；R2 的退货门槛里追加这一条 |

### 8.1 我认为最可能翻车的几条（按严重度，不按编号）

1. **R14 时间轴**：这条最阴——系统看起来一切正常，指标也在跳，但心率是错的。**必须用实测帧间隔**，并在 `quality` 里暴露帧间隔方差。
2. **R18 编码器调制**：MJPG 是"压缩过的像素"。VBR 码控会在帧间改量化表，而 rPPG 要的信号是 0.5~2% 的亮度变化——**编码器完全有能力造出一个假峰**。验收时必须锁码率/量化，并用静止场景的频谱证明它没在作弊。
3. **R17 两核都被解码占满**：这是"双核并行"这个决定的**隐藏代价**——7020 只有 2 个核，解码吃满之后人脸关键点/管线/预览编码都没地方跑。但**关键点不能为了省 CPU 降到 5~10 fps**（眨眼 100~400 ms，会整段漏掉）。真正的解法是 §4.2.1 的**双向通路**：PL 回写 480×270 灰度，关键点在小图上跑 30 fps。
4. **R10 滤波器降级**：63 阶 @60 Hz 的直流抑制只剩 9.8 dB，光照一漂，HR 就飘。这条**已经用数据钉死了**，不要再凭感觉选 63。
5. **R16 启动瞬态**：127 阶 @60 Hz 前 2.1 s 不收敛，而这段时间**看起来完全正常**。它和 R14/R18 是同一类错误：数字有、但错。**必须由 `quality` 主动否掉**。
6. **R9 PetaLinux 不存在**：这是唯一"不在我们技术路线图里"的风险——**PL 没有 USB PHY**，板上的 USB Host 是 `USB3320C`（ULPI→PS MIO），所以"一条 USB 线"这件事**必须先把 PS 跑起来**。没有 BSP 就得自己建 PetaLinux，工期不可估。
