## 0. 一句话结论

1. **是代码问题，而且是唯一能解释 `mclk_seen=0` 的问题**：板上**根本没有**任何器件驱动 `CAM_CLK`，
   而 RTL 又把 `DRIVE_MCLK` 设成 0（高阻）⇒ 相机 INCK 悬空 ⇒ 它按数据手册就不接 SCCB。
2. **改 `DRIVE_MCLK=1` 后，片上实测 `CAM_CLK = 25.00 MHz`**（`mclk_period=8192`），
   「没时钟」这条**已闭环**。
3. **但相机 0x20 仍不应答**（只有板载 EEPROM 0xA0/0xB0 应答）⇒ 时钟不是唯一病因，
   下一层是**供电 / 复位 / 模块引脚定义 / 模块本体**。
4. **时钟该打多少**：IMX219 的 INCK 规格 **6 ~ 27 MHz（typ. 18 MHz）**，本板可用 50 MHz 分频；
   本轮先打 **25 MHz**（50/2）—— 只要求"在规格内"以回答"相机活不活"。
   真正出图时建议对齐业界标准 **24.000 MHz**（RPi 与 Linux `imx219.c` 寄存器组都按 24 MHz 写）。

## 2. 原理图复核：**更正 `docs/31` §2.3 的误读**【已验证】

原 `docs/31` §2.3 写「`U19` 经 `R156 33R` 直驱连接器 pin 12（`CAM_CLK`），所以 50 MHz 是板上固定的相机时钟」。
**这是错的**。逐页复核（`Mizar-Z7_R11.pdf`，Rev1.0，2020-05-05，18 页）：

| 页 | 内容 | 结论 |
|---|---|---|
| p.14「MIPI EEPROIM Clock」 | `U19`=`50M_OSC`，pin3 OUT → **`33R R156`** → 网络 **`PL_CLK_50M`** | R156 串在 **FPGA 时钟**上，**不是**相机线上 |
| p.5「PL Bank 34 & 35」 | `IO_L13P_T2_MRCC_35` = **球 `H16`** ← `PL_CLK_50M` | 50 MHz 进的是 FPGA 自己（与 XDC `clk=H16` 一致） |
| p.4「PL BANK0&13」 | `IO_L17P_T2_13` = **球 `U9`** → `CAM_CLK` | 相机时钟是**另一张网**，只到 FPGA |
| 全文检索 `CAM_CLK` | 仅出现 p.4（球 U9）与 p.14（连接器）两处 | **全网没有第二个驱动源** |

⇒ 板上**不提供**相机 MCLK，**只能由 PL 驱动**（角色等同树莓派 SoC 给相机 24 MHz）。
⇒ `DRIVE_MCLK=0` 不是"避免两源对打"，而是**让相机彻底没时钟**。
`docs/31` §2.3 与 `pl_cam_detect.v` 原注释里的"两源对打"结论**作废**（文档已就地改写并标注更正）。

### 2.1 连接器 `J11`（`CON15_FPC`）引脚表【已验证，500 dpi 裁图逐行确认】

| pin | 网络 | pin | 网络 |
|---|---|---|---|
| 1 | （未接） | 9 | `MIPI_CSI_CLK_P` |
| 2 | `MIPI_CSI_L0_N` | 10 | **GND** |
| 3 | `MIPI_CSI_L0_P` | 11 | `CAM_GPIO` → LV `PL_LED4` 经 **R33 0R(NC) 未贴** |
| 4 | **GND** | 12 | **`CAM_CLK`**（球 U9） |
| 5 | `MIPI_CSI_L1_N` | 13 | **`CAM_SCL`**（球 A20） |

  若用户手里是**通用树莓派模块**，需按模块自己的 15-pin 定义逐脚对一遍（否则供电/总线落空）。


| 量 | 读数 | 含义 |
|---|---|---|
| `step` | `7 (DONE)` | 定序器跑完了，不是卡死 |
| `mclk_period` | **8192** | `f = 4096 × 50 MHz ÷ 8192 =` **`25.00 MHz`** ← 驱动成功 |
| `mclk_self` | 1 | 标识"这是自己驱动的读数" |
| `hit_n` | 2 | 只有两个地址应答 |
| `hit_a0/a1`（8bit 写地址） | `0xA0` / `0xB0` | **板载 24C32 EEPROM**（p.14 U18），不是相机 |
| `cam_ack` | **0** | **相机 7bit `0x10` / 8bit `0x20` 不应答** |
| `rec0`/`rec1` | `0xFFFFFFFF` | 型号寄存器两次读回全 1（无人给数据） |
| `cam16`/`cam8` | `0x0000` | 型号不是期望的 `0x0219` |

**结论：`CAMERA_NOT_ACK`（退出码 1）。** 时钟这条已经排除，问题在相机侧。

## 5. 现在能确定 / 不能确定

**能确定【已验证】**
1. PL 能驱动 `CAM_CLK`（U9），且驱动后片上量到 **25.00 MHz**、SCCB 时序不受影响（EEPROM 仍稳定应答）。
2. 相机在**有合法 INCK（25 MHz，规格 6~27）**的情况下**仍然不 ACK**。
3. 总线本身没问题（同一对 SCL/SDA 上 EEPROM 应答正常，`i2c_act`/`pwr_done` 正常）。

**不能确定【推测，需物理手段】**
1. 相机是否真的拿到 **3.3V**（连接器 pin 15）—— 全程从未量过。
2. 相机 **XCLR** 是否被拉高（pin 22 在模块内部；`CAM_GPIO`(pin11) 的 **R33 未贴**，
   若模块把 XCLR 挂在该脚上则由模块自己上拉，否则可能一直处于复位）。
3. 模块的 **15-pin 定义**是否与本板逐脚一致（见 §2.1 的警告）。
4. 排线是否**插反/没插到底**（top-contact：金手指必须朝上）、模块是否损坏。

## 9. 追加实验：EEPROM dump 探针（2026-10-19 17:40）

**动机**：判读里总线上只有 `0xA0(7bit 0x50)` 与 `0xB0(7bit 0x58)` 两个地址应答，而板上只有
一颗 24C32(`U18`)。若 `0x58` 是**相机模块自带的 EEPROM**，就说明模块已通电、排线也通，
故障点应转向传感器本体/XCLR。于是新做一支只读探针，把两台器件的前 16 字节读出来做比对。

**做法**：新建 `board/cam_detect/pl_eeprom_dump.v`（不改已验证的 `pl_cam_detect.v`），
事务 = `START → 写地址 → 字地址 00 00 → 重发起 START → 读地址 → 连读 16 字节 → STOP`，
两台器件各一轮；**只读不写**（唯一"写"的是字地址指针 00 00）。
包装 `pl_eeprom_dump_dbg.v` + `build_dump.tcl` + `read_dump.tcl` + `board/check_eeprom.py`。

**结果【已验证】**（`_cam_build/eeprom_dump/eeprom_dump_ila.csv`，2048 采样全一致）：

```
dbg0 = magic 0xCAFE / done=1 / last_qi=22(qi_STOP) / a_ok=1 / b_ok=1 / fail_seen=0 / mclk_seen=1
A(0x50) 16 字节：FF FF FF FF FF FF FF FF FF FF FF FF FF FF FF FF
B(0x58)  8 字节：FF FF FF FF FF FF FF FF
```

**结论：这一轮"用内容比对"的测试【无区分力】** —— 空白 EEPROM 读出来本来就是全 `0xFF`，
所以"A 与 B 相同"既可能是同一颗芯片，也可能只是两颗都空。**但另有一条硬事实成立**：

- 【已验证】`0x50` 与 `0x58` **都在应答**（两轮独立位流/两次读回都见到）；
- 【已验证】两者读回**全为 0xFF**；
- 【推测，强】`0x58` **不可能是 24C32**：24C32 的 7bit 地址格式是 `1010 A2 A1 A0`，
  只能落在 `0x50~0x57`；`0x58`(`1011 000`) 已超出该范围 ⇒ 它是**另一种器件**。
  而这条 I2C 总线在板上只连三处：`U18`、FPGA(`A20/E17`)、`J11` 的 `CAM_SCL/CAM_SDA`(pin13/14)。
  ⇒ 该器件**只能在相机模块上**（若成立，则模块已通电、排线可用）。

**怎么把"无区分力"补成"有区分力"（未做，留给下一步）**：

| # | 动作 | 判读 |
|---|---|---|
| 1 | 拔掉相机 FFC，重跑 `read_dump.tcl` | `b_ok` 若变 0 ⇒ `0x58` 在**模块**上；若仍为 1 ⇒ 在**板上** |
| 2 | 万用表量 `J11 pin15` 对 GND | 3.3 V ⇒ 模块已通电（最直接，不依赖总线） |
| 3 | 给 `U18` 写一个字节再读回 | 能读回 ⇒ 接收路径正常；失败 ⇒ 先怀疑 WP(pin7) 被拉高 |

> ⚠️ 第 3 条会**改动硬件状态**（板上 24C32 目前是空白片），需人工同意后再做。

> 🔧 **2026-10-19 补充**：`board/check_eeprom.py` 现支持 **`--selftest`**（离线自检，不需要板卡）：
> 用构造 CSV 钉住「解码顺序」与三条结论分支，实测 **`RESULT: PASS (6/6)`**、退出码 0。
> 它已修过一个真 bug：原本先判 `a_same` 再判 `b_blank`，两台全 `0xFF` 时会误报
> 「同一颗芯片被两个地址命中」—— 现在多了一条 `elif a_zero and b_blank:` ⇒ 「无区分力」。

## 13. 结论与未闭合项（截至 2026-10-19 18:20）

### 13.1 能确定【已验证】

1. **板上不给相机时钟**：`U19(50M_OSC)`→`R156 33R`→`PL_CLK_50M`→球 `H16`（FPGA 自己的时钟）；
   `CAM_CLK`（球 `U9`）是**另一张网**，只连 J11 pin 12（§2 两页原理图互证 + MicroPhase 手册第 1 条）。
2. **PL 能把时钟发出去**（旧位流 `DRIVE_MCLK=1`、25 MHz 档）。⚠️ 但旧读数受 **F2** 影响（量的其实是自己的分频器）；
   新位流已把 `mclk_meas` 改成**真读引脚**（§12），**下次读回才是"波形出 pad"的首次硬证据**。
3. **SCCB 主机与总线都正常**：`U18`(0x50) 稳定应答；`0x58` 也应答；扫描走完 `step=DONE`。
4. **相机 7bit `0x10` / 8bit `0x20` 在任何地址都不应答**（两轮独立位流、两次读回）。
5. **`R33` 物理上未贴**（用户 2026-10-19 现场目视确认）⇒ `H17` 与 pin 11 之间**无电气通路**。
6. `0x50`/`0x58` 读回**内容全 `0xFF`**（§9），比对无区分力；但 `0x58` **不可能是 24C32**（地址格式 `1010 A2 A1 A0` 只覆盖 `0x50~0x57`）。

### 13.2 主假设（【推测-强】，待物理验证）

**`pin 11`(=`CAM_GPIO`) 是相机上电使能，当前悬空 ⇒ 传感器没被使能 ⇒ `0x10` 永不应答。**

支持它的四件事：①RPi 官方文档与 Arducam 同型号模组都把 pin 11 定义为 Power-Enable（高有效）；
②`0x58` 在应答 ⇒ 排线的 SCL/SDA/3.3V 通路**大概率是通的**（否则那台器件也不会应答）；
③时钟已由 PL 给出；④唯一的"没人管"的控制脚就是 pin 11。
