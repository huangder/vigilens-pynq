# 一、项目概述

## 1.1 一句话定位

> **用一颗摄像头看疲劳，用 FPGA 保证它测得准、报得及时。**

本项目（知倦 / VigiLens）是一套**无接触疲劳与生命体征趋势监测终端**：仅用一个普通 RGB 摄像头采集面部与上半身信息，先判断"信号是否可信"，再融合眨眼、闭眼比例、打哈欠、头部姿态等指标，给出**可解释**的疲劳风险提示；FPGA（PYNQ-Z2 的 PL 端）承担确定性的视觉与时序预处理。

## 1.2 项目名称与含义

| 场合 | 名称 |
|---|---|
| 中文规范全称 | 基于摄像头与 FPGA 的无接触疲劳与生命体征趋势监测终端 |
| 产品名 / 简称 | 知倦 |
| 英文全称 | VigiLens: A Trust-Aware Contactless Fatigue Monitoring Terminal with FPGA-Accelerated Vision Preprocessing |
| 英文简称 / 仓库名 | VigiLens |

命名逻辑：`Vigi`（Vigilance，警觉/值守）指向"长时间学习、值守"主场景；`Lens`（镜头）点明"只用摄像头、无接触"的输入形态；`Trust-Aware`（可信优先）把"信号质量门控"这一核心差异化写进标题；`FPGA-Accelerated Vision Preprocessing` 则让标题层面向评委/导师表明 FPGA 不是转发器，自研 IP 有真实价值。

## 1.3 标准版简介

> 知倦（VigiLens）是一套基于摄像头与 FPGA 的无接触疲劳与生命体征趋势监测终端，面向长时间学习、值守等场景。系统只用一个普通 RGB 摄像头，提取眨眼频率、闭眼时长、PERCLOS、打哈欠、头部姿态与运动质量等指标，并在受控条件下给出心率/呼吸率趋势估计。与同类作品不同，本系统把"测量是否可信"作为核心能力：先由光照、运动、人脸可见率与波形稳定性做信号质量门控，不可靠时明确拒绝输出而非乱报数字。PYNQ-Z2 的 PL 端承担 ROI 统计、帧差运动量、FIR 滤波等确定性预处理，PS 端负责人脸关键点、指标计算与规则融合，网页端实时呈现指标、趋势曲线与可解释建议。

# 二、背景与动机

## 2.1 问题

长时间学习、驾驶模拟或值守岗位中，疲劳往往**难以自查**，等意识到时注意力已明显下降。理想的状态监测应当是**无接触、实时、且结果可解释**的。

## 2.2 现有方案的痛点

1. **接触式**：穿戴设备（手环、胸带）有束缚感、需要佩戴，难以在自然场景长期使用。
2. **黑盒式**：多数视觉疲劳监测只给出一个"分数"或"疲劳/不疲劳"标签，无法追溯到触发它的指标。
3. **不可信却仍报数**：更普遍的问题是——当光照不足、人脸被遮挡、被测者大幅晃动时，信号已明显不可靠，系统却仍在输出一个跳变数值。这是非接触测量真正落地时最痛的一点。

## 2.3 本项目的回答：可信优先

本项目的核心主张不是"能测出什么"，而是**"它知道自己什么时候不该测"**。系统主动回答"当前测量是否可信"，不确定时输出"信号不可靠 / 请调整姿势"，而非报出一个跳变数字。

# 三、目标与范围

## 3.1 做什么（指标分层）

| 层级 | 指标 | 计算方式 | 可行性 | 定位 |
|---|---|---|---|---|
| 第一层（主线必做） | 眨眼次数/频率、单次闭眼时长、PERCLOS、打哈欠、头部姿态、人脸可见率/运动质量 | EAR/MAR/PERCLOS + 关键点 + 状态机 | 高 | 核心行为指标，不依赖训练数据 |
| 第二层（增强） | 信号质量评分、呼吸率趋势 | 光照/运动/可见率/波形稳定性融合；胸部 ROI 低频运动 | 中 | 质量门控是差异化核心 |
| 第三层（高风险） | rPPG 心率趋势 | 面部 ROI 绿通道均值 + 带通滤波 + 频谱峰值 | 中低 | 受控场景下才显示，宁缺毋滥 |

## 3.2 明确不做什么（边界声明）

- ❌ 血氧、血压、血糖、疾病/健康等级诊断（普通 RGB 摄像头原理上不可靠）；
- ❌ 医疗级精度承诺；
- ❌ 云端 API 人脸/医疗模型、在 PYNQ-Z2 上训练大型神经网络。

统一口径为：**疲劳风险提示 / 状态趋势监测 / 非接触测量原型 / 受控条件下的心率呼吸趋势估计**。本作品为实验室条件下的工程原型，**不用于医疗诊断**。

# 四、系统总体架构

## 4.1 软硬件分工

系统以 **PYNQ-Z2（Zynq-7000 XC7Z020）** 为核心，PS（ARM）+ PL（FPGA）分工如下：

| 模块 | 部署位置 | 职责 |
|---|---|---|
| 视频输入 | 摄像头 / 视频回放 | 提供 RGB 帧序列 |
| **PL 端（FPGA）** | PYNQ-Z2 PL | RGB/YUV 转换、缩放灰度化、ROI 像素统计、帧间运动量计算、FIR 带通滤波 |
| **PS 端（软件）** | PYNQ-Z2 PS / PC 后台 | 人脸与关键点检测、EAR/MAR/PERCLOS、头姿、质量评分、规则融合 |
| **前端** | 浏览器（网页） | 实时指标、趋势曲线、事件日志、六态状态灯 |

核心设计思想：**把"确定性、逐帧、量大"的预处理下沉到 PL**（低延迟、低抖动、省 CPU），把"算法密集、可调参"的感知与决策留在 PS，两者通过 AXI-Stream + DMA 衔接。

## 4.2 数据流

```text
摄像头/回放视频
      │  帧序列
      ▼
PL（FPGA）：格式转换 → 灰度化 → ROI 统计 / 帧差运动量 / FIR 滤波
      │  AXI-Stream + DMA（特征流）
      ▼
PS（软件）：人脸/关键点 → EAR/MAR/PERCLOS/头姿 → 质量评分 → 规则融合
      │  契约 JSON（WebSocket 每秒推送）
      ▼
网页仪表盘：指标卡 + 趋势曲线 + 六态状态灯 + 事件日志 + 可解释建议
```

## 4.3 部署形态（比赛默认路径）

- **软件演示路径（保底）**：USB 摄像头 → PC 后台（Python）→ 网页，完全不需要板卡即可闭环。
- **硬件加速路径（加分）**：同一输入在 PL 端走自研 IP，与软件基线**同屏对比**延迟/CPU 占用/吞吐/资源，证明 FPGA 的真实价值。

# 五、实现思路总览：三线并行

## 5.1 总体原则：先冻结接口，再各自开发

三人并行开发的**最大敌人是"等别人先做完"**。解决办法只有一条：

> **第 0 天先把三条线之间的"数据契约"（接口）冻结，之后每个人只对着契约开发，不关心别人的内部实现。**

## 5.2 三条线一览

| 线 | 角色 | 方向 | 难度 | 无硬件测试方式 |
|---|---|---|---|---|
| **A 线** | 算法 / 后端 | Python 视觉 + 指标 + 规则 | ★★★★ 中高 | 视频回放 + 黄金标注 |
| **B 线** | 前端 / 可视化 | FastAPI + WebSocket + 网页 | ★★★ 中 | Mock 假数据源驱动 |
| **C 线** | FPGA / 硬件 | HLS IP + 仿真 + Overlay | ★★★★★ 高 | C 仿真 + 黄金参考 |

## 5.3 无硬件测试手段（并行开发的基石）

三线各自用**互不依赖**的测试手段，把"必须碰硬件"压缩到最后一个里程碑：

1. **A 线用视频回放**：录制 4 段标准视频（静止 / 眨眼 / 打哈欠 / 转头遮挡），逐帧读入即等于实时输入，可无限次重复、结果可复现。
2. **B 线用 Mock 数据**：按契约生成"合理跳动"的假数据流，第一天起就无需等 A 线。
3. **C 线用 HLS C 仿真 + 黄金参考**：每个 IP 在 Vivado HLS 里完成 C 仿真，与 A 线提供的软件黄金参考比对，**100% 不需要板卡**；板卡只在最后"Overlay + DMA 上板"阶段才用。

> 即使 C 线在中期卡住，A+B 在 M2 已能合出完整可演示的**软件作品**，团队始终有一个保底作品。

# 六、A 线：算法与后端实现思路

## 6.1 技术选型

| 决策点 | 选择 | 理由 |
|---|---|---|
| 人脸关键点 | MediaPipe FaceMesh（468 点）主力，dlib（68 点）对照 | 免编译、快、自带 3D 坐标；dlib 用于交叉验证 |
| 视频输入 | OpenCV `VideoCapture`，优先文件回放 | 回放可复现，摄像头作为现场入口 |
| 头部姿态 | OpenCV `solvePnP` + MediaPipe 3D landmark | 无需标定相机，误差够用 |
| 信号处理 | NumPy + SciPy（`butter`、`rfft`） | 带通滤波与频谱峰值 |
| rPPG | 先手写绿色通道法，再用 open-rppg 对照 | 手写可解释、可移植到 FPGA 对比 |
| 配置 | YAML（`config.yaml`）统一存阈值 | 阈值不散落代码 |

## 6.2 各指标实现

**① 眨眼 / 闭眼 / PERCLOS**

- 眼关键点：MediaPipe 左眼 6 点 `[33,160,158,133,153,144]`、右眼 `[362,385,387,263,373,380]`。
- 公式（Soukupová & Čech 2016）：`EAR = (|p2−p6| + |p3−p5|) / (2·|p1−p4|)`。
- 状态机：`OPEN → CLOSING → CLOSED → OPEN`；连续 ≥3 帧低于阈值才算 CLOSED（去抖）。
- 初始阈值 `0.21`（dlib 常用），MediaPipe 版需用录制视频实测重新标定（一般 0.20~0.25）。
- 输出：眨眼次数、眨眼频率（次/分）、平均/最大闭眼时长、`PERCLOS = 窗口内闭眼帧数 / 有效帧数`（窗口 30s）、长闭眼事件数。

**② 打哈欠（MAR）**

- 嘴部纵横比 MAR = 上下唇距离 / 嘴角距离。
- 阈值约 `0.6~0.7`，且持续 `>800ms` 才算一次哈欠；用嘴部稳定性 + 头姿约束过滤说话/咳嗽误判。

**③ 头部姿态**

- MediaPipe 3D 关键点 + `solvePnP` → 旋转向量 → `Rodrigues` → yaw/pitch/roll。
- 阈值建议：`|yaw|>25°`、`|pitch|>20°` 触发"请调整姿势"，并辅助人脸可见率判断。

**④ 运动 / 光照 / 可见率质量**

- 运动：相邻帧灰度差分总和（与 C 线 `motion_quality` 用**同一口径**，便于软硬件比对）。
- 光照：ROI 灰度均值 + 饱和像素比例。
- 可见率：人脸框是否出界 + 关键点置信度。

**⑤ rPPG 心率（增强项，最后做）**

- 流程：面部 ROI（额头/脸颊，避开眼嘴）→ 每帧 G 通道均值 → 30s 滑窗 → 去直流/归一化 → `0.7~3.5Hz` 带通 → `rfft` 峰值 → BPM。
- **必须配套质量门控**：主峰突出度不足、BPM 跳变过大时输出 `hr_bpm=null, hr_conf=低`。

**⑥ 呼吸率（增强项）**

- 胸部/肩部 ROI → 帧间位移或亮度变化 → `0.1~0.5Hz` 带通 → 周期检测 → 次/分。

## 6.3 规则融合与可解释建议

```python
if face_visible < 0.7:        status = "adjust_posture"
elif quality.overall < 0.6:   status = "unreliable"
elif perclos > 0.25 and yawn >= 1:  status = "fatigue_risk"
elif long_close >= 1:         status = "fatigue_risk"
else:                         status = "normal"
```

每条建议带 `reason`（如"闭眼比例上升、连续打哈欠，且信号质量良好"），阈值全部来自 `config.yaml`，保证**逻辑可解释、参数可复现**。

# 八、C 线：FPGA 硬件实现思路

## 8.1 工具链

- **Vitis HLS 2026.1**（赛制指定），入口为 `vitis-run --mode hls --tcl <脚本>`（2026.1 已无旧 `vitis_hls` 命令）。
- 像素流接口范式直接套 **Vitis Libraries（Vision）**：`hls::stream<ap_axiu<24,1,1,1>>`（RGB888，TUSER 帧头、TLAST 行末），控制用 `#pragma HLS INTERFACE s_axilite bundle=ctrl`。
- 定点化：像素 8bit、累加 32bit、FIR 系数 Q15；精度决策写进 `interface.md`，A 线黄金参考按同一精度实现。

## 8.2 三个自研 IP

| IP | 输入 | 处理 | 输出 | 用途 |
|---|---|---|---|---|
| `roi_statistic` | 像素流 + ROI 坐标 | ROI 内像素累加 `sum_r/sum_g/sum_b` 并计数 | `{sum_r,sum_g,sum_b,count}` | 为 rPPG 与图像质量提供时间序列，替代 PS 逐像素扫描 |
| `motion_quality` | 当前/上一帧灰度 | 逐像素 `|cur−prev|` 求和 + 运动比例统计 | `{diff_total,motion_ratio}` | 运动质量评分，屏蔽不可靠测量 |
| `fir_filter` | 时间序列流 | 固定阶数 FIR 带通（0.7~3.5Hz） | 滤波序列 | 硬件滤波，与 PS `scipy.signal.lfilter` 对比延迟/CPU |

## 8.3 黄金参考纪律（软硬件一致性的关键）

> 原则：**同一份输入，硬件算的 vs 软件算的，必须一致**（整数逐点相等、定点在容差内）。

| IP | A 线黄金参考 | C 线输出 | 比对口径 |
|---|---|---|---|
| `roi_statistic` | NumPy 同一 ROI 累加 | `{sum_r,sum_g,sum_b,count}` | 定点位宽一致、逐帧一致 |
| `motion_quality` | OpenCV `absdiff` 求和 | `{diff_total,motion_ratio}` | 同一帧对、同一阈值 |
| `fir_filter` | `scipy.signal.lfilter` | 滤波序列 | 同一系数、容差内 |

C 线全程离线验证"硬件算得对"，靠的是 A 线这份软件黄金参考，**而不是等板卡**。

## 8.4 上板链路（后期，此时才需要板卡）

Block Design（Zynq PS + AXI DMA + 自研 IP）→ PYNQ `Overlay('xxx.bit')` + `allocate` DMA 缓冲 + `register_map` 配置 → 调用 → 与软件基线做软硬件一致性对比（延迟/CPU 占用/吞吐/资源）。

# 九、接口契约（三线耦合点）

## 9.1 A ↔ B：指标 JSON（WebSocket 每秒推送）

```json
{
```

# 十一、创新点与竞争力

## 11.1 三大特色

1. **可信优先（核心差异化）**：系统主动回答"当前测量是否可信"，不确定时输出"信号不可靠/请调整姿势"而非跳变数值。多数作品只展示"测出来了"，很少展示"我知道什么时候不该测"。
2. **硬件可量化**：自研 `roi_statistic` / `motion_quality` / `fir_filter` 等 HLS IP，提供纯软件 vs FPGA 模式在延迟、CPU 占用、吞吐与资源（LUT/FF/BRAM/DSP/WNS）上的同条件对比数据——这正是对抗"FPGA 价值隐形"短板的关键。
3. **可解释**：每一条建议都能追溯到触发它的指标与置信度，配合时间趋势曲线与事件日志，输出六态结果。

## 11.2 与赛制评分权重对应

| 评测项（权重） | 本项目对应策略 |
|---|---|
| 创新性与应用价值（30） | "信号质量门控 + 多指标融合 + 可解释报告 + FPGA 确定性处理"构成工程创新 |
| 性能与资源优化效果（20） | 软件 vs FPGA 同条件对比表 |
| 功能正确性与设计完整性（20） | MVP 优先 + 黄金参考 + 状态机 + 软硬件一致性比对 |
| 大模型协作与技能包（15） | AI 协作记录模板 + Skill 沉淀；通用 PYNQ Skill 单独加分 |
| 文档质量与可复现性（15） | 英文命名、可复现脚本、CSV 日志、一键复现 |

# 十二、风险与预案

| 风险 | 后果 | 预案 |
|---|---|---|
| 摄像头接入 FPGA（HDMI/MIPI）不稳定 | 硬件模式卡死 | 比赛默认走"USB→PC 开发模式"；FPGA 板卡用回放/文件流驱动闭环 |
| rPPG 心率跳变 | 现场演示丢分 | 只显示趋势 + 置信度，异常时拒绝输出；严格执行"置信度不足即显示暂不可用" |
| Vivado 2026.1 新版本 | 综合/时序出意外 | 锁定版本；尽早做"最小 Overlay 空跑"验证工具链（已部分完成） |
| 3 人 8 周工作量 | 范围失控 | 三线并行、各自独立测试；集成点压到最少；rPPG 严格放最后 |
| 人脸关键点受光照影响 | 眨眼误检 | 图像质量门控；演示锁定光照；录制"失败案例"作为边界说明 |
| 医疗表述过度 | 答辩/合规风险 | 全组统一"趋势监测、辅助提示"话术 |
| A 线进度慢，B 线干等 | 前端没数据 | B 线永远先接 Mock，不阻塞 |
| 板卡到手晚/损坏 | 无法上板 | 用远程板卡或 C 线仿真结果先撑住，M4 延后但不致命 |

# 十四、恳请导师指导的问题

以下是我们希望在确定最终方案前，请导师把关的关键问题：

1. **选题定位与创新性**：疲劳监测在同类竞赛中出现频率较高，创新性天花板受限。我们计划把"信号质量门控（可信优先）"升级为核心卖点，您认为这个切入角度是否足够形成差异化？还有没有更值得押注的差异化方向？
2. **rPPG 心率的取舍**：rPPG 心率是"做稳了是亮点、做不稳是软肋"的双刃剑。您建议把它定位为"有条件的增强"（当前方案），还是直接砍掉、把精力全部集中到行为指标主线？
3. **FPGA 价值如何被看见**：ROI 统计、帧差、滤波都在芯片内部跑，评委/导师在演示里"看不见"硬件加速。我们计划用"软件 vs FPGA 同屏对比（延迟/CPU/吞吐/资源）"来呈现，您认为这种呈现方式是否充分、专业？
4. **技术选型把关**：人脸关键点我们倾向 MediaPipe（468 点）主力 + dlib（68 点）交叉验证；摄像头接入比赛默认走"USB→PC"、板卡用文件流回放。这两项选型是否有更稳妥的替代？
5. **范围与时间**：三人（大二）约 8 周，主线"行为指标 + 网页 + FPGA 预处理"是否够得着？您建议在哪些地方进一步砍范围、保完成度？
6. **工程规范与可复现性**：赛制强调"可复现以实测数据为主"，我们已建立黄金参考 + 契约 + 一键复现的框架。以您的经验，还有哪些工程细节最容易在评审中失分、需要提前补齐？
