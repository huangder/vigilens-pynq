## 一、评估依据与前提

本评估严格以《2026 FPGA 赛道选题指南（AMD）》中 **3.3 自主选题赛道（初级组）** 的公开规则为基准，核心约束与权重如下：

| 项目 | 规则要点 | 对本方案的直接影响 |
|---|---|---|
| 参赛资格 | 大一至大三在读本科生（队伍中最高学历决定组别） | 若任意成员为大四/研究生将强制归入**高级组**，需先自查 |
| 器件范围 | 7 Series / Zynq-7000 / UltraScale / UltraScale+ | PYNQ-Z2（Zynq-7000 XC7Z020）**合规** |
| 推荐实现 | 初级组推荐 PYNQ：PS 用 Python，PL 用 HLS/RTL 封装 Overlay | 现有方案与官方推荐**高度吻合** |
| 工具版本 | Vivado / Vitis 2026.1（推荐）或 2025.2 | 需固定版本，保证脚本可复现 |
| 大模型协作 | 允许任意公开大模型，**须提交提示词/回答/自我纠错轨迹** | 现有方案第 12 节已覆盖，且是**必交项** |

| 决赛 | 一页英文 PPT 海报（A4 彩色打印） | 需预留英文海报制作时间 |

### 3.3 赛道评审权重（评测项 / 权重）

| 评测项 | 权重 |
|---|---:|
| 创新性与应用价值 | 30 |
| 性能与资源优化效果 | 20 |

## 二、可行性评估

### 2.1 总体结论

**总体可行性：中高（约 7.5 / 10），但高度依赖"砍范围 + 接口冻结"两个前置动作。**

现有方案是本次评估中**最值得肯定的一点**：它把"能做到的"和"做不到的"分得很清楚，没有掉进"用摄像头测血氧/血压"这类必死陷阱。方案的分层（第一层稳定指标 / 第二层增强 / 第三层明确不做）是专业且成熟的。

**结论一句话：核心主线（眨眼 + PERCLOS + 打哈欠 + 头姿 + 运动质量 + 网页 + FPGA 预处理）对一个大二三人组是"够得着、但吃紧"的目标；rPPG 心率/呼吸率是"锦上添花、做不稳就砍"。**

### 2.2 技术可行性分层

| 层级 | 内容 | 可行性 | 三人组落地的真实难度 | 判断依据 |
|---|---|---|---|---|
| 第一层（主线，必做） | 眨眼/眨眼频率、闭眼时长、PERCLOS、打哈欠、头部姿态、人脸可见率/运动质量 | **高** | 中 | 依赖成熟库（MediaPipe / dlib / OpenCV），算法是"状态机 + 阈值"，不依赖训练数据 |
| 第二层（增强） | 信号质量评分、呼吸率趋势 | **中** | 中高 | 呼吸率靠胸部 ROI 低频运动，受衣着/角度影响，需质量门控 |
| 第三层（高风险） | rPPG 心率趋势 | **中低** | 高 | 对光照、肤色、运动、静止极敏感；即使做出来也难在演示现场稳定复现 |
| 明确不做（正确） | 血氧、血压、血糖、疾病诊断 | — | — | 普通 RGB 摄像头原理上不可靠，写入承诺会反噬答辩 |

### 2.3 关键风险点与现有方案应对

| 风险 | 后果 | 现有方案是否已有降级 | 补充建议 |
|---|---|---|---|
| 摄像头接入 FPGA（HDMI/MIPI）不稳定 | 硬件模式卡死 | 有：用固定视频帧序列先验证 PL | 把"真实摄像头走开发模式（USB→PC）"设为**比赛默认路径**，FPGA 板卡用**回放/文件流**驱动即可闭环 |
| rPPG 心率跳变 | 现场演示丢分 | 有：只显示趋势 + 置信度，异常时拒绝输出 | 严格执行"置信度不足即显示『暂不可用』"，**宁缺毋滥** |
| Vivado 2026.1 新版本 | 综合/时序出意外 | 部分（提到用 AI 分析报告） | 锁定版本，尽早做一次"最小 Overlay 空跑"验证工具链 |
| 3 人 8 周工作量 | 范围失控 | 有 MVP 冻结点（第 5 周） | 三条线**并行**且各自可独立测试（见分工文档），把集成点压到最少 |
| 人脸关键点受光照影响 | 眨眼误检 | 有：图像质量门控 | 演示现场**锁定光照条件**，录制"失败案例"作为边界说明（反而加分） |
| 医疗表述过度 | 答辩/合规风险 | 有：统一"趋势监测、辅助提示" | 全组统一话术，报告/视频/PPT 三处口径一致 |

### 2.4 可行性结论

1. **软件主线（算法 + 网页）可行性接近"确定"**：有成熟开源库，三天可出第一个可用闭环，且**完全不需要硬件**即可测试（USB 摄像头 + 视频回放）。
2. **FPGA 主线可行性"中高"**：`roi_statistic` / `motion_quality` / `fir_filter` 这类 IP 是 HLS 教学级难度，C 仿真即可验证正确性，**上板只是最后一步**。真正的门槛不在代码而在"工具链 + 时序收敛"的第一次跑通。
3. **rPPG 是唯一"可能白做"的部分**：建议严格执行方案的"受控场景才显示、否则拒绝输出"，并把它定位成**答辩亮点而非 MVP 依赖**。

## 三、获奖率评估

### 3.1 按评审权重逐项预估

> 评分带为"若按现有方案认真执行到各自程度"的**经验区间**，非承诺。

| 评测项（权重） | 预估区间 | 依据 |
|---|---|---|
| 创新性与应用价值（30） | **20 ~ 24** | 选题"疲劳监测"本身**常见、不新**；但"信号质量门控 + 多指标融合 + 可解释报告 + FPGA 确定性处理"构成**工程创新**。天花板被选题同质化压制 |
| 性能与资源优化效果（20） | **13 ~ 17** | 方案明确要求软件 vs FPGA 的延迟/CPU/吞吐/资源对比表，若真实执行是强项；当前是**纯规划、零实测** |
| 功能正确性与设计完整性（20） | **14 ~ 18** | MVP 优先 + 黄金参考 + 状态机 + 软硬件一致性比对，方法论扎实；取决于"是否真上板跑通" |
| 大模型协作与技能包（15） | **11 ~ 14** | 方案有专门 AI 协作记录模板 + Skill 规划，且 PYNQ Skill 有**额外加分**；需真实沉淀而非补写 |
| 文档质量与可复现性（15） | **12 ~ 14** | 英文命名、可复现脚本、CSV 日志等要求齐全；符合赛制对"可复现"的硬性强调 |
| **合计（100）** | **约 70 ~ 87** | 执行质量决定落点 |

### 3.2 优势（支撑得奖的确定性）

1. **与赛制高度咬合**：PYNQ 框架 + HLS Overlay 是初级组官方推荐路径，等于"顺着评分标准做题"。
2. **自研 FPGA 模块有真实、可量化的价值**（ROI 统计 / 运动质量 / FIR 滤波），能拿出"软件 vs 硬件"对比，这正对"性能与资源优化（20）"。
3. **PYNQ Skill 加分点**：方案第 12.4 节规划的 `pynq_overlay_loader`、`dma_buffer_debug` 等是**跨题目通用**的，直接命中"通用 PYNQ Skill 单独加分"。
4. **可复现性会非常好看**：黄金结果 + CSV + 英文目录 + 复现脚本，契合"文档与可复现（15）"和"可复现以实测为主"的核查口径。

### 3.3 劣势与天花板

1. **选题创新性是硬伤**：驾驶/疲劳监测是学生竞赛里的高频题目，评委第一眼不会觉得"新"。
2. **FPGA 的价值"看不见"**：ROI 统计和帧差是内部计算，评委在视频里看不出"硬件加速了"，必须靠对比表说话（见第四节）。
3. **rPPG 是把双刃剑**：做稳了是亮点，做不稳是答辩被追问的软肋。
4. **三人组的精力上限**：如果同时铺开 rPPG + 双摄像头 + 复杂前端，很可能"什么都有一点、什么都不扎实"，反而拉低完成度。

### 3.4 获奖率结论（客观）

| 情形 | 大概率结果 |
|---|---|
| **最佳**：MVP 完整闭环 + FPGA 真上板 + 软硬件对比表 + 通用 PYNQ Skill + 文档齐全 + rPPG 作为"有条件的增强" | 初级组**二等奖稳、冲一等奖**（一等奖需在创新性上再压一个差异化点，见第五节扩展方向） |
| **一般**：MVP 完成、FPGA 上板但对比数据弱、rPPG 砍掉或仅验证 | **三等奖 / 二等奖边缘** |
| **差**：只有软件 demo、FPGA 未上板或仅有转发 | 难以进决赛（赛制要求"作品须在板上跑通并提供实测输出"） |

> **一句话：这个方案的"下限高、上限中等"。** 它几乎不可能因选题翻车（合规、完整、可复现都稳），但也很难靠"疲劳监测"本身拿一等奖。**提高上限的唯一办法是把第五节里的某个扩展方向做成"真实现、可演示"的差异化卖点。**

## 四、最终视频呈现效果评估

> 决赛视频/现场演示是"评委对你的第一印象"，对打分的影响往往大于报告。

### 4.1 天然优势

1. **这是一套"活的"演示**：真人坐在摄像头前，网页上人脸框、眨眼曲线、PERCLOS、状态灯实时跳动，**有画面、有动作、有反馈**，比静态数据或纯硬件闪烁 LED 更抓眼球。
2. **叙事线清晰**："摄像头看到 → 系统判断 → 给出可解释建议"，观众 30 秒内能看懂在做什么。
3. **有人情味**：疲劳/专注监测贴近每个人的生活（学习、开车、熬夜），天然有共鸣。

### 4.2 致命短板

1. **FPGA 的价值在画面里是隐形的**：ROI 统计、帧差、滤波都在芯片内部跑，观众只看到网页，**完全感受不到"这块板子到底干了什么"**。这会导致评委误判为"就是个 Python + OpenCV 的网页 Demo"。
2. **rPPG 数字若飘**（心率 72 → 忽然 110）：会在视频里留下"不可信"的直观印象，且难以剪辑掉。
3. **如果 UI 粗糙**：会立刻拉低"工程完成度"印象分，甚至盖过算法的正确性。

### 4.3 针对性提升建议（按性价比排序）

1. **同屏放"软件 vs FPGA"实时对比**（最高优先级）：画面一侧是 FPGA 模式的延迟/CPU 占用/吞吐数字，另一侧是纯软件基线，配一句"同一输入，FPGA 延迟 0.8ms vs CPU 12ms"。**这是让评委"看见"硬件价值的最直接手段。**
2. **给 FPGA 板一个特写分镜**：开机、Overlay 加载、DMA 数据流动、LED 指示，把"板子真的在干活"拍进视频。
3. **设计 30 秒"可复现剧情"**：正常状态 → 连续眨眼/打哈欠 → 状态转为"疲劳风险升高" → 系统给出可解释建议。**剧情可控、结果确定，才能拍得干净。**
4. **把"信号不可靠"拍成一个卖点**：故意遮脸/大幅晃动 → 系统显示"信号不可靠/请调整姿势"而不是乱报数字。**这比"测出心率"更能体现工程严谨，也更符合赛制对"失效边界"的重视。**
5. **UI 打磨优先于功能堆料**：一个干净的仪表盘（深色底 + 大数字 + 平滑曲线 + 中文状态提示）远胜一堆挤在一起的原始波形。
6. **保留一条"回放视频驱动"的备用演示路径**：现场设备出问题时，用录好的视频流也能完整走一遍，避免翻车。

**视频呈现结论：呈现效果的天花板取决于"能否让评委看见 FPGA 的价值 + UI 是否精致"，而非算法本身有多准。**

## 五、项目扩展方向（兼具实用性与创新性）

> 以下方向按"对获奖率的边际提升"排序，每个都标注：实用性、创新性、落地成本、与 FPGA 的结合点。**建议只选 1 个做成"真实现 + 可演示"，其余作为答辩里的"未来规划"一句话带过。**

### 方向 1：把"测量质量门控"做成独立卖点（最推荐）

- **做法**：把现有方案里的"信号质量评分 + 拒绝输出"从附属功能**升级为核心能力**——系统主动回答"**什么时候我的测量是可信的**"。
- **实用性**：极高。几乎所有非接触测量（心率、呼吸、甚至人脸识别）的落地痛点都是"结果不可信却没人告诉你"。
- **创新性**：中高。多数参赛作品只展示"测出来了"，很少展示"我知道什么时候不该测"。
- **FPGA 结合点**：运动质量/光照/帧差的**确定性实时计算**恰好是该门控的低延迟来源，能自然形成软硬件对比。
- **成本**：低（现有方案已具备 80% 的素材，只是换叙事重心）。

### 方向 2：边缘隐私保护——"原始视频不上云"

- **做法**：强调系统**只在本地/板卡上处理**，向外只输出指标与统计量，原始人脸视频不离开设备。
- **实用性**：高（合规、隐私是当前行业刚需）。
- **创新性**：中高（把"本地推理 + 特征化输出"作为作品的价值主张，而非技术本身）。
- **FPGA 结合点**：PL 直接输出 ROI 统计/特征，PS 只上传数值——天然契合"隐私计算"叙事。
- **成本**：低（是"叙事 + 架构取舍"问题，几乎不增加开发量）。

### 方向 3：无接触呼吸率/心率的"夜间/静止场景"专项

- **做法**：放弃"实时驾驶"这种高运动场景，转攻**静止/睡眠**场景下 rPPG 与呼吸率——人静止时信号质量大幅上升，成功率远高于动态场景。
- **实用性**：高（睡眠呼吸、老人夜间照护是真实需求）。
- **创新性**：中（领域不算新，但"面向静止场景的非接触长期趋势"定位更扎实）。
- **FPGA 结合点**：长时间窗口的 ROI 统计 + FIR 滤波 + 峰值估计，正是 FPGA 的确定性时序处理主场。
- **成本**：中（需要稳定的 rPPG 调参，但比动态场景容易得多）。

### 方向 4：轻量可解释 AI 信号质量分类器

- **做法**：在规则之上加一个**小型模型**（决策树/逻辑回归/小 MLP），输入是"人脸可见率、光照、ROI 位移、波形周期稳定性"等特征，输出仅"可靠 / 需调整 / 无效"，并与规则基线对比。
- **实用性**：中高。
- **创新性**：中高（"可解释小模型做门控"比"大模型做诊断"更聪明，也更符合赛制对"边界"的偏好）。
- **FPGA 结合点**：特征由 PL 实时算，模型在 PS 推理，形成"特征-推理"软硬件分工。
- **成本**：中（需采集/标注少量特征数据，但可自行造）。

### 方向 5：多视角（正面 + 侧面）融合

- **做法**：现有方案第 4.4 节已规划：正脸做眨眼/嘴部，侧面做头姿/胸部起伏，按"信号质量加权"融合。
- **实用性**：中（解决正面遮挡、转头时的鲁棒性）。
- **创新性**：中。
- **FPGA 结合点**：多路视频同步、质量加权、跨视角时序对齐。
- **成本**：**高**（多路同步/标定/带宽/遮挡都是坑）。**建议仅作为"答辩规划"，不进 MVP。**

### 方向 6：跨题目通用 PYNQ Skill 库（赛制直接加分项）

- **做法**：把 `overlay 加载校验`、`DMA 缓存一致性封装`、`黄金参考比对 + 性能/资源自动采集报告生成器` 做成**不与本题绑定的开源工具包**。
- **实用性**：高（对后来的参赛者、教学、工程复用都真有用）。
- **创新性**：中高（赛制明文"通用 PYNQ Skill 单独加分"，且这是**评委能直接验证**的加分）。
- **成本**：低（从本队开发过程中顺手沉淀即可）。
- **结论**：**这是所有扩展里"投入产出比最高"的一项，建议无条件做。**

---

## 六、总体结论与建议

1. **现有方案整体质量高、方向正确、与赛制贴合**，是"正确但不够惊艳"的稳妥路线。
2. **可行性**：主线（行为指标 + 网页 + FPGA 预处理）对三人组"够得着但吃紧"；rPPG 心率必须降级为"有条件的增强"。
3. **获奖率**：下限高（三等奖稳）、上限中等（二等奖可期），**冲一等奖必须靠第五节某个扩展方向做出可演示的差异化**，建议优先 **方向 1 + 方向 6**（成本低、加分直接）。
4. **视频呈现**：最大风险是"FPGA 价值隐形"与"rPPG 数字飘"，务必做"软硬件同屏对比 + 可控剧情 + 精致 UI"。
5. **下一步（当前阶段）**：先按《04_基础框架搭建指南》搭出**可端到端跑通的骨架**（目录 + 接口契约 + stub 流水线 + 测试脚手架 + 一键复现），再按《02》《03》逐模块填充真实现；AI 使用一律遵循《05_AI使用约束》。
