# 18 相机推流修复方案 —— BUG-027：`img.compress()` 抛 `Compression Failed!` 导致推流死掉

> **适用**：分支 `c-line/fs30` · 编写 **2026-09-27** · 相机：**OpenMV Cam H7**（`OpenMV v5.0.0` / `MicroPython v1.28.0-49` / `csi` 类 API）/ 串口 **COM10**
> **要修的那张卡**：`docs/16` → [BUG-027](16_测试问题台账.md#bug-027)（P1，已定位+缓解，**未根治**）
> **配套**：`docs/17_阶段二_OpenMV采集测试手册.md`（操作手法）、`board/openmv/openmv_stream.py`（要改的文件）、
> `metrics/scripts/omv_stream_bridge.ps1` + `metrics/scripts/omv_camera_demo.ps1`（PC 侧）
> **一句话**：**这块板子是 H7 R2（传感器 MT9M114，本身不输出 JPEG）→ 路线①已经被硬件排除**；
> 先跑 30 秒探针把 `sensor.get_id()` 记下来（补齐事实缺口），然后走**路线②（发原始灰度、PC 侧编码）**，
> 赶时间就先上**路线③**顶住 —— 别先动手改代码。

## 0. 现状（2026-09-27 本机实测，**这是对照基线**）

| 项 | 实测值 | 出处 |
|---|---|---|
| 失败表现（相机侧） | `img.compress(quality=80)` → `OSError: Compression Failed!` → **异常逃出循环，整条流回 REPL** | BUG-027 的串口原始转录 |
| 失败表现（PC 侧） | 脚本"启动横幅"打印了，之后 **0 字节**；网页 `age_s` 单调增长 → 画面被隐藏 | BUG-027 |
| 同会话对照（决定性的三条） | `QVGA/q80` **失败** · `QVGA/q50` **成功 9337 B** · `QQVGA/q80` **成功 6601 B** | BUG-027 |
| `gc.mem_free()` | 302416 / 311264 / 312096 / 314928 / 319360 B（不同阶段） | 本轮实测 |
| QVGA RGB565 帧缓冲 | **153600 B**（QQVGA 只要 **38400 B**） | 契约/传感器规格 |
| 已做的缓解 | 每帧 `gc.collect()`、单帧失败只丢该帧不退出、`del _src` 后再 `exec`（+8848 B）、推流默认 `quality=50`、监护脚本自动重启 | 本轮 |
| 缓解后的最好成绩 | 一个 100 s 窗口 **frames=353 / crc_bad=0**（~10 fps / 96 KB/s），**但之后仍会失败**（窗口后来缩到 ~10 s） | 本轮 |
| 链路吞吐参考 | VCP 实测 ~258 KB/s（QVGA JPEG 30 fps 时代） | `fpga/report/t8_*.md` |
| 现在桥接开的端口速率 | **115200**（`Get-OMVPort` 里写死的） | `metrics/scripts/omv_stream_bridge.ps1` |

**为什么会失败（当前认知）**：
- 【已验证】失败点就是"编码器要一块**连续**内存"——同编码器、同画面，**只改分辨率/quality 就决定成败**；而 H7 可用堆只有 ~302 KB，QVGA 帧缓冲已占 153600 B。
- 【推测】根因是**堆/帧缓冲池的碎片**：多轮 `sensor.reset()` + 逐帧 `compress()` 各分配一次输出缓冲，最终找不到连续块。
- 【不确定】为什么同一配置有时能跑 353 帧、有时第 1 帧就失败（与上电/复位历史有关，**没有稳定的复现规律**）。
  ⇒ 所以**不能把"降低 quality/分辨率"当作"修好了"**：真正的修复必须让"要一大块连续内存"这件事**在原理上不发生**。

## 0.1 硬件事实（**2026-09-27 确认，这条改变了整份方案**）

| 项 | 事实 | 出处 |
|---|---|---|
| 板子 | OpenMV Cam H7 **R2** | 用户确认（实物） |
| 传感器 | **ON Semi MT9M114**（H7 = OV7725，**R2 = MT9M114**） | [官方 v5.0.0 文档](https://docs.openmv.io/v5.0.0/openmvcam/quickref/openmv-cam-h7.html)（原文：*"the **H7** with the **OV7725** and the **H7 R2** with the **ON Semi MT9M114**"*） |
| **传感器能出 JPEG 吗** | **不能**。MT9M114 是 raw Bayer 传感器；官方产品页写它 *"capable of taking 640×480 8-bit **Grayscale** images or 640×480 8-bit **BAYER** images at 40 FPS"* | [OpenMV Cam H7 R2 产品页](https://openmv.io/products/openmv-cam-h7-r2) |
| **传感器能出灰度吗** | **能，而且是原生 8-bit 灰度**（40 FPS @640×480） | 同上 → **路线② 有硬件底气** |
| 板子有硬件 JPEG 编解码器吗 | **有**（STM32H743 内置），但**当前固件没把它当作 `img.compress()` 的免内存通路**（否则我们不会撞内存墙） | 官方文档 Highlights："Hardware JPEG encoder/decoder"；【推测】见下 |
| 传感器能不能换 | **能**：官方文档明确 "The sensor sits on a **removable module** — swap it for any of the other OpenMV camera modules" | 同上 → 路线①以"换模块"的形式重新可行（§2 路线①b） |

**由此得到的两个硬结论**：

1. **`sensor.set_pixformat(sensor.JPEG)` 报 `Sensor control failed` 是正常现象，不是缺陷**
   → 这也给 BUG-017 的定性补上了根因（**传感器物理上不支持 JPEG**，不是固件配错）。
2. **这块板子上"相机出 JPEG"只能靠软件压缩** → `img.compress()` 必然要一块大缓冲 →
   **BUG-027 的失败模式是"这块硬件 + 这条路线"的固有矛盾**，不是偶发 bug。
   所以修复方向必然是：**要么别在相机上压缩（路线②/④），要么换一颗带 JPEG 的传感器（路线①b）。**

> ⚠️ 探针仍然要跑，但它的目的变了：**不是为了决定走哪条路**（已定），而是
> ① 记下 `sensor.get_id()` 与完整固件串，补齐 `AGENTS.md` §7.7 的"未拿到"两项；
> ② 顺手确认这颗传感器的 **GRAYSCALE 模式**在本固件下可用（路线②的前提）。

## 2. 三条候选路线（按"彻底程度"排）

### 路线 ① 用传感器硬件 JPEG（**✗ 本硬件不可行**：H7 R2 的 MT9M114 不输出 JPEG，见 §0.1）

**原理**：`sensor.set_pixformat(sensor.JPEG)` 让 **传感器/固件直接产出 JPEG**，`sensor.snapshot()` 返回的就是 JPEG 图像，
`stream()` 里**不再调用 `img.compress()`** → 失败模式**在原理上不可能再发生**。

**改动**（`board/openmv/openmv_stream.py` 的 `stream()` 里 `use_jpeg` 那一段）：

```python
    if use_jpeg:
        # 路线①：JPEG 由传感器直接产出，不做软件压缩（BUG-027 的根治）
        sensor.set_pixformat(sensor.JPEG)      # ← 由调用方/参数决定，见下
        ...
        img = sensor.snapshot()
        blob = _to_bytes(img)                  # 不再 img.compress()
        mtype = link.TYPE_JPEG
```

⚠️ 三个必须注意的点：
1. **`use_jpeg` 与 `use_usb` 之外，还要区分"统计量模式"**：JPEG 图像上做 `get_statistics(roi=…)` 不可靠
   → `stats` 那条路（`link.pack_stats`）**必须继续用 RGB565/GRAYSCALE**，两套 pixformat 不能混着用一个分支；
2. `sensor.set_pixformat()` **必须在 `set_framesize()` 之前**（顺序反了就是 `Sensor control failed`，`board/openmv/README.md` §4.4 有记）；
3. **先把 `/flash` 上的脚本备份**（`board/openmv/flash_backup_20260926/` 已有一次字节级备份，含 sha256 与恢复步骤）。

**代价**：几乎没有（帧率应比软件压缩**更高**）。**判据**：见 §3。

**✗ 但在这块板子上这条路是死的**：H7 R2 的 **MT9M114 传感器不输出 JPEG**（§0.1），
`set_pixformat(sensor.JPEG)` 必然 `Sensor control failed`。**不要试着"换个 quality 蒙过去"。**
上面这段代码留着，是因为**换传感器模块之后它立刻可用**（见路线①b）。

---

### 路线 ①b 换一颗带 JPEG 的传感器模块（**唯一"又要硬件 JPEG、又要动板子"的路**）

**事实**：官方文档写明 H7 的传感器在**可插拔模块**上 —— *"The sensor sits on a removable module —
swap it for any of the other OpenMV camera modules (global shutter, thermal, higher resolution, etc.)"*
（[官方 v5.0.0 文档](https://docs.openmv.io/v5.0.0/openmvcam/quickref/openmv-cam-h7.html)）。

⇒ 换一颗**支持 JPEG 输出**的模块（如 OV5640 类），路线① 立刻成立：**JPEG 由传感器直出、软件压缩彻底消失**。

| 项 | 说明 |
|---|---|
| 收益 | **原理性根治**，且画质/分辨率反而更好；代码改动 = 路线①（一行 pixformat） |
| 代价 | 要买模块 + 等货；**必须确认模块与 H7 R2 固件匹配**（引脚/驱动） |
| 前提 | 【不确定】官方是否仍在售适配 H7 的 OV5640 模块 —— **先问厂商/代理再下单**，别照猜 |
| 判据 | 换完先跑 §1 探针：`HWJPEG <字节数> 320 240` 成功 → 走路线① |

> ⚠️ 本项目的硬件结论只认实测：**买之前先确认模块型号 + 能否退**，并把它写进 `docs/12_硬件清单与接线文档.md`。

---

### 路线 ② 不压缩：发原始灰度，PC 侧编码成 JPEG（**同样结构上彻底**）

**原理**：相机侧**完全不调用编码器**，只把传感器输出的灰度像素原样发出去；JPEG 由 PC 生成。
协议**已经支持**：`vigilens_link.py` 有 `TYPE_GRAY = 0x03` + `pack_gray(width, height, pixels)` / `unpack_gray(payload)`。
这也是 OpenMV 维护者对"如何在 PC 上实时拿帧"的官方答复：*"Just don't compress the image and write it as it is,
and on the other side read the expected frame size (w \\* h \\* bpp)"* —— 见
[Streaming Video Over USB is Slower than Streaming to IDE](https://forums.openmv.io/t/streaming-video-over-usb-is-slower-than-streaming-to-ide/5641)。

**相机侧改动**（`openmv_stream.py`）：
```python
    # 路线②：灰度直发，不压缩
    sensor.set_pixformat(sensor.GRAYSCALE)     # OV7725 支持灰度
    sensor.set_framesize(getattr(sensor, STREAM_FRAMESIZE))   # 建议 QQVGA（见下）
    ...
    img = sensor.snapshot()
    blob = link.pack_gray(img.width(), img.height(), img.to_bytes())
    mtype = link.TYPE_GRAY
```

**带宽（按实测 ~258 KB/s 折算，【推测】，需实测确认）**：

| 分辨率 | 灰度单帧 | 折算帧率 | 用途 |
|---|---|---|---|
| QQVGA 160×120 | **19200 B** | **~13 fps** | ✅ 网页画面够用 |
| QVGA 320×240 | 76800 B | ~3.4 fps | 只够指标，画面很卡 |

**PC 侧改动**（`metrics/scripts/omv_stream_bridge.ps1`）：收到 `TYPE_GRAY` 后自己编成 JPEG 再 `POST /api/frame`。
- 为什么在 PowerShell 里做：**这样不用碰 B 线的 `backend/api.py`**（目录归属，`AGENTS.md` §5）；
- 怎么做：`Add-Type -AssemblyName System.Drawing` → `New-Object System.Drawing.Bitmap($w,$h,[System.Drawing.Imaging.PixelFormat]::Format24bppRgb)`
  → `LockBits` 写入 BGR → `Save($ms, [System.Drawing.Imaging.ImageFormat]::Jpeg)`；
- ⚠️ 桥接的 `iter`/解析已经由 `Get-OMVFramesFromBytes` 统一，加一个 `Type -eq 0x03` 的分支即可（**别忘了给它补自检用例**）。

**代价**：网页画面变成**小尺寸灰度**（QQVGA）；桥接多 ~30 行。**收益**：相机侧再也没有"要一大块连续内存"的调用。

---

### 路线 ③ 立刻能用：QQVGA + 双帧缓冲（**已验证部分成功，但不是原理性根治**）

**原理**：把需求压到最小 + 让"编码当前帧"和"DMA 填下一帧"分开，编码器不再和锁定中的帧缓冲抢连续块。
维护者在同一帖里也指出解决这类问题的正路是**双缓冲**（*"You need double buffering"*）。

```powershell
# 只换参数，零代码改动：分辨率 QQVGA（帧缓冲 38400 B）+ 质量回到 80
Send-OMVStreamer -Framesize QQVGA -Quality 80
Send-OMVFramesToApi -TotalSeconds 600 -ApiBase http://127.0.0.1:8031 -BurstSeconds 0.25 -SaveMax 0
```
若还要更稳，再在 `stream()` 里加一行 `sensor.set_framebuffers(2)`（QQVGA 双缓冲共 76800 B，QVGA 双缓冲 307200 B 会爆）。

**为什么顺带把 `-BurstSeconds` 从 1.0 改到 0.25**：这与 BUG-027 是**两个**独立问题 ——
1.0 s 攒批导致"投递空档可达 3 s 以上"（实测 `age_s` 出现过 3.32 s），而前端过期线是 `max(1.5, 3.0/video_push_hz) = 1.5 s`
（`backend/api.py:274`），超过就隐藏画面 → **相机好着的时候画面也在闪**。缩小攒批窗口能同时压掉"闪"。

**代价**：画质 160×120（放大后偏糊）。**定位**：**过渡手段**，不要当修好了（见 §4 的"不算修复"）。

---

### 路线 ④ 规避：相机侧不发图（**对"这一类 bug"的完全规避**）

`openmv_stream.py` 已有 `MODE="stats"`（`link.pack_stats`，~44 B/帧）：**不产生任何图像**，因此**不存在压缩**。
代价是网页没有画面，只有指标。这正是 `AGENTS.md` §7.7 对 H7 的定位（**降规格采集 + 人脸检测目标**，不是契约像素源）。
**如果明天的目标是"把指标链路做稳"，这条是成本最低、最不可能翻车的。**

## 3. 验收方法（**必须可复现，且必须跑够时间**）

### 3.1 客观判据：连续 5 分钟，记录"最大投递空档"

```powershell
$api = "http://127.0.0.1:8031"
$maxAge = 0; $n = 0; $fresh = 0
$t0 = Get-Date
while (((Get-Date) - $t0).TotalSeconds -lt 300) {
    Start-Sleep -Milliseconds 500
    try { $a = (Invoke-RestMethod "$api/api/video_status").age_s } catch { continue }
    $n++
    if ($null -ne $a) { if ($a -gt $maxAge) { $maxAge = $a }; if ($a -lt 1.5) { $fresh++ } }
}
"样本 {0} 个；最大 age = {1:N2}s；画面可见占比 = {2:N1}%" -f $n, $maxAge, (100.0 * $fresh / $n)
```

| 路线 | 通过标准 |
|---|---|
| ① / ②（原理性根治） | 300 s 内 **`Compression Failed!` 一次都不出现**；相机侧转录里没有 Traceback；`frames=` 持续增长 |
| ③（过渡） | 300 s 内 **可见占比 ≥ 95%**、**最大 age < 3 s**；仍允许偶发重启，但必须**记下**重启次数与时刻 |
| ④（规避） | `frames=`（STATS）持续增长；不出现任何图像相关报错 |

## 4. 明确**不算**修复的做法（防止明天走弯路）

| ❌ 不要 | 为什么 |
|---|---|
| 只把 quality 80→50 就宣布修好 | 实测只是把窗口拉长（0 帧 → 353 帧），**之后照样失败**；根因（连续内存）没动 |
| 放宽前端的 1.5 s 过期线来"让画面不闪" | 那会破坏"**不显示冻结旧帧**"的正确性承诺，`check_video_bypass.py` 的 **T6** 就是钉它的 |
| 靠监护脚本无限重启当解决方案 | `omv_camera_demo.ps1` 是**可用性兜底**，不是修复；重启时还会 `Ctrl-D` 软复位，可能**加剧碎片** |
