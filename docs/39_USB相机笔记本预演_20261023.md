# 39 · USB 相机笔记本预演（2026-10-23）

> **背景**：`docs/37` 定了"USB UVC 720p60 MJPG"路线，W1（相机验收工具）必须最先做，
> 但**相机还没到货**。本轮用**本机内置相机**先把工具与"720p 口径"跑一遍，
> 目的是把"等相机到了才发现工具不对"的返工提前消掉。
>
> **本轮结论一句话**：工具与 720p 端到端链路都跑通了（工具自检 21/21、`check_all` 工具自检 16/16），
> 但**这颗内置相机只到 720p30**，所以 **M0 的三条判据一条都没过——不是失败，是没法判定**。
> 另外真机跑出一个会被静默忽略的缺陷 ⇒ 已立 [BUG-038](16_测试问题台账.md#bug-038) 并修掉。

**证据等级**：本文所有数字都是 2026-10-23 本机真实运行输出，标【已验证】；
凡"相机到货后才能测"的一律标【不确定】。**没有外推、没有估算值冒充实测。**

## 2. 模式矩阵【已验证】

请求 → 实际协商结果（每档先丢掉 6 帧再量 45 帧）：

| 请求 | 协商回来 | 实测 fps | 结论 |
|---|---|---|---|
| 1280×720@60 | **1280×720@30** | 30.14 | **60 拿不到** |
| 1280×720@30 | 1280×720@30 | 30.25 | 正常 |
| 1920×1080@60 / @30 | **1280×720@30** | 29.9 / 30.0 | 1080p 请求被回退 |
| 640×480@60 / @30 | 640×480@30 | 29.6 / 30.4 | 低分辨率**也不给 60** |
| 848×480@30 | **960×540@30** | 30.15 | MSMF 会自己挑最近档位（**请求值 ≠ 实际值**） |
| `CAP_PROP_FOURCC` 读回 | `0x00000016` | — | **MSMF 不暴露 fourcc**，无法用 OpenCV 判断是 MJPG 还是 NV12/YUY2 |

**三条必须说清的话**：

1. 【已验证】这颗相机的**能力上界是 1280×720@30**（帧率在所有分辨率下都锁 30）。
2. 【不确定】**它到底支不支持 MJPG**：Windows/MSMF 既不报 fourcc 也不给模式表，
   所以本机**无法判定**——`docs/37` 的 M0 判据必须在 **Linux/V4L2（板上）** 上重跑，
   这也是工具里把"证据源"分成 `v4l2` 与 `opencv-negotiation` 两种的原因。
3. 【已验证】**不能**把这次的结论写成"该相机不支持 720p60"，只能写"用 OpenCV/MSMF 协商不到"。

## 3. 10 s 帧率与抖动【已验证】

```
1280x720@30.0  抓到 300 帧 / 9.97 s
到达帧率 29.98 fps；间隔 p50 31.2 ms / p95 62.5 ms / max 94.39 ms；丢帧估算 0.0
```

- 30 fps 下**到达帧率稳定**（29.98，丢帧 0）。
- 但 **p95 = 62.5 ms ≈ 2 × p50**：约 5% 的帧间隔恰好是两帧的时间，
  说明存在**周期性单帧停顿**（MSMF 取帧/缓冲批处理），不是均匀抖动。
- 这个形态在 30 fps 下可以接受；**在 60 fps 下它会变成"每 20 帧掉一拍"**——
  而 `docs/37` R3 的判据正是抖动 p95/max。**相机到货后这一项必须重测，不能拿本机数字替代。**

## 4. 解码基准【已验证，但**只能当工具预演**】

```
输入是代理 JPEG：1280x720，q=85，编码器=cv2 自带（不是相机编码器）
帧数 200，平均 91.8 KB/帧，模式 color
单线程     p50 2.78 ms  p95 6.78 ms
2 线程帧级并行  3.07 ms/帧（墙钟摊薄）
ROI-only   未测：libjpeg 的 jpeg_skip_scanlines / crop 解码在 Python 绑定里没有暴露
→ 最快档 3.07 ms/帧 vs 预算 16.7 ms：✅ 达标（⚠️ 本机 CPU ≠ A9）
```

三个值得记账的点：

1. **代理输入的局限**：拿不到相机真实 MJPG 字节（第 2 节），所以这 200 帧是
   "相机真实画面 + cv2 编码"得来的。帧尺寸/内容真，**码率行为不真**（相机是 VBR，且可能锁不住）。
   最可信的输入是 `--mjpg-dump`（相机 dump 的真流），这条路径工具已实现但**本轮无素材**。
2. **双线程没有收益**（3.07 vs 2.78 ms/帧，反而更慢）：
   720p 解码在本机是**内存带宽/缓存**受限，不是核数受限。
   ⇒ `docs/37` §6.1 里"双核帧级并行能救回来"这个假设，**在 A9 上也要实测**，不能照搬。
3. **ROI-only 在 Python 侧没有**：`jpeg_skip_scanlines` 是 libjpeg 的 C API，
   cv2/PIL 都没暴露。板上要测，得写 C 调 `tjDecompressWithROI`（libjpeg-turbo）或用
   `jpeg_skip_scanlines` + `jpeg_read_scanlines` 手动跳。**工具里显式返回 `null` + 原因，不编数。**

## 5. 720p 端到端预演（`run_pipeline.py --source 0`）【已验证】

这是本轮**最有价值**的一条：它证明"1280×720 的帧"能走完 A 线现有链路，而不是只能跑 640×480。

```
帧源   : camera#0  30.0fps
处理帧数  : 300（逻辑时长 10.0s，墙上耗时 10.27s）
关键点来源: mediapipe
状态分布  : adjust_posture=299  fatigue_risk=1
末帧质量  : overall 0.73 (light 0.85 / motion 0.00)
```

- **MediaPipe 真跑**（`landmark_source=mediapipe`，不是 stub），720p 帧上 300 帧用了 10.27 s
  ⇒ 笔记本端到端 ≈ **29.2 fps**（相机 30 fps 上限内没有拖后腿）。
- **坐标没有被 640 截断**：唯一可见帧的 `bbox = [337, 135, 122, 104]`（`x+w=459`、`y+h=239`），
  在 1280×720 里合法 ⇒ `image_size()` 那套"用当帧真实尺寸"的修法（BUG-008 的一半）**在 720p 上成立**。
- ⚠️ **但画面里没有人脸**：`face.visible` 在 301 条记录里只有 1 条非零（1/301），
  状态全部落在 `adjust_posture`（"人脸可见率 0.00 低于下限 0.70"）。
  所以这次运行**不能**作为任何算法结果的证据（`docs/05` 铁律 1），只能作为**链路**证据。
  重测方式：人坐正、正对镜头、室内正常光照，再跑一次同样的命令。

## 6. 真机踩到的缺陷：朝向探测 1 帧误检就翻转整段【已验证】⇒ BUG-038（已修）

同一次运行的这一行日志：

```
方向   : 顺时针旋转 180°（探测 8 帧，各角度检出帧数 {0: 0, 90: 0, 180: 1, 270: 0}）
```

- **8 帧里只有 1 帧**在 180° 检出"人脸"（而整段 300 帧只有 1 帧可见人脸 ⇒ 画面里根本没有人）。
- `choose_rotation()` 原来的规则是"命中数最多者胜、并列取 0"，**没有最小命中数**，
  于是**一帧误检 = 整段 300 帧被转 180°**。
- 后果不是崩溃，是**静默错**：日志只多一行"顺时针旋转 180°"，看起来完全正常，
  而 ROI/姿态/rPPG 全部建立在翻转后的图上。
- 修法：`min_hits = max(2, 探测帧数 // 4)`，非 0 角度证据不足就按"不转"处理（0 不需要命中数）。
  新增两条测试钉住两个方向：
  `test_choose_rotation_ignores_a_single_lucky_hit`（1 帧不翻）、
  `test_choose_rotation_accepts_two_agreeing_hits`（2 帧一致就翻）。
- 【已验证】`pytest backend/tests/test_orientation.py -q` → **17 passed**；`pytest -q` → **184 passed**（原 182，+2）。

## 9. 相机到货后的验收动作（按顺序，一步一判据）

1. **插上就跑** `check_uvc_camera.py`：`v4l2-ctl` 真表里必须出现
   `MJPG 1280x720 [60.000 fps]`；**没有就当场退货**（`docs/37` §3 硬性）。
2. `--capture 10`：`fps ≥ 55`、丢帧 ≤1、`p95 ≤ 2×p50`（抖动判据）。
3. `--list-ctrls`：`exposure_auto_manual` / `white_balance_auto` / `gain` 全部**可写**。
4. `--bench-decode --mjpg-dump dump.mjpg`：**三档逐档 <16.7 ms**（笔记本这关先过）。
5. 静止场景 `--bench-encode-noise` 10 s：0.5~3 Hz **没有** ≥8× 的离散峰（R18）。
6. 畸变 ≤5%（标定板）——这一项工具还没做，属于 L 级补充项。

> 板上（A9）还要重跑 2) 和 4)，且要把 ROI-only 用 C/libjpeg-turbo 实现出来。
> **笔记本的数字永远只是"工具与图像尺寸"的预演，不是 A9 的结论。**

## 11. W2 真机跑出来的两个数（**给排期用**，不是算法结论）

`run_pipeline.py --source uvc:0`（720p30 源，MediaPipe 真推理）：

| 命令 | 输入时长 | 输出帧数 | 墙上耗时 | 结论 |
|---|---|---|---|---|
| `--seconds 8`（画面里有人脸） | 8.0 s | 240 | 11.75 s | **≈0.68× 实时**（管不住 30 fps 的输入） |
| `--seconds 4`（同上） | 4.0 s | 120 | 7.48 s | **≈0.54× 实时**（启动开销占比大） |
| `--seconds 10`（画面里没人脸，见 §5） | 10.0 s | 300 | 10.27 s | ≈0.97× 实时 |

> 差别在 MediaPipe：**检出人脸时每帧贵得多**，没人脸时几乎白跑。
> 这不是"720p 太重"，而是"CPU 上的人脸模型还没优化"—— 但它直接决定 W3 的形态：
> 板上（A9 双核）大概率更慢，所以 **W3 的"实时"必须是"丢帧不阻塞"而非"追上 30 fps"**。
> 【推测】此处不外推板上性能，A9 单核实测要等 W7。
