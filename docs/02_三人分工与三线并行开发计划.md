# 三人分工与三线并行开发计划
## 无接触状态监测终端 · 项目初期 Demo 阶段

> 适用对象：三人小组（大二，AMD 3.3 自主选题初级组）
> 核心目标：**三个人三线并行、互不阻塞，且都能在不依靠 FPGA 板卡的前提下各自完成并测试自己的部分**，最后按冻结好的接口一次性拼装。
> **当前阶段首要任务：先搭"基础框架"（骨架），详见《04_基础框架搭建指南》；本计划回答"三个人怎么并行落地"。**

---

## 一、总原则：先冻结接口，再各自开发

三人并行的**最大敌人不是技术，而是"等别人先做完"**。解决办法只有一条：

> **第 0 天先把三条线之间的"数据契约"（接口）冻结下来，之后每个人只对着契约开发，不关心别人的内部实现。**

> **当前阶段（M0~M1）的目标不是"把算法做全"，而是先让一条"视频 → JSON → 网页"的 stub 链路端到端跑通**——模块可以是占位实现，但链路必须是通的。骨架细节见《04_基础框架搭建指南》。

三线分工一句话版：

| 线 | 角色 | 方向 | 难度 | 能否无硬件测试 | 无硬件测试方式 |
|---|---|---|---|---|---|
| **A 线** | 算法 / 后端 | Python 视觉 + 指标 + 规则 | ★★★★ 中高 | ✅ 可以 | USB 摄像头 / **视频回放** + 黄金标注 |
| **B 线** | 前端 / 可视化 | FastAPI + WebSocket + 网页 | ★★★ 中 | ✅ 可以 | **Mock 假数据源**驱动，不依赖 A |
| **C 线** | FPGA / 硬件 | HLS IP + 仿真 + Overlay | ★★★★★ 高 | ✅ 可以 | **C 仿真 + 黄金参考**，不依赖板卡 |

> 三条线的测试方式天然互斥：A 靠"回放视频"、B 靠"假数据"、C 靠"仿真"，**谁都不需要谁的代码，也不需要在初期碰板子**。

## 二、成员匹配建议（按难度与技能）

| 线 | 建议人选 | 需要的先备技能 | 一句话画像 |
|---|---|---|---|
| **C（FPGA，最难）** | 三人中**最愿意啃硬件/系统、最有耐心看文档**者 | C/C++ 基础 + 逻辑电路概念（Vivado/HLS 可现学，但学习曲线陡） | "能坐得住、不惧报错、会读 UG 手册" |
| **A（算法，中高）** | **Python 最熟**者 | Python + 基础 OpenCV/NumPy；人脸关键点可调库（MediaPipe） | "写代码快、会调参、愿意处理误检" |
| **B（前端，中）** | **设计感/细心**者，或想快速看到成果者 | 基础 HTML/JS + FastAPI 概念 | "能把界面做干净、把状态做全" |

> 若三人中**无人碰过 FPGA**：让 C 线在启动时就用官方 HLS 教学案例跑通第一个最小 IP，其余两条线照常推进。**因为 A+B 在 M1 就能合出一个完整软件 Demo，即使 C 线进度慢，团队始终有一个能演示的保底作品。**

## 三、三条线的详细任务

### 【A 线】算法与后端（Python 视觉）

**难度：★★★★（中高）。隐性工作量最大的是"误检调参"，不是写代码本身。**

**无硬件测试方式：** 用**视频回放**替代实时摄像头——录制 4 段标准视频（静止、正常眨眼、打哈欠、转头/遮挡），用脚本逐帧读入并输出指标，与人工标注对比。全程不碰板卡。

**任务清单（按可独立验证拆解）：**

| 序号 | 任务 | 产出 | 独立验收标准 |
|---|---|---|---|
| A1 | 摄像头/视频源读取 + 人脸框检测 | `capture.py` | 能逐帧读视频并画出人脸框 |
| A2 | 人脸关键点（眼睛/嘴部/头部）提取 | `face_landmark.py` | 输出 68/478 关键点并可视化 |
| A3 | EAR（眼睛纵横比）+ 眨眼状态机（OPEN→CLOSING→CLOSED→OPEN） | `behavior_metrics.py` | 对眨眼视频能正确计数，同视频重复运行结果一致 |
| A4 | PERCLOS（窗口内闭眼比例）+ 眨眼频率 | 同上 | 30 秒窗口数值稳定，与人工标注误差可接受 |
| A5 | MAR（嘴部纵横比）+ 打哈欠事件（时长去抖） | 同上 | 能区分打哈欠 vs 正常说话/张口 |
| A6 | 头部姿态（yaw/pitch/roll）+ 人脸可见率 | 同上 | 转头/出框时数值正确变化 |
| A7 | 运动质量 + 光照质量评分 | `quality.py` | 大幅晃动/变暗时评分下降 |
| A8 | 规则融合 + 可解释建议（"疲劳风险升高，建议休息"） | `decision.py` | 阈值写在 `config.yaml`，逻辑可解释 |
| A9 | 输出 JSON（按契约）+ CSV 日志 | `storage.py` | JSON 字段与契约**完全一致** |
| A10 | 黄金结果：对 4 段视频生成基准 CSV 并锁版本 | `data/golden/` | 后续任何改动不得破坏黄金结果 |

**A 线第一周里程碑：** 跑通"视频回放 → 关键点 → EAR/MAR/头姿 → JSON/CSV"，不接前端、不碰 FPGA。

---

### 【B 线】前端与可视化（FastAPI + WebSocket + 网页）

**难度：★★★（中）。门槛最低，但"把 UI 打磨精致"会持续消耗时间。**

**无硬件测试方式：** 用一个**内置 Mock 数据生成器**模拟 A 线的指标流（按契约 JSON 随机但合理地生成眨眼、PERCLOS、状态等），浏览器里直接看效果。**B 从第一天起就不需要等 A。**

**任务清单：**

| 序号 | 任务 | 产出 | 独立验收标准 |
|---|---|---|---|
| B1 | 搭 FastAPI 服务 + 契约样例数据 | `api.py` | `/api/status`、`/api/metrics`、`/api/events` 可访问 |
| B2 | Mock 数据生成器（模拟 A 线输出） | `mock.py` | 浏览器能连续看到"合理跳动"的假数据 |
| B3 | WebSocket 实时推送 | `websocket.py` | 每秒推送一次，断开有明确提示 |
| B4 | 页面骨架：视频占位区 + 指标卡 + 状态区 | `frontend/index.html` | 布局与方案第 5.2 节一致 |
| B5 | 趋势曲线（Chart.js/ECharts） | `frontend/` | 眨眼、PERCLOS、心率等曲线实时滚动 |
| B6 | 事件日志 + 状态机展示（正常/疲劳/请调整姿势/信号不可靠/连接中断） | 同上 | 六种状态都能演示且样式区分清晰 |
| B7 | 软硬件模式切换占位（"软件模式 / 硬件模式"标签） | 同上 | 为 C 线结果预留入口 |
| B8 | 深色仪表盘 UI 打磨 + 截图 | 同上 | 产出可直接用于报告的页面截图 |

**B 线第一周里程碑：** 用 **Mock 数据**在浏览器里看到一个完整、精致、六种状态齐全的仪表盘；等 A 线 JSON 就绪后，把 Mock 换成真实数据只需改一个数据源开关。

---

### 【C 线】FPGA 硬件（HLS IP + 仿真 + Overlay）

**难度：★★★★★（最高）。学习曲线最陡，但任务"里程碑驱动、可完全离线仿真验证"。**

**无硬件测试方式（关键）：** 每个 IP 都走"HLS C 仿真 → 与 Python 黄金参考比对 → 综合"，**全部在 Vivado HLS 里完成，不需要板卡**。板卡只在最后"Overlay 封装 + DMA 上板"阶段才用。

**任务清单：**

| 序号 | 任务 | 产出 | 独立验收标准 |
|---|---|---|---|
| C1 | 锁定 Vivado/Vitis 版本 + 跑通官方最小 HLS 例程 | 环境记录 | 能完成一次"仿真 + 综合"全流程 |
| C2 | 定义 IP 接口（AXI-Stream + 控制寄存器，写进 `interface.md`） | 接口文档 | 与 A/B 线的数据契约对齐 |
| C3 | `roi_statistic`：ROI 内像素累加/计数/均值 | `fpga/src/` | C 仿真与 Python 参考**逐点一致** |
| C4 | `motion_quality`：帧差总量 + 运动比例 | 同上 | 边界（全零/全满/单点变化）与随机输入都通过 |
| C5 | `fir_filter`：时间序列带通滤波 | 同上 | 与 NumPy 参考滤波结果一致（误差在容差内） |
| C6 | 每个 IP 写 testbench + 黄金参考（Python 版） | `fpga/sim/` | 生成可复现的比对报告 |
| C7 | C 综合：记录 LUT/FF/BRAM/DSP/时钟/WNS | `fpga/report/` | 无 ERROR，目标时钟下时序可收敛 |
| C8 | 封装 Overlay + Block Design + AXI DMA | `board/` | （此步起才需要板卡）加载成功、寄存器读写正常 |
| C9 | DMA 搬运 + 缓存一致性验证 | 同上 | 短数组回环测试无随机错误 |
| C10 | 软硬件一致性：同一输入，PL 结果 vs A 线软件结果比对 | 报告 | 主要指标差异在预设容差内 |

**C 线第一周里程碑：** 完成 `roi_statistic` 或 `motion_quality` 的 **C 仿真并出综合报告**——**这一步 100% 不需要板子**，等于把"能不能上板"的不确定性推迟到第 4 周以后。

## 四、接口契约（三线不互相阻塞的生命线）

> 本契约必须在第 0 天冻结并写入 `docs/interface.md`，之后谁改契约谁发公告。**这是"三线并行不干扰"的唯一技术保障。**

### 4.1 A → B：指标 JSON（WebSocket 推送）

```json
{
  "ts": 1710000000.123,
  "frame_id": 12345,
  "face": {
    "visible": 0.98,
    "bbox": [320, 180, 180, 220],
    "pose": {"yaw": -2.1, "pitch": 1.5, "roll": 0.3}
  },
  "behavior": {
    "ear_left": 0.28,
    "ear_right": 0.29,
    "blink_state": "OPEN",
    "blink_count": 14,
    "blink_rate_per_min": 18.2,
    "perclos": 0.06,
    "long_close_count": 0,
    "mar": 0.12,
    "yawn_count": 1
  },
  "vital": {
    "hr_bpm": null,
    "hr_conf": null,
    "rr_per_min": null,
    "rr_conf": null
  },
  "quality": {"light_score": 0.82, "motion_score": 0.05, "overall": 0.86},
  "status": "normal",
  "advice": "状态正常",
  "reason": "各项指标均在正常范围，信号质量良好"
}
```

- `status` 取值固定为：`normal` / `fatigue_risk` / `adjust_posture` / `unreliable` / `disconnected` / `done`。
- `vital.*` 允许为 `null`，前端必须能优雅处理"暂无心率"。
- **B 线的 Mock 与 A 线的真实输出必须完全符合本 schema**，否则集成时必然返工。

### 4.2 C 线 IP 接口（与 A 的对接点）

- `roi_statistic`：输入像素流 + ROI 坐标 → 输出 `{sum_r, sum_g, sum_b, count}`；**A 线用相同 ROI 坐标做 Python 版累加，作为黄金参考。**
- `motion_quality`：输入当前/上一帧灰度 → 输出 `{diff_total, motion_ratio}`；A 线用 OpenCV 帧差做黄金参考。
- `fir_filter`：输入时间序列 → 输出滤波序列；A 线用 NumPy 做黄金参考。
- 三者都要求：**输入数据格式、数值精度（如定点位宽）、输出顺序在 `interface.md` 里写死。**

> 核心思想：**C 线验证"硬件算得对"，靠的是 A 线提供的那份"软件黄金参考"，而不是等板卡。** 这样 C 线全程离线可测。

### 4.3 目录结构（英文命名，符合赛制）

```text
vigilens-pynq/          # 仓库根（= 工作目录；GitHub: huangder/vigilens-pynq）
├── frontend/          # B 线
├── backend/           # A 线
├── fpga/              # C 线：src/ sim/ report/
├── board/             # C 线后期：bitstream/ overlay/ bringup_check.py
├── data/              # A 线：raw/ annotations/ golden/
├── metrics/           # 三方共享：metrics.csv logs/ scripts/ evidence/
├── docs/              # 契约 interface.md、charter、llm_log/
├── skill/             # 通用 PYNQ Skill（加分项，见评估报告方向 6）
└── report/
```

## 五、里程碑与集成节奏

| 里程碑 | 时间 | 内容 | 谁 | 是否需要硬件 |
|---|---|---|---|---|
| **M0 冻结** | 第 0 天 | 冻结主场景、指标范围、**接口契约**、目录结构 | 全员 | 否 |
| **M1 基础框架跑通** | 第 1 周 | 三线各自把"自己的骨架"跑通：A 出"回放→JSON"（指标可为占位）；B 出"Mock→网页"；C 出"最小 IP 仿真+综合" | 三线独立 | 否 |
| **M2 软件合体** | 第 2 周 | A 的 JSON 接入 B 的网页（换数据源开关），形成**完整软件 Demo** | A + B | 否 |
| **M3 硬件接入** | 第 3~4 周 | C 的 Overlay 上板 + DMA 跑通，结果以"硬件模式"接入后端 | C 为主，A 配合比对 | **首次需要板卡** |

**关键设计：** 即使 C 线在 M3 前完全卡住，**M2 已经产出了一个可演示、可录视频的完整软件作品**；M3/M4 只是往上叠加"硬件加速对比"这一加分项。这保证了团队**任何时候都有一个保底作品**。

## 六、如何"不依靠硬件"完成 Demo 测试（核心说明）

1. **A 线用视频回放**：不需要 FPGA，甚至不需要 USB 摄像头（有则更好）。用手机录 4 段视频，逐帧读入即等于"实时输入"，可无限次重复、结果可复现。
2. **B 线用 Mock 数据**：不需要 A、不需要摄像头，一段假数据就能验证整条前端链路与 UI 状态。
3. **C 线用 HLS 仿真 + 黄金参考**：不需要板卡，Vivado HLS 的 C 仿真即可验证 IP 功能正确性；综合报告验证资源/时序。**板卡只用于最后"上板 + DMA"这一步。**
4. **集成点只有一个数据契约**：A 的 JSON 和 C 的"黄金参考比对"都以同一份 `interface.md` 为准，三方各自离线完成后，拼装是"换数据源"级别的操作，而非重写代码。

> 一句话：**三线各自用"回放 / Mock / 仿真"三套互不依赖的测试手段，把"必须碰硬件"压缩到最后一个里程碑。**

## 七、互不干扰的保障与风险预案

| 风险 | 表现 | 预案 |
|---|---|---|
| A 线进度慢，B 线干等 | 前端没数据 | B 线永远先接 Mock，不阻塞 |
| B 线没做状态处理 | A 的数据接进来前端崩 | 契约里 6 种 `status` 必须在 B1 阶段就全部支持 |
| C 线工具链第一次跑不通 | 综合/仿真报错卡壳 | C1 先跑官方最小例程；若卡死，M2 的软件 Demo 仍是保底 |
| A 线改了字段没通知 | 集成时字段对不上 | 契约冻结 + 任何改动须发公告并同步 `interface.md` |
| rPPG 做不稳拖累主线 | 时间被占 | rPPG 严格放最后，不影响 M2/M3 |
| 板卡到手晚/损坏 | 无法上板 | 用远程板卡（赛事方提供）或 C 线仿真结果先撑住，M4 延后但不致命 |

## 九、给三人的三条铁律

1. **只对契约开发，不对别人的代码开发。** 任何字段、任何接口先写进 `interface.md` 再动手。
2. **能离线验证的绝不等到上板。** 回放、Mock、仿真三件套是并行开发的生命线。
3. **任何"看起来能用"都不算完成。** 用黄金结果、重复运行一致性、可复现脚本来定义"完成"，而不是"我屏幕上跑了一下"。
