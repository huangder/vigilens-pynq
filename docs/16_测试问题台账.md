## 0. 工作流（**我们约定的固定模式，7 步**）

```
① 测试者发现现象
      ↓  按 §1 模板把"命令 + 原始输出 + 期望 vs 实际"贴给 AI
② AI 判定类别（按 docs/15 §1 三分类）
      ├─ 命中 docs/15 §4「预期行为白名单」 → 记"非缺陷"，不进卡片
      ├─ 缺素材/硬件/标定/会签            → 记"待前提"，不进缺陷卡片
      └─ 违反 docs/15 §3 的通过标准       → 缺陷，继续
③ AI 写「原因分析」，**必须**标注 【已验证】/【推测】/【不确定】
      ↓  信息不足时**不编原因**，改记为「待定位」并列出"还需要什么信息"
④ AI 落成卡片 → 追加到 §5（本文件）
      ↓
⑤ 你们上传 GitHub：**一张卡片 = 一个 issue**（规范见 §2）
      ↓
⑥ 分工修复；提交信息引用卡片 ID（`AGENTS.md` §10.1 的"怎么验证的"不许空）
      ↓
⑦ 按卡片的「验收方法」逐条验证 → 状态改「待验证」→ 复核通过后关闭
```

> ⚠️ **AI 的边界**：AI 只做**原因分析与归档**，**不替任何人拍板"这是不是缺陷"**，
> 也不代写 `report/llm_log/` 的协作记录（铁律 3）。

## 2. GitHub 落地规范（**为"分工修改"服务**）

| 项 | 规范 |
|---|---|
| **标题** | `[<线>][<级别>] <现象一句话>`，例：`[shared][P3] run_demo 横幅在合成源下与实际推送状态矛盾` |
| **Labels** | 线：`line:A` `line:B` `line:C` `line:shared` `line:repo`；类型：`type:bug` `type:doc` `type:hygiene` `type:compliance` `type:tbd` `type:assets`；级别：`sev:P0`~`sev:P3`；另可加 `needs:evidence`（证据不足） |
| **粒度** | **一张卡片 = 一个 issue**。多个问题不要塞进一个 issue（否则没法分工、没法关闭） |
| **正文** | 直接贴 §1 模板填好的内容；把「修复建议」与「验收方法」展开成 **GitHub checklist**（`- [ ]`） |
| **关联** | 契约类改动必须在正文写清"影响哪条线、需要谁配合"（`AGENTS.md` §4） |
| **提交信息** | `<线>: 修复 <ID> <一句话主题>`；"怎么验证的"贴复现命令 + 真实结果（`AGENTS.md` §10.1） |
| **关闭条件** | 「验收方法」全部勾选 **且** `check_all.py` 仍 `PASS 22 / FAIL 0`、`pytest` 仍 `78 passed`（只增不减） |

### BUG-001 `run_demo` 横幅在合成源下与实际推送状态矛盾

|---|---|
| 类型 | 缺陷 |

**现象**：用合成帧源跑 `run_demo` 时，工具横幅打印"旁路画面: http://…/video.mjpg"，但管线其实**已经把画面推送关掉了**，网页画面区是占位。

**复现步骤**

```powershell

python metrics/scripts/run_demo.py --source synthetic --seconds 25 --port 8012 `
  --csv metrics/logs/demo_syn.csv --json metrics/logs/demo_syn_last.json --no-open
```

**原始输出 / 证据**（2026-09-26 实测，两段来自同一次运行，**顺序就是这样**）

网页    : http://127.0.0.1:8012/
旁路画面: http://127.0.0.1:8012/video.mjpg          ← 横幅这样说
[1/3] 服务已就绪  http://127.0.0.1:8012
[3/3] 开始测量（Ctrl-C 可中断；服务会保持运行到退出）

### BUG-006 头姿 `roll` 基准偏 180°：**正立正面的人脸被判为 `roll≈±180°`**

| 字段 | 内容 |
|---|---|
| 类型 | 缺陷 |
| 严重度 | **P1**（污染契约可见的 `status` / `reason`） |
| 归属线 | **A** |
| 涉及文件 | `backend/face_landmark.py:264`~`286`（`_pose_from_landmarks`，模型定义在 L269~L273） |
| 关联契约 | `docs/15` **A5**（六态决策）、**E-1**（证据标准）；`docs/interface.md` §1 `face.pose` |
| 状态 | 待处理 |

**现象**：一个**正立、正面**的人脸，`pose.roll` 输出 ≈ **±175°~180°**（而不是 ≈0°），并被 `decision.py` 判成头姿异常。

**2026-09-26 量化（**规范素材 640×480 + mediapipe + 真实人脸**，证据 `metrics/evidence/2026-09-26_stage1_all_tests.md` §3/§5）**

```
状态分布: adjust_posture=618  fatigue_risk=7  normal=4  unreliable=1
          → 618/630 = 98.1% 的帧被判「头部偏离过大」，而人是正对镜头的
|yaw| ≈ 180° 的帧占比 : 507/629 = 80.6%
相邻帧 |Δyaw| 最大     : 359.0°      （>90° 的跳变 119 次）
pitch 逐帧符号翻转     : +41.17 / +40.54 / −40.02 / +39.87 / +40.11（帧 0~4）
```

⇒ **这条缺陷不是"数值不好看"，而是让整段测量 98% 不可用** —— 严重度维持 **P1**。

**复现步骤**（这一段是纯数值的已知答案校验，**不需要相机、不需要人脸视频**）

```powershell
. .\env.ps1
python -c @"
import numpy as np, cv2, math
model=np.array([[0,0,0],[0,-63.6,-12.5],[-43.3,32.7,-26],[43.3,32.7,-26],[-28.9,-28.9,-24.1],[28.9,-28.9,-24.1]],dtype='double')
w,h=1920,1080; focal=w
cam=np.array([[focal,0,w/2],[0,focal,h/2],[0,0,1]],dtype='double')
Rm=np.array([[1.,0,0],[0,-1.,0],[0,0,-1.]])          # Rx(180) = 图像里脸是正立的
t=np.array([[0.],[0.],[600.]])
img,_=cv2.projectPoints(model,Rm,t,cam,np.zeros((4,1)))
rvec=cv2.solvePnP(model,img,cam,np.zeros((4,1)),flags=cv2.SOLVEPNP_ITERATIVE)[1]
r=cv2.Rodrigues(rvec)[0]; sy=math.sqrt(r[0,0]**2+r[1,0]**2)
print('yaw  =', round(math.degrees(math.atan2(r[1,0],r[0,0])),2))
print('pitch=', round(math.degrees(math.atan2(-r[2,0],sy)),2))
print('roll =', round(math.degrees(math.atan2(r[2,1],r[2,2])),2))
"@
```

**原始输出 / 证据**（2026-09-26 实测）

```
投影后各点 y（越小越靠上）: [540.0, 739.4, 439.7, 439.7, 628.9, 628.9]
眼睛在鼻子上方? True   下巴在鼻子下方? True        ← 确认投影出来的确实是"正立的脸"
-> 这套代码解出来的姿态 (yaw,pitch,roll) = (0.0, 0.0, -180.0)
```

**期望**：正立、正面的人脸，`roll` 应 ≈ **0°**（契约里 `pose` 是给"头姿异常"判定用的，见 `config.yaml` 的 `pose_yaw_max_deg` / `pose_pitch_max_deg`）。
`docs/interface.md` §1 只写了 `pose` 是 `yaw`/`pitch`/`roll`（度），**没有写明基准** —— 这正是下面 §"附带问题"要澄清的点。

**原因分析**：
- **【已验证】基准/约定错误**：3D 模型点是 **Y 轴朝上**（眼睛 `Y=+32.7`、下巴 `Y=-63.6`），而 OpenCV 相机的 **Y 轴朝下**。
  因此"图像里正立的脸"对应的旋转是 **`Rx(180°)`**，而按本文件的 ZYX 分解
  （`roll = atan2(r21, r22)`，`r = diag(1,-1,-1)` ⇒ `r21=0, r22=-1`）**必然解出 `roll = 180°`**。
  ⇒ **`roll` 的零点偏了 180°**：正常正面脸永远显示在 ±180 附近。
- **【已验证】这不是"数学写错了"**：同款分解公式喂已知旋转能**精确还原**（已做已知答案校验：`(20,10,5)→(20.00,10.00,5.00)`、
  `(-15,25,-30)→(-15.00,25.00,-30.00)`、`(0,0,40)→(0,0,40)` 全部 OK）。
  错的是**模型坐标系约定**，不是公式。
- **【已验证】与真实数据吻合**：用户录制的 `blink.mp4` 里，媒体流给出的关键点每帧都是**正立**的
  （`forehead 209.8 < eye 416.2 < mouth 720.5 < chin 884.7`），但姿态输出的 `roll` 一直是 ±173°~±179°；
  且实测的真实面内倾斜只有 **≈4.6°**（两眼 y 差 28.6 px / x 跨度 358 px），
  而 `|roll|-180 ≈ 4~7°` —— **量级对得上，符号/零点错**。

**影响**：
1. `roll` 字段**完全不可用**（恒在 ±180 附近，看不出真实倾斜）；
2. `pitch` / `yaw` 也随之进入**错误分支**（见 BUG-007），
   直接导致用户在阶段一实测到的错误结论：`status = adjust_posture`、
   `reason = "头部 pitch = 48.1° 超出 ±25°"` —— **一张正面脸被判成头姿异常**；
3. `data/README.md` 里 `turn.mp4` 的验收标准是"**应触发** `adjust_posture`"，
   而现在**正面脸也触发** → 该验收标准失去判别力。

**修复建议**（需 A 线决定，二选一）：
1. **改模型坐标系**：把模型点统一到"相机系等价"的约定（等价于把模型 `Y`/`Z` 取反），
   使正立正面脸 → `(0,0,0)`；
2. **或在分解后做基准扣除**：对解出的旋转先乘 `Rx(180)` 的逆再分解；
   无论哪种，都要**同时**给 `pose` 的基准写进契约（见 BUG-008 的"契约需澄清"部分）。

**验收方法**：
- [ ] 上面那段**已知答案校验**中，"正立正面脸"输出 `roll ≈ 0 ± 1°`（而不是 ±180°）；
- [ ] 已知旋转校验仍全部 OK（不许为了修基准把分解弄坏）；
- [ ] 用 `data/raw/blink.mp4` 重跑：`pose.roll` 落在小角度区间，`status` **不再**因头姿误触发 `adjust_posture`；

### BUG-007 `solvePnP` 解出**负 Z 的镜像解**，且逐帧在 176° / −2° 两个分支间跳变

> 📌 **自我更正**：我在对话里最初把"`bbox` 超出 640×480"当成可疑现象 —— 经查**它是原生分辨率导致的**，

**影响**：任何按"640×480 空间"消费 `bbox` 的一方（B 线界面的框选叠加、C 线的 ROI 寄存器、将来的上板对拍）

**修复建议**：
1. **先澄清契约**（`docs/interface.md` §1 给 `bbox` 补一句坐标系定义），走 `contract:` 流程 + A/B 确认；
2. 按澄清结果二选一实现：A 线在 `capture.py` 里按契约尺寸缩放（或把"帧尺寸"加进契约帧/接口）；
3. 无论哪种，都补一个**回归用例**（例如：喂 1920×1080 输入，断言 `bbox` 落在契约空间内）。

**验收方法**：

**自洽性检查**：`770 帧 / 10 s = 77.0 fps`，而帧间隔均值 `12998 µs → 76.9 fps` —— **长跑这条路径内部自洽** ✅。
⇒ 所以**存疑的是矩阵那条路径**（或其口径）。

**🔴 追加证据：同一组合的帧率在不同运行之间就大幅波动**（从相机盘备份里又读到一次矩阵报告）

| 运行 | `GRAYSCALE / QQVGA / fb=1` | 样本数 / 窗口 | 备注 |
|---|---|---|---|
| 用户那次（回收） | **40.05 fps** | 81 帧 / 2.022 s | `interval_us_max 25001`、`jitter_us_std 246` |

一次 41.7 ms 的停顿在 2 秒里就是约 2%，但起始阶段的连续停顿会把 2 秒的平均明显拉低；
10 秒窗口把瞬态稀释掉，所以得到更接近真实能力的 77 fps。
（**【不确定】**仍需读 `_measure()` 确认它有没有丢弃起始帧/有没有等待稳定。）

**原因分析**：
- **【已验证】两条路径对同一组合的结论不一致**，且长跑路径内部自洽；
- **【不确定】矩阵为何偏低**：可能是 `_measure()` 用了不同的计时口径（例如包含传感器稳定时间、
  或用了滚动平均 `clock.fps()` 而不是"帧数 / 墙钟"）。**需要读 `_measure()` 的实现才能定性。**
- **【影响面】09-24 记录的 `RGB565/QVGA = 39.76 fps` 也来自矩阵路径** ⇒

**修复建议**：

T_QQVGA_q80  → 6601   free 314928      ← 成功
T_QVGA_q50   → 9337   free 312096      ← 成功

修好"注入时占着 16 KB 源码字符串"之后（`compile` → `del _src` → `gc.collect()` → `exec`），

**原因分析**：**【已验证】**与"压缩时需要一大块**连续**内存"有关 —— 同一次会话里 **QVGA+q80 必失败、QVGA+q50 成功、QQVGA+q80 成功**，

**【推测】**H7 可用堆只有 ~302 KB（`AGENTS.md` §7.7），QVGA RGB565 帧缓冲就要 153600 B，
再叠加多轮 `sensor.reset()` + 推流造成的堆碎片，`compress()` 就找不到连续块。
**【不确定】**为什么同一配置有时能跑几百帧、有时第 1 帧就失败（与上电/复位历史有关，未见稳定规律）。

> 🔴 **2026-09-27 补：硬件层面的根因（这条把本卡的定性钉死了）**
> 板子是 **OpenMV Cam H7 R2**，传感器是 **ON Semi MT9M114**（官方 v5.0.0 文档：*"the H7 with the **OV7725**
> and the H7 R2 with the **ON Semi MT9M114**"*）。**MT9M114 是 raw Bayer 传感器，本身不输出 JPEG** ——

- **【不确定】**真机上 `null` 的**逐帧**归因（是"无真峰"还是"fs_eff 校验失败"）需要把
  `estimate()` 的中间量打出来才能定；本机的受控实验已足以证明口径问题是**充分**成因之一。

**影响**：`docs/interface.md` §5.2 第 12 项（rPPG 端到端）无法验收；

**更危险的是**在其它帧率（如 13 fps 的相机档位、或回放视频）上会**输出错误但高置信度的数字**。

**修复建议**（三条路，需 A/C 一起拍板；**不要**只改其中一处）：
1. **按真实速率重采样**：PS 侧把 ROI 序列插值到 `fps_nominal`（改动最小、但引入插值伪影，需说明）；

   （**契约级改动**，必须走 §4 会签流程）；
3. **改 `estimate()` 的口径**：`fs_eff` 改用**墙上时间戳**（`frame.ts`）而不是 `frame_id` 差，

### BUG-033 `motion_quality` 片内"上一帧"缓存**放不下 480×270** → csim 挂死（RTL 越界）

| 字段 | 内容 |
|---|---|
| 类型 | **缺陷（静默错）** |
| 严重度 | **P1** |
| 归属线 | **C** |
| 涉及文件 | `fpga/src/motion_quality_cap.h`（新，容量唯一来源）、`fpga/src/motion_quality.cpp`、`fpga/sim/tb_motion_quality.cpp` |
| 关联契约 | `docs/interface.md` §3.3（`motion_quality` 句柄）/ §0 v1.5 档位（待会签） |
| 状态 | ✅ **已修**（2026-10-01，C 线） |

**现象**：v1.5 档位（480×270 = 129600 像素）下，`motion_quality` 的 **csim 编译完成后不再前进**：
`csim.exe` 已生成、`temp0.log` 为 **0 字节**，日志 **>9 分钟零增长**；直接运行那个二进制同样**零输出**。
对照组：**384×288** 档位约 **1 秒**跑完。

**复现步骤**
```bat
call D:\Xilinx\2026.1\Vitis\settings64.bat
cd /d D:\Desktop\AMD\fpga
set "HLS_IP=motion_quality"
set "HLS_COMPONENT=component_u1_mq720full"
set "VIGILENS_TIER=720p60"
vitis-run --mode hls --tcl run_hls.tcl
rem 旧容量（384×288）下：csim 编译完成（15:57:04 生成 csim.exe、temp0.log 0 字节）后 >9 分钟零输出
```

**原始输出 / 证据**
```
# 旧容量：RTL 里那块 ram 只有 110592 深，而地址口是 17 bit（可寻址到 131071）
component_u1_mq720full/hls/syn/verilog/..._prev_buf_RAM_2P_BRAM_1R1W.v
  parameter AddressWidth = 17;
  parameter AddressRange = 110592;
  (* ram_style = "block" *) reg [DataWidth-1:0] ram[0:AddressRange-1];

# 旧容量 csynth
| prev_buf_U | ram_2p | | 64 | | N | pragma | prev_buf | bram | 1 | 8, 110592, 1 |

# 而数据要的是 480x270
fpga/sim/data_motion_720p60/meta.txt -> out_width=480 out_height=270 gray_bytes=129600

# 修后（component_u1_mq720full_after）
| prev_buf_U | ram_2p | | 64 | | N | pragma | prev_buf | bram | 1 | 8, 129600, 1 |
  parameter AddressRange = 129600;
meta     : work 480x270 (RGB in 1280x720), 10 frames, gray_bytes=129600, motion_thresh=16, 9 golden rows
Layer 1: 6 passed, 0 failed
Layer 2: 9 passed, 0 failed  (stream header errors: 0)
==== RESULT: PASS ====
INFO: [COSIM 212-1000] *** C/RTL co-simulation finished: PASS ***
```

**期望**：按 `docs/interface.md` §0 的 v1.5 三档（384×288 / 480×270 / 480×270），
`motion_quality` 在**每一档**都要 csim/csynth/cosim 通过；工作尺寸超过片内容量时必须**响亮失败**。

**原因分析**
- 【已验证】容量宏写死 `MOTION_MAX_W/H = 384/288` ⇒ 数组 **110592** 格；
- 【已验证】v1.5 最大档 **480×270 = 129600** 像素，**越界 19008 格**；
- 【已验证】RTL 的 `ram` 深度就是 110592，而地址口 17 bit ⇒ `i ≥ 110592` 的读/写在 RTL 语义上越界
  （读出 X、写入被丢弃）；
- 【推测】csim 挂死的**具体位置**取决于 BSS 布局（`fid` 就紧跟在 `prev_buf` 后面），
  **换个编译器、加一个变量，症状就会变** —— 这正是"静默错"最难查的地方。
- ⚠️ **上一轮把这条误判成"计算量问题"**（`docs/26` §3 U1 原文），并因此没去查代码。

**影响**：旧档（384×288）不受影响 ⇒ 既有 7 个 IP 的结论**仍然成立**；
但 **v1.5 的两档对 `motion_quality` 完全不可用**，且症状是"跑不动"，极易被当成算力/环境问题。

**修复建议**：容量抽到 `fpga/src/motion_quality_cap.h`（IP 与 tb **共用一份**，照 `fir_coeffs_q15.h` 的写法），
取最大档 480×270 = 129600（**≤ 2¹⁷ ⇒ BRAM 台阶不跨，仍是 64 个**）；
测试台加**容量硬校验**，越界时打印 `FATAL: ... EXCEEDS on-chip capacity ...` 并 `RESULT: FAIL`。

**验收方法**
- [x] 480×270：csim 6/6 + 9/9、csynth 64 BRAM18 / LUT 1501 / FF 1158 / DSP 1 / Fmax 140.05 MHz、cosim PASS
- [x] 640×480 档**无回归**：csim + cosim PASS（263 s）
- [x] 1080p45 档（同为 480×270）：csim PASS
- [x] 证据归档：`fpga/report/c7_sim_closed_loop_20261001.md` §2 + `fpga/report/logs/2026-10-01_*`

### BUG-034 `run_hls.tcl` 的 `ROI_DATA_DIR` 不可用时**静默回退**到默认档位数据

| 字段 | 内容 |
|---|---|
| 类型 | **缺陷（静默错）** |
| 严重度 | **P1** |
| 归属线 | **C** |
| 涉及文件 | `fpga/run_hls.tcl`（数据目录定位段） |
| 关联契约 | 无（脚本层）；影响所有"按档位各有一套黄金参考"的结论 |
| 状态 | ✅ **已修**（2026-10-01，C 线） |

**现象**：命令行显式把 `ROI_DATA_DIR` 指到 720p60 的数据目录，日志却显示它跑了**另一个档位**，
且**没有任何警告**：

```
INFO: data dir  = D:/Desktop/AMD/fpga/sim/data_motion        <- 640x480 档
meta     : work 384x288 (RGB in 640x480), 10 frames, gray_bytes=110592, motion_thresh=16, 9 golden rows
```

**后果**：一次"@720p 全尺寸 cosim"的结论被**张冠李戴**（本轮真实发生过，见 BUG-033 的取证过程）。

**复现步骤**
```bat
call D:\Xilinx\2026.1\Vitis\settings64.bat
cd /d D:\Desktop\AMD\fpga
set "HLS_IP=motion_quality"
set "ROI_DATA_DIR=D:\Desktop\AMD\fpga\sim\data_motion_720p60"
rem 旧脚本 + 该目录里【还没有】golden_motion.csv 时：
vitis-run --mode hls --tcl run_hls.tcl
rem -> INFO: data dir = .../sim/data_motion （静默换了档位）
```

**原始输出 / 证据**
```
# 旧逻辑（commit 2ada236，run_hls.tcl 第 141-156 行）把 ROI_DATA_DIR 当"候选之一"：
#   目录里没有 golden_* 就静默跳到下一个候选（候选 3 = [pwd]/sim/data_motion）
# A/B 反证：数据就位之后，同一段旧逻辑【能】正确选中 —— 所以错在"降级不报错"，不在候选匹配
PROBE: ROI_DATA_DIR = 'D:\Desktop\AMD\fpga\sim\data_motion_720p60'
PROBE: candidate 'D:/Desktop/AMD/fpga/sim/data_motion_720p60'  golden_motion.csv exists = 1
PROBE: CHOSEN = 'D:/Desktop/AMD/fpga/sim/data_motion_720p60'

# 修后（同一条 cmd 调用形状）
INFO: ROI_DATA_DIR -> D:/Desktop/AMD/fpga/sim/data_motion_720p60  (explicit, verified)
meta     : work 480x270 (RGB in 1280x720), 10 frames, gray_bytes=129600, ...
==== RESULT: PASS ====
```

**期望**：**显式指定的东西一旦不可用，就必须报错退出**，不能悄悄换成另一个口径。
（测试台自己早已是这个约定："调用方显式指定目录 → 找不到就硬失败"。）

**原因分析**：【已验证】旧代码把 `ROI_DATA_DIR` 与"默认档位目录"并列成候选，
逐个测"目录里有没有 `golden_*.csv`"，第一个通过的就用 —— **显式意图与兜底策略混在同一个循环里**。
当时那个目录里确实还没有 `golden_motion.csv`（会话开始时 `git status` 里没有该目录的未跟踪文件、
`git ls-files fpga/sim` 也只有它的 `README.md`），于是静默落到候选 3。

**影响**：任何"按档位/按数据集"跑出来的结论都可能**跑的不是你以为的那份数据**；
而且日志里那行 `INFO: data dir = ...` 极易被忽略。

**修复建议**：把两条路分开 —— ① `ROI_DATA_DIR` 设置了就必须可用，否则 `exit 1` 并打印期望文件名，
可用时打印 `INFO: ROI_DATA_DIR -> <dir>  (explicit, verified)`；
② 没设时按默认档位找，并**打印选中的目录**（不再只打一行没人看的 `data dir =`）。

**验收方法**
- [x] 显式指定且可用 ⇒ 打印 `(explicit, verified)` 且 `meta` 行是 480×270
- [x] 显式指定但不可用 ⇒ `exit 1`（不再静默回退）
- [x] 未指定 ⇒ 走默认档位并打印选中目录
- [x] 证据：`fpga/report/c7_sim_closed_loop_20261001.md` §5
