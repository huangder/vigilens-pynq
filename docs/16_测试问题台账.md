## 0. 工作流（**我们约定的固定模式，7 步**）

```
① 测试者发现现象
      ↓  按 §1 模板把"命令 + 原始输出 + 期望 vs 实际"贴给 AI
② AI 判定类别（按 docs/15 §1 三分类）
      ├─ 命中 docs/15 §4「预期行为白名单」 → 记"非缺陷"，不进卡片
      ├─ 缺素材/硬件/标定/会签            → 记"待前提"，不进缺陷卡片
      └─ 违反 docs/15 §3 的通过标准       → 缺陷，继续
③ AI 写「原因分析」，**必须**标注 【已验证】/【推测】/【不确定】
      ↓  信息不足时**不编原因**，改记为「待定位」并列出"还需要什么信息"
④ AI 落成卡片 → 追加到 §5（本文件）
      ↓
⑤ 你们上传 GitHub：**一张卡片 = 一个 issue**（规范见 §2）
      ↓
⑥ 分工修复；提交信息引用卡片 ID（`AGENTS.md` §10.1 的"怎么验证的"不许空）
      ↓
⑦ 按卡片的「验收方法」逐条验证 → 状态改「待验证」→ 复核通过后关闭
```

> ⚠️ **AI 的边界**：AI 只做**原因分析与归档**，**不替任何人拍板"这是不是缺陷"**，
> 也不代写 `report/llm_log/` 的协作记录（铁律 3）。

### BUG-001 `run_demo` 横幅在合成源下与实际推送状态矛盾

| 字段 | 内容 |
|---|---|
| 类型 | 缺陷 |
| 严重度 | **P3** |
| 归属线 | shared（`metrics/scripts/` 是共享脚本） |
| 涉及文件 | `metrics/scripts/run_demo.py:159`（对照 `backend/run_pipeline.py:229`~`234`） |
| 关联契约 | `docs/15` **E3**（预期行为白名单）、**B9** |
| 状态 | 待处理 |

**现象**：用合成帧源跑 `run_demo` 时，工具横幅打印"旁路画面: http://…/video.mjpg"，但管线其实**已经把画面推送关掉了**，网页画面区是占位。

**复现步骤**

```powershell
. .\env.ps1
python metrics/scripts/run_demo.py --source synthetic --seconds 25 --port 8012 `
  --csv metrics/logs/demo_syn.csv --json metrics/logs/demo_syn_last.json --no-open
```

**原始输出 / 证据**（2026-09-26 实测，两段来自同一次运行，**顺序就是这样**）

```
VigiLens 一键演示：图像采集 → 数据分析 → 网页显示
帧源    : synthetic
网页    : http://127.0.0.1:8012/
旁路画面: http://127.0.0.1:8012/video.mjpg          ← 横幅这样说
[1/3] 服务已就绪  http://127.0.0.1:8012
[3/3] 开始测量（Ctrl-C 可中断；服务会保持运行到退出）

[warn] 帧源是合成帧，没有真实像素 —— 已关闭 --push-video（网页会显示占位画面）。   ← 事实是这样
       要看真实画面请用真实视频或摄像头：--source <视频文件> 或 --source 0。
```

**期望**：终端里的画面状态描述**必须与实际一致**（按 `docs/15` E3：合成源下画面是占位）。

**原因分析**：
- **【已验证】时序原因**：`run_demo.py:159` 在**构造子进程命令之前**（`cmd_base` 在 L190、子进程在 L224 启动）就打印了横幅，
  而"是否推送画面"的最终决定发生在**子进程内部**（`run_pipeline.py:229`~`234`：`if synthetic_src: vpusher = None`）。
  ⇒ 横幅**在信息上不可能**知道这个决定。
- **【已验证】判定条件过窄**：该行只依据 `args.no_video` 一个条件（`'关闭（只显示占位网格）' if args.no_video else …`），
  没有把"帧源类型"纳入判断。
- **【已验证】同类问题不止一处**：`run_demo.py:247`~`248` 的收尾语同样只看 `args.no_video`。

**影响**：使用者会以为"画面已经推上去了"，于是去查前端、查 MJPEG、查端口 —— **排障方向被带偏**；
阶段一测试里这类误导会直接浪费半天。

**修复建议**（三选一，从简到全）：
1. 横幅按帧源类型分叉：`--source synthetic` 时直接打印"合成源无像素，画面推送将被自动关闭"；
2. 横幅**不再**自己宣布画面状态，改为只打印"画面状态以管线输出为准"，并保留子进程打印的那行；
3. 测量结束后**追加一行真实统计**（`旁路画面: 投递 N / 编码 M / 送达 K / 丢弃 D`，该数据管线已经在打印）。

**验收方法**：
- [ ] `--source synthetic` 运行时，终端里**不再出现**与实际相反的"能看画面"表述；
- [ ] `--source metrics/logs/_video_bypass_clip.avi` 运行时，仍能明确看到画面地址与实际投递统计；
- [ ] 两条都跑完后 `python metrics/scripts/check_all.py` 仍 `PASS 22 / FAIL 0`。

### BUG-002 横幅里的画面默认值是硬编码，未读 `config.yaml`

| 字段 | 内容 |
|---|---|
| 类型 | 缺陷 |

| 关联契约 | `docs/15` **G6**（阈值唯一来源是 `config.yaml`）、**B9** |

**现象**：横幅用 `args.video_hz or '8'`、`args.video_quality or 80`、`args.video_max_width or 640` 估算默认值。

**原始输出**

```
          （节奏/质量/最长边未指定的取 config.yaml：8 Hz / q80 / 最长边 640）
```

**期望**：显示的值必须**真的来自** `config.yaml`（`video_push_hz: 8.0`、`video_jpeg_quality: 80`、`video_max_width: 640`）。

**原因分析**：
- **【已验证】**代码里写死了 `'8'` / `80` / `640`，**没有调用** `backend/config.py` 的 `load_config()`。
- **【已验证，目前看不出问题】**今天这三个值与 `config.yaml` **恰好一致**，所以现在不会出错 ——

- 与 `AGENTS.md` 的硬性约束冲突：**"所有阈值的唯一来源是 `config.yaml`，代码里不许出现魔法数字"**。

**影响**：违反 G6；`config.yaml` 是三人共用文件，任何一次调整都会让横幅与事实脱节。

**修复建议**：改为从 `load_config()` 读这三个值（`run_demo` 已经是"透传"角色，读配置不改变它的职责）。

### BUG-006 头姿 `roll` 基准偏 180°：**正立正面的人脸被判为 `roll≈±180°`**

| 字段 | 内容 |
|---|---|
| 类型 | 缺陷 |
| 严重度 | **P1**（污染契约可见的 `status` / `reason`） |
| 归属线 | **A** |
| 涉及文件 | `backend/face_landmark.py:264`~`286`（`_pose_from_landmarks`，模型定义在 L269~L273） |
| 关联契约 | `docs/15` **A5**（六态决策）、**E-1**（证据标准）；`docs/interface.md` §1 `face.pose` |
| 状态 | 待处理 |

**现象**：一个**正立、正面**的人脸，`pose.roll` 输出 ≈ **±175°~180°**（而不是 ≈0°），并被 `decision.py` 判成头姿异常。

**2026-09-26 量化（**规范素材 640×480 + mediapipe + 真实人脸**，证据 `metrics/evidence/2026-09-26_stage1_all_tests.md` §3/§5）**

```
状态分布: adjust_posture=618  fatigue_risk=7  normal=4  unreliable=1
          → 618/630 = 98.1% 的帧被判「头部偏离过大」，而人是正对镜头的
|yaw| ≈ 180° 的帧占比 : 507/629 = 80.6%
相邻帧 |Δyaw| 最大     : 359.0°      （>90° 的跳变 119 次）
pitch 逐帧符号翻转     : +41.17 / +40.54 / −40.02 / +39.87 / +40.11（帧 0~4）
```

⇒ **这条缺陷不是"数值不好看"，而是让整段测量 98% 不可用** —— 严重度维持 **P1**。

**复现步骤**（这一段是纯数值的已知答案校验，**不需要相机、不需要人脸视频**）

```powershell
. .\env.ps1
python -c @"
import numpy as np, cv2, math
model=np.array([[0,0,0],[0,-63.6,-12.5],[-43.3,32.7,-26],[43.3,32.7,-26],[-28.9,-28.9,-24.1],[28.9,-28.9,-24.1]],dtype='double')
w,h=1920,1080; focal=w
cam=np.array([[focal,0,w/2],[0,focal,h/2],[0,0,1]],dtype='double')
Rm=np.array([[1.,0,0],[0,-1.,0],[0,0,-1.]])          # Rx(180) = 图像里脸是正立的
t=np.array([[0.],[0.],[600.]])
img,_=cv2.projectPoints(model,Rm,t,cam,np.zeros((4,1)))
rvec=cv2.solvePnP(model,img,cam,np.zeros((4,1)),flags=cv2.SOLVEPNP_ITERATIVE)[1]
r=cv2.Rodrigues(rvec)[0]; sy=math.sqrt(r[0,0]**2+r[1,0]**2)
print('yaw  =', round(math.degrees(math.atan2(r[1,0],r[0,0])),2))
print('pitch=', round(math.degrees(math.atan2(-r[2,0],sy)),2))
print('roll =', round(math.degrees(math.atan2(r[2,1],r[2,2])),2))
"@
```

**原始输出 / 证据**（2026-09-26 实测）

```
投影后各点 y（越小越靠上）: [540.0, 739.4, 439.7, 439.7, 628.9, 628.9]
眼睛在鼻子上方? True   下巴在鼻子下方? True        ← 确认投影出来的确实是"正立的脸"
-> 这套代码解出来的姿态 (yaw,pitch,roll) = (0.0, 0.0, -180.0)
```

**期望**：正立、正面的人脸，`roll` 应 ≈ **0°**（契约里 `pose` 是给"头姿异常"判定用的，见 `config.yaml` 的 `pose_yaw_max_deg` / `pose_pitch_max_deg`）。
`docs/interface.md` §1 只写了 `pose` 是 `yaw`/`pitch`/`roll`（度），**没有写明基准** —— 这正是下面 §"附带问题"要澄清的点。

**原因分析**：
- **【已验证】基准/约定错误**：3D 模型点是 **Y 轴朝上**（眼睛 `Y=+32.7`、下巴 `Y=-63.6`），而 OpenCV 相机的 **Y 轴朝下**。
  因此"图像里正立的脸"对应的旋转是 **`Rx(180°)`**，而按本文件的 ZYX 分解
  （`roll = atan2(r21, r22)`，`r = diag(1,-1,-1)` ⇒ `r21=0, r22=-1`）**必然解出 `roll = 180°`**。
  ⇒ **`roll` 的零点偏了 180°**：正常正面脸永远显示在 ±180 附近。
- **【已验证】这不是"数学写错了"**：同款分解公式喂已知旋转能**精确还原**（已做已知答案校验：`(20,10,5)→(20.00,10.00,5.00)`、
  `(-15,25,-30)→(-15.00,25.00,-30.00)`、`(0,0,40)→(0,0,40)` 全部 OK）。
  错的是**模型坐标系约定**，不是公式。
- **【已验证】与真实数据吻合**：用户录制的 `blink.mp4` 里，媒体流给出的关键点每帧都是**正立**的
  （`forehead 209.8 < eye 416.2 < mouth 720.5 < chin 884.7`），但姿态输出的 `roll` 一直是 ±173°~±179°；
  且实测的真实面内倾斜只有 **≈4.6°**（两眼 y 差 28.6 px / x 跨度 358 px），
  而 `|roll|-180 ≈ 4~7°` —— **量级对得上，符号/零点错**。

**影响**：
1. `roll` 字段**完全不可用**（恒在 ±180 附近，看不出真实倾斜）；
2. `pitch` / `yaw` 也随之进入**错误分支**（见 BUG-007），
   直接导致用户在阶段一实测到的错误结论：`status = adjust_posture`、
   `reason = "头部 pitch = 48.1° 超出 ±25°"` —— **一张正面脸被判成头姿异常**；
3. `data/README.md` 里 `turn.mp4` 的验收标准是"**应触发** `adjust_posture`"，
   而现在**正面脸也触发** → 该验收标准失去判别力。

**修复建议**（需 A 线决定，二选一）：
1. **改模型坐标系**：把模型点统一到"相机系等价"的约定（等价于把模型 `Y`/`Z` 取反），
   使正立正面脸 → `(0,0,0)`；
2. **或在分解后做基准扣除**：对解出的旋转先乘 `Rx(180)` 的逆再分解；
   无论哪种，都要**同时**给 `pose` 的基准写进契约（见 BUG-008 的"契约需澄清"部分）。

**验收方法**：
- [ ] 上面那段**已知答案校验**中，"正立正面脸"输出 `roll ≈ 0 ± 1°`（而不是 ±180°）；
- [ ] 已知旋转校验仍全部 OK（不许为了修基准把分解弄坏）；
- [ ] 用 `data/raw/blink.mp4` 重跑：`pose.roll` 落在小角度区间，`status` **不再**因头姿误触发 `adjust_posture`；
- [ ] 在 `data/README.md` 规定的 `turn.mp4` 上，转头时**仍能**触发 `adjust_posture`（避免"修过头"）；
- [ ] `pytest` **只增不减**（新增一个"正立正面 → roll≈0"的回归用例）。

> 📌 **自我更正**：我在对话里最初把"`bbox` 超出 640×480"当成可疑现象 —— 经查**它是原生分辨率导致的**，
> 不是坐标算错。真正的两个问题见下。

**期望**：契约 §0 冻结的图像尺寸是 **640×480 RGB888**；但契约 §1 对 `bbox` **只写了"单位像素、左上角原点"，

**原因分析**：

- **【不确定】**契约的**本意**是哪种：① `bbox` 必须始终在 640×480 空间（那么 A 线应**缩放**输入）；

**影响**：
1. 团队会为"要不要修"争论，而**没有依据可引**；
2. 真的风格问题（比如变量名打错拼写）**没人拦**；

**修复建议**：参数去掉 `Mandatory`、给默认值 `@()`，并在函数入口显式短路

### BUG-027 相机推流跑一阵后 `img.compress()` 抛 `OSError: Compression Failed!` → **整条流退出回 REPL**（"相机活着但串口 0 字节"）

| 字段 | 内容 |
|---|---|
| 类型 | 缺陷（相机侧 + 脚本鲁棒性） |
| 严重度 | **P1**（阶段二"相机→网页/指标"演示只能维持几十秒~几分钟） |
| 归属线 | C（相机侧）+ shared（`metrics/scripts/` 的监护） |
| 涉及文件 | `board/openmv/openmv_stream.py` 的 `stream()`（原第 249 行 `img.compress`）；`metrics/scripts/omv_stream_bridge.ps1`、`metrics/scripts/omv_camera_demo.ps1` |
| 关联契约 | `docs/15` **O4**；与 [BUG-020](#bug-020)（内存擦边→相机复位）、[TBD-004](#tbd-004) 同族；是 `AGENTS.md` §7.7"内存天花板"的又一证据 |
| 状态 | ⚠️ **已定位 + 缓解**（未根治） |

**现象**：相机侧推流跑一阵后，Camera 的 `img.compress(quality=80)` 抛 `OSError: Compression Failed!`，
**异常逃出 `while True` 循环 → 整条流结束回 REPL**。PC 侧看到的是"脚本启动横幅都打印了、之后一个字节都没有"。

**复现步骤**
```powershell
# 终端 1（服务）  python backend\api.py --no-mock --host 127.0.0.1 --port 8031
. .\metrics\scripts\omv_stream_bridge.ps1
Send-OMVStreamer                       # 默认 quality=80，注入成功、LINK_OK 1 12 2、MEM 302416
Send-OMVFramesToApi -TotalSeconds 100 -ApiBase http://127.0.0.1:8031 -SaveMax 0
```

**原始输出 / 证据**（相机串口原样回读）
```
[stream] 开始：jpeg=True usb=True QVGA roi=(0, 0, 640, 480)
[stream] 每约 1 秒打一行进度。让上位机跑 host_capture_test.py 收。
Traceback (most recent call last):
  File "<omv_stream>", line 382, in <module>
  File "<omv_stream>", line 354, in main
  File "<omv_stream>", line 249, in stream
OSError: Compression Failed!
>>>
```
同一时刻在 **REPL 里单独测**（同一台相机、同一会话，逐条一行行发）：
```
T_QVGA_q80   → Traceback ... OSError: Compression Failed!
T_QQVGA_q80  → 6601   free 314928      ← 成功
T_QVGA_q50   → 9337   free 312096      ← 成功
```
修好"注入时占着 16 KB 源码字符串"之后（`compile` → `del _src` → `gc.collect()` → `exec`），
`MEM 302416 → MEM2 311264`，一个 100 s 窗口里拿到了 **frames=353 / crc_bad=0**（~10 fps / 96 KB/s）——
也就是**从 0 帧变成 353 帧**，但**再往后仍会失败**（后续窗口缩到 ~10 s）。

**原因分析**：**【已验证】**与"压缩时需要一大块**连续**内存"有关 —— 同一次会话里 **QVGA+q80 必失败、QVGA+q50 成功、QQVGA+q80 成功**，
而失败与分辨率/质量（即输出大小与工作缓冲）强相关，与画面内容无关。
**【推测】**H7 可用堆只有 ~302 KB（`AGENTS.md` §7.7），QVGA RGB565 帧缓冲就要 153600 B，
再叠加多轮 `sensor.reset()` + 推流造成的堆碎片，`compress()` 就找不到连续块。
**【不确定】**为什么同一配置有时能跑几百帧、有时第 1 帧就失败（与上电/复位历史有关，未见稳定规律）。

> 🔴 **2026-09-27 补：硬件层面的根因（这条把本卡的定性钉死了）**
> 板子是 **OpenMV Cam H7 R2**，传感器是 **ON Semi MT9M114**（官方 v5.0.0 文档：*"the H7 with the **OV7725**
> and the H7 R2 with the **ON Semi MT9M114**"*）。**MT9M114 是 raw Bayer 传感器，本身不输出 JPEG** ——
> 所以 `set_pixformat(sensor.JPEG)` 必然 `Sensor control failed`（这也正是 [BUG-017](#bug-017) 的真正根因，
> **不是固件配错**）；**这块板子上"相机出 JPEG"只能靠软件压缩**，而软件压缩必然要一块大缓冲。
> ⇒ **BUG-027 不是偶发 bug，而是"这颗传感器 + 软件 JPEG"的固有矛盾**。
> 修法只有两类：**要么别在相机上压缩**（`docs/18` 路线②：发原始灰度、PC 侧编码 / 路线④：只发统计量），
> **要么换一颗带 JPEG 的模块**（`docs/18` 路线①b —— H7 的传感器是官方文档写明的**可插拔模块**）。
> 完整方案见 **[docs/18 相机推流修复方案](18_相机推流修复方案_BUG-027.md)**。

**影响**：① 阶段二演示与"相机→A 线指标"长跑**不可持续**；② PC 侧症状极易被误判成硬件/固件故障
（本轮先后误判为"相机流没起来""COM10 被占""需要拔插冷复位"）；③ 任何"相机长跑帧率"结论都必须写明**跑了多久**。

**修复建议**：
0. **明天开工先看 [docs/18 修复方案](18_相机推流修复方案_BUG-027.md)** —— 里面有 30 秒判定探针
   （拿 `sensor.get_id()`）、三条路线（① 传感器硬件 JPEG / ② 发原始灰度 PC 侧编码 / ③ QQVGA+双缓冲过渡）、
   验收判据与回滚步骤；**先跑探针再动手**。
1. **已做（缓解）**：`stream()` 里每帧先 `gc.collect()`；**单帧压缩失败只丢这一帧并计数，不再让整条流退出**（这是最重要的一条）；
2. **已做（配置）**：推流改用 `quality=50`（`omv_camera_demo.ps1` 默认值），并把 80 会失败的结论写在脚本头；
3. **已做（监护）**：`metrics/scripts/omv_camera_demo.ps1` 轮询 `/api/video_status`，画面一过期就自动重起相机流
   （**这是"画面过一会儿就没了"的可用答案**：不是前端 bug，是源断了）；
4. **待做（根治方向）**：换 `QQVGA`；或把压缩缓冲一次性预分配；或在每次推流前做一次**冷复位**（拔插）并接受人工介入。

**验收方法**：
- [x] 单帧压缩失败**不再**让相机流退出 REPL（实测：连续 150+ 帧失败仍在跑，并逐帧打印计数）；
- [x] `quality=50` 下 `frames=` 从 0 变成 353（100 s 窗口、`crc_bad=0`）；
- [ ] **连续 5 分钟** `frames=` 持续增长、不出现 `Compression Failed!`（**当前做不到，故此条未打勾**）；
- [ ] 若改动 `config.yaml` 的 `video_jpeg_quality` 或推流分辨率，必须同步更新本卡的实测数字（不许凭印象改）。
