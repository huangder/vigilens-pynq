#### 8.2.1 两次误判的教训（写下来以免再犯）

1. 我用 `vitis-run ... | Select-String ... | Select-Object -Last N` 看进度 ——

#### 8.2.2 长时 cosim 在本会话有**时长上限**（2026-10-01 实测）
同一套"**脱离工具调用、独立进程**"的跑法（`Start-Process -PassThru` + 写日志），结果按**耗时**分成两类：

| 时长 | 例子 | 结果 |
|---|---|---|
| **≤ ~2 分钟** | `roi_statistic`@640×480（1m40s）、`motion_quality`（52s）、`raw10_unpack`、`bayer_demosaic`、`rgb2gray`、`fir_filter` | ✅ **都跑完 PASS** |
| **≈ 10 分钟以上** | `frame_scale`（~21 min）、`roi_statistic`@1280×720 | ⚠️ `frame_scale` **跑完了**；`roi_statistic`@720p **两次都在 ~9 分钟后进程消失** |

`roi_statistic`@720p 那两次的日志都停在 UVM 包编译处（见下）：

```
Time Resolution for simulation is 1ps
Compiling package xil_defaultlib.$unit_sv_module_top_sv
Compiling package uvm.uvm_pkg          <- 停在这
```

即 **xsim 还在编译 UVM 包**、RTL 尚未开跑就断了；而 `frame_scale` 能跑完说明**"长"本身不是绝对的死亡条件**。

**但后来从日志尾部看到了真正的原因**：这个 cosim 的测试台含 **73 个事务**
（每个事务是一整帧 1280×720），日志实测跑到
```
// RTL Simulation : 0 / 73 [n/a] @ "125000"
```
—— 也就是**进度条才 0/73 就已经耗掉了整个存活窗口**。所以它是**本身就很长的作业**，
不是"卡住"、也不是死锁：同一套跑法下 `frame_scale`（**8 个事务**、流深度 921600）21 分钟跑完并 PASS。

⇒ **可复用的判据**：**cosim 耗时 ≈ 事务数 × 每事务像素数**。
选 cosim 数据时要先看 `// RTL Simulation : k / N` 里的 **N**：
`N≤10` 通常能在本会话跑完；`N` 到几十（如 73）就必须给足时间或用更小的向量。

⇒ **结论（不算定论）**：`roi_statistic`@720p 的 cosim **请放到完整权限终端**跑；
命令 = `set HLS_IP=roi_statistic` + `set HLS_EXEC=2` + `set ROI_DATA_DIR=D:\Desktop\AMD\_roi720`
（数据已生成好，见 `fpga/report/c6_*` §5.4）。
⚠️ 我**仍不**对"进程为什么恰好在那时消失"下断言 —— 本轮已经因为过早下结论错过两次。

#### 8.2.3 2026-10-01 深挖：RTL 协同仿真在本沙箱失败的**具体机理**（两道关卡，已定位）

> 🔴 本节把上一版"超预算 / 做不完"的说法**改掉**了。真实情况是：**这些 cosim 一直在推进**，
> 只是**在本会话里活不到终点**。我实测过三条 run 的进度：
> `_cosim_roi720p.log` 到 **40 / 73**、`_cosim_roi720p_b.log` 到 **33 / 73**，
> 而 `frame_scale`（8 事务、流深度 921600）**21 分钟跑完并 PASS**。
> ⇒ **不是算力不够，是会话对长时子进程的存活窗口有限。**

**关卡一：xsim 默认多线程在本机直接崩 —— 已找到确定的绕法 ✅（本轮最有价值的发现）**

`xelab` 默认 `Multi-threading is on. Using 22 slave threads`，随后 xsim 一启动就：
```
Exception at PC 0x00007FF9CFFF2165      <- xsimcrash.log，裸访问违例
ERROR: [Simtcl 6-50] Simulation engine failed to start:
       The Simulation shut down unexpectedly during initialization.
```
**绕法：重建快照时加 `-mt off`**（`-mt` 的合法值是 `auto|off|>1`，**`-mt 1` 会报错**）：
```
xelab <...> -mt off -s <snapshot>
xsim <snapshot> -tclbatch <tb>.tcl
```
加完输出变成 `Turned off multi-threading.`，**引擎正常起来、跑进 UVM 阶段、事务开始推进**。
📌 **这条对任何在本机跑 HLS cosim 的人都有用**：若报
`simulation shut down unexpectedly during initialization`，**先试 `-mt off`**。
⚠️ 但 `run_hls.tcl` 没有把 `-mt` 透传出去的口子，所以走 `vitis-run` 这条路**默认仍是崩的**。

**关卡二：测试向量在 `fpga/` 下生成会撞写权限（部分已绕过）**

cosim 需要**先由 C 测试台把 HDL 测试向量写进** `hls/sim/tv/`（`cdatafile/` + `rtldatafile/`），
xsim 再用 `$fscanf` 读。我一度在**拷贝到仓库根的副本**里跑，那里没有 `tv/`，于是报：
```
ERROR: File descriptor (0) passed to $fscanf is not valid.
UVM_FATAL ./file_agent/file_read_agent.sv(370) [file_rd_TVOUT_transaction_size]
```
**验证**：原目录 `component_cosim_roi_720p/hls/sim/tv/` 里**确实有 71 个向量文件**
（`frame_scale` 66 个、`motion_quality` 68 个、`bayer_demosaic` 58 个），
而 `rgb2gray` / `fir_filter` 那两个**失败的** run 是 **0 个** —— 与"谁的 cosim 过了"完全对应。
⇒ **判据**：cosim 失败时先数 `hls/sim/tv/` 下的文件数；**0 个 = C 侧的向量没写出来**。

**结论（可执行）**：`roi_statistic`@720p 的 cosim **需要完整权限终端**：
① 让 `vitis-run` 跑完 C 测试台、把向量写进 `fpga/component_*/hls/sim/tv/`；
② xsim 若报初始化崩溃，就按上面加 `-mt off` 重跑（或把 `-mt off` 接进 `run_hls.tcl` 的 cosim 调用）。
本会话两步都活不到终点，**但两道关卡的机理与绕法现在都写清了**。

## 4. 本轮修掉的 C 线 bug（逐条）

### 4.1 `frame_scale` 的"aspect check"是**恒假断言**（新发现，已修）
`fpga/sim/tb_frame_scale.cpp:212` 原来写的是

```cpp
(960u * 3u == 640u * 2u * 2u) && (720u * 3u == 480u * 2u * 2u)
```

`960*3 = 2880 ≠ 640*4 = 2560`、`720*3 = 2160 ≠ 480*4 = 1920` —— **两边全是编译期常量，
与 DUT 无关 ⇒ 该断言永远 FAIL**，而且与同一表达式里的 `ow == 640` 自相矛盾
（`960*3/4 = 720 ≠ 640`）。也就是说：这条 "aspect check" **从来没有在测任何东西**，
它报 FAIL 不含任何关于 IP 的信息。

- **IP 本身是对的**：Layer 2 跨语言黄金参考 5 帧 × 921600 B **逐字节 0 不符**。
- **改法**：换成与 `host_model_scale.cpp:204`、`gen_scale_vectors.py:164` 同一条比例恒等式
  `out * DEN == in * NUM`（用测试台已有的 `SCALE_NUM` / `SCALE_DEN` 宏，避免以后再漂）。
- **验证**：`Layer 1: 3 passed, 0 failed / Layer 2: 5 passed, 0 failed / RESULT: PASS`，
  并首次拿到该 IP 的资源：**LUT 2282 / FF 2479 / BRAM 0 / DSP 3 / Fmax 151.68 MHz / Final II = 1**。
- **无需重新生成任何黄金参考**。

#### 4.5.1 顺手抓到一个**会静默吃掉开关**的坑（值得记）

第一次实现的 `-SelfTest` **被忽略**：`-SelfTest` 跑完仍然启动了 api.py 并跑了整轮演示。
根因**不是**本脚本写错，而是：

> `omv_stream_bridge.ps1` 自己也有 `param([switch]$SelfTest)`（第 37 行）。
> **dot-source 一个脚本会在当前作用域执行它的 param 块** ⇒ 本脚本的 `$SelfTest` 被重新绑定为 `$false`。

`omv_stream_bridge.ps1` 对**自己**有防护（`$MyInvocation.InvocationName -ne '.'`），
但被 dot-source 时**父脚本的同名变量仍会被覆盖**。
**修法**：在 dot-source **之前**把开关快照到 `$Script:RunSelfTest`，判定用它。

📌 **给后续维护者的判据**：任何 dot-source `omv_stream_bridge.ps1` 的脚本，
**不要在 dot-source 之后再读 `$SelfTest`**；要用就先存成别的名字。
另外顺手更正一条：`-File` 启动时**光靠 `exit` 不足以中止脚本体**（后面还会继续跑），
真要立刻停就用 `[Environment]::Exit()`。


缺省行为一字不变；用于绕开 §1.2 那种"旧构建目录被 NTFS 拒绝项锁死"的环境。见 §2.1。

`--selftest` 离线验：`frames.bin`/`gray.bin`/`rgb_frames.bin` 的**大小能否被本档单帧整除**
（整除不了 = 别的档的数据）、灰度帧数与 RGB 帧数一致、`golden_roi.csv` 表头符合契约字段、
各 CSV 有数据行、`meta.txt` 声明了 `fs=`。

**它真的能抓错（受控实验）**：把 720p 的数据放进 640×480 档的目录布局里跑：
```
[FAIL] motion: gray.bin 能被本档 GRAY_PIXELS 整除   (1296000 % 110592 = 79488)
[FAIL] motion: 灰度帧数 == RGB 帧数                (gray 11 帧 vs rgb 30 帧)
RESULT: FAIL
```
第一条正是"**别的抽取比的数据**"该有的报错。

**顺手修掉一处路径假故障**：`--data-root` 以前按**当前工作目录**解析，
从 `board/` 调用会去找 `board/fpga/sim/...`（不存在）而报"缺文件" ——
与"数据真缺"长得一模一样。已锚到**仓库根**。

**③ 两条都进 `check_all.py` 回归**（工具自检 **10/10 → 12/12 全 PASS**）：
```
[PASS] board/bringup_check.py --selftest
[PASS] board/hw_sw_compare.py --selftest
[工具自检] 12/12 通过
```

⚠️ **仍未闭合**：这两条只证明"**口径与数据配套**"；
**PL 侧的数值一致性（C8/C9/C10 本体）仍然必须上板跑**，一条都没验过。

#### 5.0.1 黄金参考为什么不在 `fpga/sim/` 下

沙箱只允许**仓库根目录**被进程写入（§1.4 实测），`fpga/sim/` 及其子目录一律被拒。
故 720p60 的黄金参考生成在**仓库根**，并用 `run_hls.tcl` **已经支持**的 `ROI_DATA_DIR` 环境变量指过去：

```powershell
python fpga/sim/gen_motion_vectors.py --width 1280 --height 720 --decim 3 8 --out-dir D:\Desktop\AMD\_golden720
cd fpga
$env:ROI_DATA_DIR='D:\Desktop\AMD\_golden720'; $env:VIGILENS_TIER='720p60'; $env:HLS_IP='rgb2gray'
vitis-run --mode hls --tcl run_hls.tcl
# -> INFO: data dir = D:/Desktop/AMD/_golden720 ... RESULT: PASS
```

⚠️ **给人接手时的注意**：这两条命令**必须配套**。若设了 `ROI_DATA_DIR` 却跑**缺省 3/5**，
就会拿 720p 的黄金参考去比 640×480 的输出 —— 本轮我自己踩过：
`Layer 2: 0 passed, 10 failed`、`out=768x432 pc=331776 (exp 129600)`。
**这个失败是"数据配错"，不是 IP 错**；去掉 `ROI_DATA_DIR` 重跑即 `10/10 PASS`（已在同轮复跑确认）。
正式做法应在完整权限终端把产物放进 `fpga/sim/data_motion_720p60/`（该目录的 README 已就位）。

#### 5.0.2 档位化暴露的第二个测试台缺陷（已修）

`tb_rgb2gray.cpp` 的 Layer 1 **把输入/输出尺寸写死成 10x5 → 6x3**（即 3/5）。
以 3/8 编译时它仍按 6x3 断言，**把期望读到 15x15 的输出缓冲之外**，csim 直接报
`an hls::stream ... is read while empty` 并以退出码 3 失败 —— 与"IP 算错"长得一模一样，
但根因是**测试台口径没跟着档位走**。

修法：`W/H/OW/OH` 一律由 `DECIM_NUM/DECIM_DEN` 推导（`W = DECIM_DEN*2`），
并在 `run_hls.tcl` 里**把同一组宏同时给 src 与 tb**（只给 src 就会出现上面那种"两边口径不一致"）。
Layer 1 的输出行现在会自己打印档位：`embedded cases (in 16x16 -> out 6x6, 抽取 3/8)`。

### 1.4 沙箱无法在 `fpga/sim/` 下新建子目录（**已找到绕过办法**）

对 `D:\Desktop\AMD\fpga\sim` 做过 ACL 诊断+授权（备份在 `D:\Desktop\AMD-acl-recovery\`，`VERDICT=PRECONDITION` 已修复），

- 目录本身是用文件工具建出来的（`fpga/sim/data_motion_720p60/README.md` 已成功写入）；

- 这是**沙箱的授权边界**，不是仓库缺陷：同一条命令在**完整权限终端**里应当能跑。
- **绕过办法（给人）**：在完整权限终端执行上面那条命令；或把 `--out-dir` 指到一个
