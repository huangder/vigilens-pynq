## 0. 这份评审为什么存在

实物板卡换成 Mizar-Z7020 后，采集侧与执行侧的规划出现了新的想法，需要先落成文字再动手：

1. **采集**：用 OpenMV 采集图像并做「初次处理」，要求**简洁迅速**；后续可能升级为更高级的摄像头模块；
2. **PL**：在 FPGA 板卡上做「下一步运算」；
3. **上位机**：显示界面（B 线现有工作）；
4. **执行（新增）**：两个电机的**二自由度摄像头云台**实现**人脸追踪**（载的是相机，不是靠近人脸的机构）；
5. **显示（新增）**：用显示屏显示上位机的页面。

与 B 线已提交的 `docs/09_桌面专注舱功能方案.md`（低压 LED 灯光 + 任务锚点）**是并存关系**：
doc 09 面向「环境氛围 + 任务上下文」，本文件面向「采集/计算分工 + 运动闭环」。
两者共用同一套「状态准入 + 用户确认 + 安全降级」的原则，但**执行器风险等级不同**，见 §5。

> ⚠️ 本文件**不是**分工决定，也**不授权**跨线改代码。它给出结论、算清数字、列出证据缺口与决策点。

## 3. 带宽算术：OpenMV 能往 PL 送什么

OpenMV Cam H7 的接口上限（官方产品页）：**UART 7.5 Mb/s**、USB full-speed 12 Mb/s、SPI 80 Mb/s。

**UART 7.5 Mb/s = 937,500 B/s**（按 8 位/字节，不含协议开销）。下表按此计算：

| OpenMV 送什么 | 单帧字节 | 能到的帧率 | 占用 | 判定 |
|---|---|---|---|---|
| 640×480 **RGB888**（契约 §0 口径） | 921,600 | **1 fps** | 98% | ❌ 不可能 |
| 640×480 灰度 | 307,200 | 3 fps | 98% | ❌ 太慢 |
| **320×240 灰度** | 76,800 | **10 fps** | 82% | ✅ **像素通路唯一可行点** |
| 320×240 灰度 @12 fps | 76,800 | 12 fps | 98% | ⚠️ 过紧，协议开销会吃掉 |
| VGA **JPEG**（约 30 KB 量级） | ~30,720 | **约 3 fps** | ~100% | ❌ 且**有损** |
| **结构化数据**（人脸框 + 偏移，约 100 B） | ~100 | 只受采集限 | ~0% | ✅ **追踪必须走这条** |

> ⚠️ 上表用的是**接口上限算术**，不是实测帧率。真实帧率必须由 `board/openmv/openmv_capture_test.py` 的
> `matrix` 模式在真机上测出来。**本文件不含任何实测性能数字。**

**三条推论**：

1. **UART 是瓶颈，不是传感器。** OV7725 本身能跑 75 fps（VGA 灰度），但 7.5 Mb/s 的线把 VGA 灰度压到 3 fps。
2. **送图就做不了追踪。** VGA JPEG 走 UART 只有约 3 fps ⇒ 端到端延迟 ≥330 ms，人脸一晃就丢。
   追踪必须靠**检测结果**（几十字节），不能靠图像。
3. **要保住契约 §0，只能换接口**，不能靠调参。Mizar-Z7 的 7020 版自带 **MIPI CSI**（官方：FPC 引脚兼容树莓派摄像头，实测 672 Mbps/lane）——比 UART 高两个数量级，是唯一能同时满足「640×480 RGB888」与「现有四个 IP 一行不改」的路线。

## 4. 逐 IP 分析：分工一变，谁会没输入

现有四个 HLS IP 的输入契约（`docs/interface.md` §3）：

| IP | 输入 | 送结构化数据时 | 送 320×240 灰度时 | 换 MIPI CSI 时 |
|---|---|---|---|---|
| `roi_statistic` | 640×480 **RGB888** AXI-Stream | ❌ **无输入** | ❌ 格式/尺寸都不符 | ✅ **原样可用** |
| `rgb2gray` | 640×480 RGB888 | ❌ **无输入** | ❌ 已是灰度，多余 | ✅ **原样可用** |
| `motion_quality` | **384×288 灰度** | ❌ **无输入** | ⚠️ 尺寸需改 320×240（`width/height` 是寄存器，改值即可），**黄金参考必须重做** | ✅ **原样可用** |
| `fir_filter` | int16 时间序列 | ✅ **不受影响** | ✅ **不受影响** | ✅ **原样可用** |

**读法**：只有 `fir_filter` 对输入形态不敏感。**前三项的存废完全取决于「PL 能不能拿到像素」。**

> 💡 一个可用的旁证：`motion_quality` 的 BRAM 成本是**台阶式**的（`AGENTS.md` §7.5）。
> 320×240 = 76,800 像素 ≤ 2¹⁷，与 384×288 的 110,592 落在**同一台阶**，都是 64 个 BRAM18 ——
> 所以「尺寸从 384×288 改成 320×240」在资源上**不付额外代价**，代价全在**黄金参考要重做 + 契约要改**。

## 5. 二自由度云台：与 doc 09 的边界，以及**一个真正的技术冲突**

> 🛑 **2026-09-24：云台方案已由用户明确「暂时搁置」。**
> 本节**保留不删**，因为里面的分析（尤其 §5.3 的「云台一动、测量就废」）
> 在云台复活时可以直接用，重做一遍是浪费。当前排期里**不含云台**。

> 📌 **2026-09-24 更正**：本节初稿把「机械臂」理解成**靠近人脸的运动机构**（并据此写了"机械撞击人体"的风险）。
> 经用户澄清，实际是**承载摄像头的二自由度小云台**（两个电机做水平/竖直转动）——机构**载的是相机，不靠近人脸**。
> 下面已按真实形态重写。**初稿那条风险判断作废**。

### 5.1 与 doc 09 的边界关系

`docs/09` 写的是：

> §1.3 首版……**不自动移动鼠标键盘、锁定设备、控制市电插座或启动机械机构**
> §3.2 控制对象仅限**可安全失效的低压 LED**/兼容智能灯场景

云台虽然载的不是人，但仍是**运动机构**，doc 09 那句"不启动机械机构"按字面**与本次规划冲突**。
两处需要对齐（二选一，由团队定）：

- **改 doc 09 的措辞**：把"不启动机械机构"收窄为"不启动**与人接触/靠近人体**的机械机构"，云台因此被允许；**或**
- **明确云台不在 doc 09 范围内**：云台另立一份方案，doc 09 保持不动，但要在 doc 09 里加一句交叉引用避免读者误解。

风险等级的差异是真实的（下表），但比初稿估计的**低得多**：

| 维度 | 低压 LED（doc 09） | **摄像头云台**（本文件，更正后） |
|---|---|---|
| 失效后果 | 灯不亮 / 长亮 | **取景丢失 / 云台卡住**（不涉及人身） |
| 需要限位 | 否 | 是（避免转出机械行程、避免扯断排线） |
| 需要限速 | 否 | 是（慢速跟随，避免果冻效应与振动） |
| 失电行为 | 无所谓 | 建议**回中或保持**，不要求断电自锁 |
| 急停 | 无 | 建议有（一键回中/停追），但**不是人身安全等级** |
| 质量门控不通过时 | 不动灯 | **停止追踪**（继续追只会更糟，见 §5.3） |

### 5.2 必须与 doc 09 统一的部分

两条线都是「**状态准入 → 用户确认 → 执行 → 可撤销**」，因此应当共用同一套控制面原则
（doc 09 §5 已给出草案：`session_id` / `command_id` / 动作白名单 / 过期时间 / 幂等）。

**建议**：把 doc 09 §5 的控制消息草案**扩展一个执行器枚举**（如 `tracker_freeze` / `tracker_center` / `tracker_enable`），
**不要为云台另起一套协议**。但**冻结接口前必须先评审** —— 本文档不定义该协议。

### 5.3 ⚠️ 真正的冲突：**云台一动，测量就废**（这是本节最重要的一条）

这不是安全顾虑，是**架构级的互相打架**，必须现在就设计，否则演示时会现场翻车：

1. `motion_quality` 的语义是**帧间像素绝对差**（契约 §3.3）。**相机一动，整个画面都在动**
   → `diff_total` / `motion_pixels` 飙升 → `motion_score` 超标 → `quality.overall` 掉到门控线以下
   → 状态被判定为 **`unreliable`** → **系统按设计拒绝输出测量结果**。
2. 同时 rPPG 也受影响：ROI 在画面里漂移，**绿通道均值的交流分量被运动伪影污染**，
   即使勉强出数也不可信。
3. 结论：**「追踪」与「测量」在时间上基本互斥。**

**三种可行设计（推荐第 1 种）**：

| 方案 | 做法 | 代价 |
|---|---|---|
| **① 分时（推荐）** | **追踪阶段只追踪、不测量**；人脸居中并静止超过 N 秒后**锁定云台**，才开始测量；测量期间云台不动 | 需要一条明确的"锁定 → 测量 → 解锁"状态迁移，并进 `config.yaml` |
| ② 慢速 + 大死区 | 云台运动足够慢、死区足够大，使帧间差始终低于阈值 | 追踪响应变钝；仍会推高 motion 分；**阈值需要标定**，且可能压不住 |
| ③ 运动补偿 | 用云台角度/光流补偿画面位移后再算指标 | 工程量大，且 rPPG 的补偿精度要求很高；**不建议首版做** |

> ⚠️ 无论选哪种，**都要在 `config.yaml` 里加一个新阈值**（如"静止多久才允许开始测量"），
> 并且它**超出现有契约的语义**（`motion_score_max` 原本是给"人自己动"设的）。这需要走共享配置变更。

### 5.4 云台特有的工程风险（初稿漏掉、但真实存在）

| 风险 | 说明 | 缓解 |
|---|---|---|
| **FPC 排线疲劳断裂** | MIPI 排线随云台反复扭动，是**最典型的失效点** | 排线留足余量并做应力释放；限制转角；**备一根** |
| 排线过长导致误码 | MIPI D-PHY 是高速差分，长排线/劣质排线会误码 | 用官方 200 mm 排线；不要随意加长 |
| 舵机堵转电流 | 堵转电流远大于逻辑电源 | **独立供电**，不与板卡 3V3 共用 |
| 舵机 PWM 噪声耦合 | 可能进相机电源/排线，表现为图像噪声 | 电源去耦；PWM 线与 MIPI 排线**走线分离** |
| 云台自重与惯性 | 相机+镜头越重，舵机越难稳住，容易微振 | 选合适扭矩；M12 小镜头优于 C/CS 大镜头 |

### 5.5 追踪闭环的实现检查表

- [ ] **行程限制**：结构上限位，避免转出机械行程或扯断排线
- [ ] **速度上限**：慢速跟随，禁止"弹射"式动作
- [ ] **死区**：人脸在中心附近**不动**（既防抖动，也避免把 `motion_quality` 一直顶高）
- [ ] **质量门控联动**：`unreliable` / `disconnected` / `adjust_posture` ⇒ **停止追踪**（§5.3）
- [ ] **分时状态机**：追踪 / 锁定 / 测量 三态明确（§5.3 方案 ①）
- [ ] **失电策略**：明确断电时回中还是保持，并**实测确认**
- [ ] **一键回中/停追**：按钮或网页操作
- [ ] **独立供电与电流核算**：舵机不共用板卡电源
- [ ] **无硬件保底**：云台缺席时演示能退回 Mock（与 doc 09 §8 同一要求）

## 6. 推荐的职责切分（三个方案对比）

| | 方案 A：OpenMV 送结构化数据 | 方案 B：OpenMV 送 320×240 灰度 | 方案 C：换 MIPI CSI 摄像头 |
|---|---|---|---|
| OpenMV 角色 | 采集 + **人脸检测/追踪目标** | 采集 + 降规格输出 | 仅作过渡/演示采集源 |
| OpenMV → PL | ~100 B/帧 | 76,800 B/帧 @≤10fps | 不需要（像素直接进 PL） |
| 契约 §0 | 需**大改**（视频源变更） | 需**改分辨率/格式** | ✅ **不用改** |
| 四个 IP | 只有 `fir_filter` 可用，**前三项废弃** | `roi_statistic`/`rgb2gray` 废弃，`motion_quality` 改尺寸 + 重做黄金参考 | ✅ **一行不改** |
| PL 是否被架空 | ⚠️ **高风险**（只剩 FIR） | ✅ 仍做像素级确定性处理 | ✅ **完全保住** |
| 追踪闭环 | ✅ 唯一可行 | ❌ 送图就 3 fps，追不动 | ✅ 可行 |
| 代价 | 契约大改 + 三个 IP 废弃 | 契约改 + 黄金参考重做 | 换摄像头 + MIPI 接收 IP（新工作量） |

### 推荐组合（分阶段）

**短期（现在就做，不动契约）**
- **OpenMV = 采集 + 人脸检测/追踪目标**（方案 A 的采集部分），输出结构化数据。
- 结构化数据先**走笔记本**（USB/UART），**不急着进 PL** —— 因为 PL 没有对应的输入 IP，硬接只会卡住。
- PL 侧先用**已有的、不依赖像素**的能力：`fir_filter` 时间序列链路 + `board/openmv/pl_uart_echo.v` 的**最小上板回环**建立板卡通路信心。

**中期（决定项目形态的关键一步）**
- **升级到 MIPI CSI 摄像头**（方案 C）。这是唯一能同时保住「契约 §0」与「四个 IP」的路线。
- 届时的分工：**PL 做像素级确定性预处理**（ROI 统计 / 灰度缩放 / 帧间运动 / FIR），
  **OpenMV 退居「追踪传感器」**（只出目标偏移），**笔记本做指标与界面**，**MCU 做执行器**。

> ⚠️ **不要走方案 B**。它同时承担了「契约要改」和「黄金参考全部重做」两笔成本，
> 却把分辨率降到 320×240、把 PL 的 `rgb2gray` 变成废件 —— 付出的代价比方案 C 大，得到的能力比方案 C 小。

## 7. 追踪闭环延迟预算（按结构化数据方案）

| 环节 | 估算 | 依据 |
|---|---|---|
| OpenMV 采集 @15 fps | ≤67 ms | 帧周期 |
| OpenMV 人脸检测 | 10~30 ms | **待实测**（H7 上跑检测的真实耗时） |
| 传 ~100 B @921600 | ~1 ms | 算术 |
| PL 处理 | 微秒~毫秒级 | 确定性硬件路径 |
| 笔记本决策 + 串口下发 | 5~20 ms | 待实测 |
| 舵机响应 + 机械稳定 | 20~50 ms | 待实测（看舵机型号） |
| **合计** | **≈100~170 ms** | ⇒ 有效追踪更新率 **约 6~10 Hz** |

**结论**：对「让人脸慢慢保持在画面中心」够用；**快速转头会明显滞后**。
因此实现上必须配**死区**（否则会持续追着噪声抖），并且**不要承诺「实时锁定」**。

> ⚠️ 上表是**预算**，不是实测。每一行标了"待实测"的都必须由真机测出来再回填。
> 这份预算的用途是**判断可行性**，不是当作性能结论引用。

## 8. 显示屏：先分清是哪一种

规划里「用显示屏显示上位机的页面」有两种完全不同的含义，工程量差两个数量级：

| 含义 | 工程量 | 结论 |
|---|---|---|

**已定**：先做笔记本外接显示器（零工程）。

不能在业务代码里悄悄加。

> （HDMI1 写 "output … can be configured as HDMI RX"，HDMI2 写 "input … can be configured as HDMI TX"）。
> **以实机实测为准**，本文档不据此下结论。

## 12. 摄像头选型建议（2026-09-24）

### 12.1 选型判据（按本项目权重排序）

| # | 判据 | 为什么 |
|---|---|---|
| 1 | **像素要能进 PL** | 比赛主题是 FPGA。走 USB/UVC 的摄像头像素只到 PS，**PL 看不到画面**，正中"FPGA 不是转发器"的反面 |
| 2 | **接线便捷** | Mizar-Z7 有专用扩展口，但**飞线越少越不容易接触不良** |
| 3 | **满足契约 §0**（640×480 RGB888 @30fps） | 不用改契约、不用重做黄金参考 |
| 4 | **适配云台** | 相机要动：自动对焦有用；排线要抗反复扭动 |
| 5 | **国内可得 + 成本** | 赛前采购周期 |

### 12.2 关键前提（我实测核对到的三条）

1. **Mizar-Z7 自带 MIPI CSI，15-pin 1 mm FPC，官方写明"FPC 引脚兼容树莓派摄像头"**，
   实测 672 Mbps/lane（来源：MicroPhase《Mizar-Z7 Reference Manual》）。
2. ✅ **Xilinx MIPI CSI 子系统 IP 自 Vivado 2020.1 起包含在免费标准授权内**，无需额外购买
   （来源：[Hackster 报道](https://www.hackster.io/news/no-license-needed-xilinx-mipi-csi-ip-block-free-in-vivado-2020-1-9da3a324f5a4)；
   本项目用 Vivado 2026.1，覆盖）。**这解掉了初稿担心的授权问题。**
3. ✅ 该 IP 是 **AXI-4 Streaming 输出**，且支持 **RAW6~RAW20 / RGB565 / RGB888 / YUV422** 等数据类型
   （来源：[AMD MIPI CSI-2 RX Subsystem 驱动文档](https://xilinx-wiki.atlassian.net/wiki/spaces/A/pages/18841643/MIPI+CSI-2+RX+Subsystem+Standalone+Driver)）
   —— **与本项目四个 IP 的 AXI-Stream 口径天然对齐。**

> ⚠️ 一条**论坛陈述**（[r/FPGA](https://www.reddit.com/r/FPGA/comments/w0tp8r/mipi_camera_frustrations/)）
> 称有人已把 **MicroPhase Mizar Z7 + 树莓派 HQ 摄像头** 用起来。**论坛内容未经本站实测**，
> 只作"这条路有人走过"的旁证，**不得当作已验证结论**。

### 12.3 推荐清单（按推荐度排序）

**第一梯队：Mizar 自带 MIPI CSI + 树莓派摄像头（唯一同时满足判据 1+2 的路线）**

| 推荐度 | 型号 | 传感器 | 分辨率 | 接口 | 对焦 | 为什么推荐 / 不适合 |
|---|---|---|---|---|---|---|
| 🥇 **首选** | **Camera Module 3**（买 **15-pin 版**） | IMX708 | 12MP | 2-lane MIPI（可 4） | **PDAF 自动对焦** | **云台首选**：相机转动、人脸距离变化时自动对焦；有 HDR；RAW10 输出；生态活跃 |
| 🥈 **最稳** | **Camera Module 2**（15-pin） | IMX219 | 8MP | 2-lane MIPI | 定焦 | **最便宜、文档与例程最多**；640×480 能到 ~100fps（远超 30fps 需求）。**建议先用它把通路打通** |
| 🥉 可换镜头 | **HQ Camera** | IMX477 | 12.3MP | 4-lane（15-pin 下走 2-lane） | **可换 C/CS 或 M12 镜头** | 可调 FOV 是云台的加分项；但**体积大、重**，对舵机扭矩要求高；且是那条论坛陈述里用过的型号 |
| ⚠️ 特殊用途 | **Global Shutter Camera** | IMX296 | 1.6MP | 2-lane MIPI | C/CS 定焦 | **全局快门**：云台转动无果冻效应，最适合运动场景。**但是黑白的** → 会破坏契约 §0 的 RGB888 与 rPPG 的绿通道选择，**不建议当主相机** |
| ⚠️ 第三方便宜货 | Arducam 等的 RPi 兼容 MIPI（OV9281 / OV7251 等） | 1MP / 0.3MP | 2-lane MIPI | 定焦 | 全局快门、高帧率、便宜；**但多为黑白**且驱动/例程质量参差 |

**第二梯队：备用路线（各有明显代价）**

| 路线 | 免授权 | 免 demosaic | 接线 | 判定 |
|---|---|---|---|---|
| **DVP 并行模块**（OV5640 等，24-pin FPC 或 40-pin 排针） | ✅ | ✅（OV5640 内置 ISP 可直出 **RGB565**） | ❌ **要 ~22 根线** | **MIPI 走不通时的备选**：省掉 demosaic 这个新 IP，代价是接线最麻烦、40-pin 上飞线易接触不良 |
| **USB / UVC 摄像头** | — | — | ✅ 一根线 | ❌ **像素只到 PS，PL 看不到画面** —— 直接违背比赛主题 |
| **继续用 OpenMV 当相机** | — | — | ✅ 3 根线 | ❌ 链路差 29 倍（§3），只能送降规格数据 |

### 12.4 ⚠️ 必须提前知道的一件事：**相机出来的是 RAW Bayer，不是 RGB**

树莓派摄像头（IMX219/IMX708/IMX477）走 MIPI CSI-2 输出的都是 **RAW10 Bayer**，
**不是 RGB**。所以 PL 必须做 **demosaic（去马赛克）**。

这**不是坏事，反而是加分项**：

- demosaic 是**定义明确、纯整数、可用黄金参考逐点比对**的确定性图像处理任务 ——
  **正是 HLS 该做的事**，比"再多做一个转发"更能证明 PL 的价值；
- 它天然接在现有 `rgb2gray`（契约 §3.4）**前面**，链路变成：
  `MIPI CSI-2 RX → Bayer RAW10 → [新 IP: demosaic] → RGB888 → rgb2gray → motion_quality`
- Xilinx 另有 **Sensor Demosaic IP**（同样在免费授权范围内，**待核实**）；
  也有开源的 debayer 实现（[CHIPS Alliance](https://www.chipsalliance.org/news/open-source-debayerization-blocks-in-fpga/)）。

**代价要说清楚**：新增一个 HLS IP = 新接口要进契约 §3、新黄金参考、新 csim/csynth/cosim。
**这是换 MIPI 路线的真实成本**，要排进计划。

### 12.5 采购与接线注意（踩坑清单）

- [ ] **买 15-pin 1 mm FPC 版本**，不要买 Pi Zero 的窄排线版（RPi 官方明确：与 Pi 400 和旧版 Zero 不兼容）；
      连接器是 **top contact**，注意排线金手指朝向（官方手册写明），**插反不工作**
- [ ] **不要随意加长 MIPI 排线**：D-PHY 是高速差分，加长/劣质排线会误码；官方排线 200 mm 够用
- [ ] Mizar 的 MIPI 口是否提供 **3.3V / I2C(SCCB) / MCLK** —— 官方说引脚兼容树莓派，**但仍要用万用表实测确认**（【未验证】）
- [ ] 云台选舵机看**扭矩**：HQ Camera + C/CS 镜头偏重；M12 小镜头轻得多
- [ ] 排线做**应力释放**，限制转角（§5.4：FPC 疲劳断裂是云台最典型失效点）

### 12.6 建议的推进顺序

1. **先买 Camera Module 2（IMX219，15-pin）** —— 最便宜、文档最多，用它把
   `MIPI CSI-2 RX → AXI-Stream → 已有 IP` 这条通路**第一次打通**；
2. 通路通了之后，再决定要不要上 **Camera Module 3（IMX708）** 拿自动对焦；
3. **demosaic IP** 与 **分时状态机**（§5.3）要**并行**排期 —— 它们是这条路线的两个真实成本。

> ⚠️ 本节所有选型结论**都还没有在本站实测过**：Mizar 的 MIPI 口、MIPI CSI-2 RX IP、
> demosaic、任何一款摄像头，**一样都没接过**。上面标注的【推测】/【不确定】请勿当结论引用。
