## 0. 这份评审为什么存在

实物板卡换成 Mizar-Z7020 后，采集侧与执行侧的规划出现了新的想法，需要先落成文字再动手：

1. **采集**：用 OpenMV 采集图像并做「初次处理」，要求**简洁迅速**；后续可能升级为更高级的摄像头模块；
2. **PL**：在 FPGA 板卡上做「下一步运算」；
3. **上位机**：显示界面（B 线现有工作）；
4. **执行（新增）**：两个电机的机械臂实现**人脸追踪**；
5. **显示（新增）**：用显示屏显示上位机的页面。

与 B 线已提交的 `docs/09_桌面专注舱功能方案.md`（低压 LED 灯光 + 任务锚点）**是并存关系**：
doc 09 面向「环境氛围 + 任务上下文」，本文件面向「采集/计算分工 + 运动闭环」。
两者共用同一套「状态准入 + 用户确认 + 安全降级」的原则，但**执行器风险等级不同**，见 §5。

> ⚠️ 本文件**不是**分工决定，也**不授权**跨线改代码。它给出结论、算清数字、列出证据缺口与决策点。

## 3. 带宽算术：OpenMV 能往 PL 送什么

OpenMV Cam H7 的接口上限（官方产品页）：**UART 7.5 Mb/s**、USB full-speed 12 Mb/s、SPI 80 Mb/s。

**UART 7.5 Mb/s = 937,500 B/s**（按 8 位/字节，不含协议开销）。下表按此计算：

| OpenMV 送什么 | 单帧字节 | 能到的帧率 | 占用 | 判定 |
|---|---|---|---|---|
| 640×480 **RGB888**（契约 §0 口径） | 921,600 | **1 fps** | 98% | ❌ 不可能 |
| 640×480 灰度 | 307,200 | 3 fps | 98% | ❌ 太慢 |
| **320×240 灰度** | 76,800 | **10 fps** | 82% | ✅ **像素通路唯一可行点** |
| 320×240 灰度 @12 fps | 76,800 | 12 fps | 98% | ⚠️ 过紧，协议开销会吃掉 |
| VGA **JPEG**（约 30 KB 量级） | ~30,720 | **约 3 fps** | ~100% | ❌ 且**有损** |
| **结构化数据**（人脸框 + 偏移，约 100 B） | ~100 | 只受采集限 | ~0% | ✅ **追踪必须走这条** |

> ⚠️ 上表用的是**接口上限算术**，不是实测帧率。真实帧率必须由 `board/openmv/openmv_capture_test.py` 的
> `matrix` 模式在真机上测出来。**本文件不含任何实测性能数字。**

**三条推论**：

1. **UART 是瓶颈，不是传感器。** OV7725 本身能跑 75 fps（VGA 灰度），但 7.5 Mb/s 的线把 VGA 灰度压到 3 fps。
2. **送图就做不了追踪。** VGA JPEG 走 UART 只有约 3 fps ⇒ 端到端延迟 ≥330 ms，人脸一晃就丢。
   追踪必须靠**检测结果**（几十字节），不能靠图像。
3. **要保住契约 §0，只能换接口**，不能靠调参。Mizar-Z7 的 7020 版自带 **MIPI CSI**（官方：FPC 引脚兼容树莓派摄像头，实测 672 Mbps/lane）——比 UART 高两个数量级，是唯一能同时满足「640×480 RGB888」与「现有四个 IP 一行不改」的路线。

## 4. 逐 IP 分析：分工一变，谁会没输入

现有四个 HLS IP 的输入契约（`docs/interface.md` §3）：

| IP | 输入 | 送结构化数据时 | 送 320×240 灰度时 | 换 MIPI CSI 时 |
|---|---|---|---|---|
| `roi_statistic` | 640×480 **RGB888** AXI-Stream | ❌ **无输入** | ❌ 格式/尺寸都不符 | ✅ **原样可用** |
| `rgb2gray` | 640×480 RGB888 | ❌ **无输入** | ❌ 已是灰度，多余 | ✅ **原样可用** |
| `motion_quality` | **384×288 灰度** | ❌ **无输入** | ⚠️ 尺寸需改 320×240（`width/height` 是寄存器，改值即可），**黄金参考必须重做** | ✅ **原样可用** |
| `fir_filter` | int16 时间序列 | ✅ **不受影响** | ✅ **不受影响** | ✅ **原样可用** |

**读法**：只有 `fir_filter` 对输入形态不敏感。**前三项的存废完全取决于「PL 能不能拿到像素」。**

> 💡 一个可用的旁证：`motion_quality` 的 BRAM 成本是**台阶式**的（`AGENTS.md` §7.5）。
> 320×240 = 76,800 像素 ≤ 2¹⁷，与 384×288 的 110,592 落在**同一台阶**，都是 64 个 BRAM18 ——
> 所以「尺寸从 384×288 改成 320×240」在资源上**不付额外代价**，代价全在**黄金参考要重做 + 契约要改**。

## 5. 机械臂：与 doc 09 的边界冲突，必须显式处理

### 5.1 冲突点

`docs/09` 写的是：

> §1.3 首版……**不自动移动鼠标键盘、锁定设备、控制市电插座或启动机械机构**
> §3.2 控制对象仅限**可安全失效的低压 LED**/兼容智能灯场景

本次规划要在**人脸附近**加两个电机的运动机构。**风险等级不是「多一点」的量变**：

| 维度 | 低压 LED（doc 09） | 人脸附近的运动机构（本文件） |
|---|---|---|
| 失效后果 | 灯不亮 / 长亮 | **机械撞击人体** |
| 需要限位 | 否 | **是**（硬行程约束） |
| 需要限速 | 否 | **是** |
| 失电行为 | 无所谓 | **必须定义**（保持 / 松开 / 回中） |
| 急停 | 无 | **必须有，且优先级高于一切软件状态** |
| 质量门控不通过时 | 不动灯 | **必须冻结电机** |

### 5.2 必须与 doc 09 统一的部分

两条线都是「**状态准入 → 用户确认 → 执行 → 可撤销**」，因此应当共用同一套控制面原则
（doc 09 §5 已给出草案：`session_id` / `command_id` / 动作白名单 / 过期时间 / 幂等）。

**建议**：把 doc 09 §5 的控制消息草案**扩展一个执行器枚举**（如 `tracker_freeze` / `tracker_center`），
**不要为机械臂另起一套协议**。但**冻结接口前必须先评审** —— 本文档不定义该协议。

### 5.3 安全底线（建议写进实现前的检查表）

- [ ] **行程硬限位**：结构上不允许转到能撞到人脸/颈部的角度（不是靠软件限位）
- [ ] **速度上限**：追踪运动限速，禁止"弹射"式跟随
- [ ] **死区**：人脸在中心附近**不动**，避免来回抖动（同时也是延长舵机寿命的关键）
- [ ] **质量门控联动**：`unreliable` / `disconnected` / `adjust_posture` ⇒ **冻结**，绝不继续追
- [ ] **失电策略**：明确断电时舵机是保持还是松开，并**实测确认**
- [ ] **实体急停**：独立于软件状态的按键，按下即断电/断驱动
- [ ] **独立供电与电流核算**：舵机不得由开发板 IO 或板卡 3V3 直接供电（堵转电流远大于逻辑电源）
- [ ] **无硬件保底**：机械臂缺席时，演示必须能退回 Mock（与 doc 09 §8 同一要求）

## 6. 推荐的职责切分（三个方案对比）

| | 方案 A：OpenMV 送结构化数据 | 方案 B：OpenMV 送 320×240 灰度 | 方案 C：换 MIPI CSI 摄像头 |
|---|---|---|---|
| OpenMV 角色 | 采集 + **人脸检测/追踪目标** | 采集 + 降规格输出 | 仅作过渡/演示采集源 |
| OpenMV → PL | ~100 B/帧 | 76,800 B/帧 @≤10fps | 不需要（像素直接进 PL） |
| 契约 §0 | 需**大改**（视频源变更） | 需**改分辨率/格式** | ✅ **不用改** |
| 四个 IP | 只有 `fir_filter` 可用，**前三项废弃** | `roi_statistic`/`rgb2gray` 废弃，`motion_quality` 改尺寸 + 重做黄金参考 | ✅ **一行不改** |
| PL 是否被架空 | ⚠️ **高风险**（只剩 FIR） | ✅ 仍做像素级确定性处理 | ✅ **完全保住** |
| 追踪闭环 | ✅ 唯一可行 | ❌ 送图就 3 fps，追不动 | ✅ 可行 |
| 代价 | 契约大改 + 三个 IP 废弃 | 契约改 + 黄金参考重做 | 换摄像头 + MIPI 接收 IP（新工作量） |

### 推荐组合（分阶段）

**短期（现在就做，不动契约）**
- **OpenMV = 采集 + 人脸检测/追踪目标**（方案 A 的采集部分），输出结构化数据。
- 结构化数据先**走笔记本**（USB/UART），**不急着进 PL** —— 因为 PL 没有对应的输入 IP，硬接只会卡住。
- PL 侧先用**已有的、不依赖像素**的能力：`fir_filter` 时间序列链路 + `board/openmv/pl_uart_echo.v` 的**最小上板回环**建立板卡通路信心。

**中期（决定项目形态的关键一步）**
- **升级到 MIPI CSI 摄像头**（方案 C）。这是唯一能同时保住「契约 §0」与「四个 IP」的路线。
- 届时的分工：**PL 做像素级确定性预处理**（ROI 统计 / 灰度缩放 / 帧间运动 / FIR），
  **OpenMV 退居「追踪传感器」**（只出目标偏移），**笔记本做指标与界面**，**MCU 做执行器**。

> ⚠️ **不要走方案 B**。它同时承担了「契约要改」和「黄金参考全部重做」两笔成本，
> 却把分辨率降到 320×240、把 PL 的 `rgb2gray` 变成废件 —— 付出的代价比方案 C 大，得到的能力比方案 C 小。

## 7. 追踪闭环延迟预算（按结构化数据方案）

| 环节 | 估算 | 依据 |
|---|---|---|
| OpenMV 采集 @15 fps | ≤67 ms | 帧周期 |
| OpenMV 人脸检测 | 10~30 ms | **待实测**（H7 上跑检测的真实耗时） |
| 传 ~100 B @921600 | ~1 ms | 算术 |
| PL 处理 | 微秒~毫秒级 | 确定性硬件路径 |
| 笔记本决策 + 串口下发 | 5~20 ms | 待实测 |
| 舵机响应 + 机械稳定 | 20~50 ms | 待实测（看舵机型号） |
| **合计** | **≈100~170 ms** | ⇒ 有效追踪更新率 **约 6~10 Hz** |

**结论**：对「让人脸慢慢保持在画面中心」够用；**快速转头会明显滞后**。
因此实现上必须配**死区**（否则会持续追着噪声抖），并且**不要承诺「实时锁定」**。

> ⚠️ 上表是**预算**，不是实测。每一行标了"待实测"的都必须由真机测出来再回填。
> 这份预算的用途是**判断可行性**，不是当作性能结论引用。

## 8. 显示屏：先分清是哪一种

规划里「用显示屏显示上位机的页面」有两种完全不同的含义，工程量差两个数量级：

| 含义 | 工程量 | 结论 |
|---|---|---|
| **笔记本外接显示器，显示同一个网页** | **零** | 插 HDMI + 浏览器 F11 全屏。对契约、对 FPGA 无任何影响。**先做这个。** |
| **Zynq 板卡驱动屏**（板子输出画面） | **与现有四个 IP 相当** | 需要一整套新的视频输出通路：HDMI TX + VDMA + 帧缓冲 + 时序控制 IP，且要新增 DDR 带宽预算。**属独立工作项，不应挤占 M3 的上板验证。** |

**已定**：先做笔记本外接显示器（零工程）。
**待定**：板驱屏是否进 M4。若要做，必须先在 `docs/interface.md` 新增视频输出相关的口径，
不能在业务代码里悄悄加。

> 📌 Mizar-Z7 7020 版有 2 个 HDMI 口，官方手册对 HDMI1/HDMI2 的收发方向描述**自相矛盾**
> （HDMI1 写 "output … can be configured as HDMI RX"，HDMI2 写 "input … can be configured as HDMI TX"）。
> **以实机实测为准**，本文档不据此下结论。
