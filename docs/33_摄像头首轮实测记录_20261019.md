## 0. 一句话结论

**新相机接上后首轮实测：SCCB 主机工作正常（认到板载 EEPROM），但 IMX219 仍不应答；
新的第 4 层「MCLK 频率测量」片上直接量到 CAM_CLK(pin12) 上【无时钟】——**
即 `mclk_seen=0 / mclk_period=0 / mclk_npulse=0`。

这**直接把 docs/31 的候选①（相机没拿到合法 MCLK）从「待万用表验证的推测」升级为
「片上实测」**。相机拿不到 INCK，按数据手册就不应答 SCCB —— 这是当前最硬的头号嫌疑。

## 3. 原始读数【已验证】

`_cam_build/cam_detect_dbg/cam_detect_ila.csv`（2048 个采样，去重后仅 1 种组合，**未经编辑**）：

按 `board/check_camera.py` 的 DBG_LAYOUT（LSB-first）解码：

| 总线 | 原始值 | 逐字段解码 |
|---|---|---|
| `dbg0` | `0x007F7012` | `hit_n=2`、`pwr_done=1`、`i2c_act=0`、`mclk_self=0`、**`mclk_seen=0`**、`ms=0`、`step=7(DONE)`、`scan_a=0x7F`、**`cam_ack=0`** |
| `dbg1` | `0xFFFFFFFFA0000000` | `mclk_npulse=0x00`、**`mclk_period=0x0000`**、`hit_a0=0xA0`、`rec0=0xFFFFFFFF` |
| `dbg2` | `0xFFFFFFFFB0000000` | `hit_a1=0xB0`、`hit_a2/3/4=0`、`rec1=0xFFFFFFFF` |
| `dbg3` | `0x0000000000000000` | `hit_a5/a6=0`、`cam8_rec=0`、`cam16_hi=0`（无型号读回） |

判读脚本输出（原样关键行）：

```
结论：CAMERA_NO_CLOCK（没连上 —— 相机不应答，且 CAM_CLK 上没量到时钟）
  应答过的地址（8bit 写地址）：0xA0 板载 EEPROM 24C32 页0、0xB0 板载 EEPROM 24C32 页1；hit_n=2
  相机地址应答（cam_ack）：否
  型号寄存器：16bit 口径=0x0000，8bit 口径=0x0000，期望 0x0219 ⇒ 对不上
  CAM_CLK：没量到（mclk_period=0）
  RESULT: FAIL（相机没连上）        # 退出码 1
```

## 4. 判定：能确定什么，不能确定什么

### 能确定【已验证】

1. **PL 的 SCCB 主机还是好的** —— 本轮换了探针、重写判读脚本，EEPROM（0xA0/0xB0）
   依旧稳定应答，说明位翻转时序、开漏三态、上拉、引脚约束（A20/E17）都对。
2. **相机(0x20)对两种地址宽度都不应答**，型号寄存器两次读回 `0xFFFFFFFF`（全 1 = 无人给数据）。
3. **定序器跑完了**（`step=7 DONE`），「读不到」不是逻辑卡死。
4. **第 4 层新证据**：片上 MCLK 测量 `mclk_seen=0 / period=0 / npulse=0` —— pin12 无时钟。

### 对比 docs/31（这是本轮最大增量）

docs/31 候选① 的验证手段是「万用表量 pin 12 对 GND（0 V ⇒ 没时钟）」—— 那是**人肉、待做**的项。
本轮探针把这件事**做进了 PL**：直接在片上数 CAM_CLK 的边沿，读回 **0 边沿**。

- 【已验证】测量逻辑本身在仿真里验证过（`tb_pl_cam_detect.v` 的 S3：无时钟 ⇒ `mclk_seen=0`）。
- 【推测】仍需万用表量 pin 12 做一次交叉确认，排除「测量层自身接线有 bug」的小概率
  （0xA0/0xB0 应答只证明 SCCB 两个脚的路由对，**不能**证明 mclk 那个 IOBUF 的路由对）。

## 5. 本轮顺带修掉的三处工具链问题（真机才暴露，留档）

| # | 问题 | 修法 | 证据 |
|---|---|---|---|
| 1 | 位流构建 `Place 30-574 rule_gclkio_bufg`：`always @(posedge mclk)` 测频，mclk(U9) 非时钟专用脚，BUFG 走不了 | `cam_detect_pins.xdc` 加 `set_property CLOCK_DEDICATED_ROUTE FALSE [get_nets mclk_IBUF]` | 构建 exit 0 |
| 2 | `check_camera.py` 的 dbg 位序反了：RTL 是 MSB-first 拼接、DBG_LAYOUT 却按 MSB-first 顺序做 LSB-first 解码 ⇒ 真机读回会静默错位 | DBG_LAYOUT 四表反转为 LSB-first；新增 T10 用手算 RTL 拼接值钉住 | 自检 10/10 |
| 3 | Vivado ILA 导出表头是 `dbg0[31:0]…dbg3[63:0]`（按位流网名），脚本只认 `probe0…` ⇒ CSV 读不动 | `_norm()` 把 `dbgN` 归一化到 `probeN` | 真机 CSV 判读通过 |

> ⚠️ 问题 2 尤其危险：若不修，本次 `dbg0=0x007F7012` 会被读成 `scan_a=0xC9` 等错值，
> 而自检还是 9/9（pack 与 decode 用同一张反序表闭回路）。真机数据才让它现形。

## 7. 复现

```powershell
# 前提：板卡上电 + USB-JTAG 连着（FTDI 210241631901）。需完整权限终端（Vivado 写 AppData）。

# ① 判读脚本离线自检（不需要板卡），期望 RESULT: PASS (10/10)
.\.venv\Scripts\python.exe board\check_camera.py --selftest

# ② 建带 ILA 位流（不需要板卡）
cd board\cam_detect
cmd /c "call D:\Xilinx\2026.1\Vivado\settings64.bat && vivado -mode batch -source build_dbg.tcl"

# ③ 编程 + 触发 + 导出 CSV（需要板卡）
cmd /c "call D:\Xilinx\2026.1\Vivado\settings64.bat && vivado -mode batch -source read_ila.tcl"

# ④ 判读
.\.venv\Scripts\python.exe board\check_camera.py ..\..\_cam_build\cam_detect_dbg\cam_detect_ila.csv --raw --json ..\..\_cam_build\cam_detect_result.json
```

⚠️ `build_dbg.tcl` / `read_ila.tcl` 里是原样绝对路径 `D:/Desktop/AMD/_cam_build/...`，换目录要先改。
