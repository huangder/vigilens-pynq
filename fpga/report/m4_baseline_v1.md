## 1. 为什么要有这份基线

M4 要交付"FPGA 模式 vs 软件模式"的延迟/CPU/资源对比。难点不在硬件，而在**基线**：

- 软件侧当时**没有任何测量脚本**（`metrics/scripts/` 只有前端两项检查）；
- PL 侧当时只有"cosim 总时长"这种**混入喂/排数据开销**的粗糙数字，没有干净的单次调用延迟；
- 没有基线就会出现"跟一个随手写的 Python 循环比"这种**不可复现、不可比**的对比。

本文件交付三样：**① PS 侧基线脚本与实测值；② PL 侧延迟口径（工具推算 + 上板测量方法）；
③ 一张待填的对比表模板**。

## 2. PS 侧基线（本机实测）

脚本：**`metrics/scripts/bench_filter_ps.py`**（纯 stdlib + numpy；PYNQ 镜像自带 numpy，
所以**同一脚本可直接拷到板子上重跑**）。系数直接解析 `fpga/src/fir_coeffs_q15.h`（唯一来源）。

### 2.1 运行环境（脚本自动记录，缺了数字就不可比）

| 项 | 值 |
|---|---|
| 平台 | `Windows-11-10.0.26200-SP0` / **AMD64** / Intel64 Family 6 Model 198 |
| Python | 3.14.7 |
| numpy | 2.5.2 |
| scipy | **未安装**（所以本机没有 `scipy.lfilter` 那一行；M4 在板子上装了会多一列） |

### 2.2 实测结果（`--repeats 3`，取最好一次）

| 实现 | 10 s（300 样本） | 60 s（1800） | 300 s（9000） | 说明 |
|---|---|---|---|---|
| `numpy_batch`（整段 `np.convolve`） | 0.069 µs/样本 | 0.033 | 0.030 | 离线/回放路径 |
| **`numpy_stream`（逐样本、状态跨调用保持）** | **1.922 µs/样本** | 1.591 | 1.672 | **真实实时路径**（每秒调一次、每次 30 个新样本） |
| `python_ref`（纯 Python 精确整数） | 1.666 µs/样本 | — | — | 与 numpy 结果逐样本一致，作正确性锚点 |
| `numpy_stream` 每秒（30 样本）耗时 | **57.7 µs** | ≈ 47.7 µs | ≈ 50.2 µs | 占 1 秒的 **0.0058%** |

**脚本内置两条自检**（结果不一致就直接退出码 3，不许拿坏数据当基线）：
`python_ref == numpy_batch` ✅、`numpy_stream == numpy_batch` ✅。

> 🐛 **自检当场抓到一个真 bug**：第一版 `numpy_stream` 每个 chunk 都新建状态（历史清零），
> 于是与整段卷积**不一致**。这正是硬件里"**段间状态保持**"那条语义在软件侧的翻版 ——
> 见 `skill/fpga_hls_c_line.md` 的坑 30。**先修好再测**，否则基线本身是错的。

> ⚠️ **本机（AMD64）数字 ≠ PYNQ PS 数字**。PYNQ-Z2 是 **ARM Cortex-A9 @650 MHz**，
> 单线程 Python/numpy 会慢一个量级左右（**具体倍数必须实测，不许外推**）。
> M4 时把同一脚本拷到板上跑，脚本会把平台信息一起写进 JSON。
> 另外必须同时记录 PS 的**当前主频与 governor**（`/sys/devices/system/cpu/cpu0/cpufreq/`），
> 否则两次测量不可比。

## 3. PL 侧延迟口径

### 3.1 现在有的（工具数字，**推算**）

`fir_filter` 的 csynth 报告（`component_fir_filter/hls/syn/report/csynth.rpt`）：

| 项 | 值 |
|---|---|
| 流水循环 | `VITIS_LOOP_106_2`：Iteration Latency **9** 拍、Interval **1**、Trip Count 65535 |
| 循环总延迟 | **65542** 拍 |
| 函数总延迟 | **65554** 拍（n = 65535 时） |

**推算**（由上面三个数算得，标注为推算）：

```
调用总拍数 ≈ n_samples + 19         // 65554 − 65535 = 19 拍固定开销
每样本      = 1 拍（II=1）           // @100 MHz = 10 ns
每抽样批次  ≈ 30 拍 + 19 拍 = 49 拍 ≈ 0.49 µs   // 一秒的数据（30 个样本）
固定开销    ≈ 19 拍 ≈ 190 ns         // 寄存器读写与 ap_start/ap_done 握手（不含 AXI-Lite 总线开销）
```

> ⚠️ **这不是上板实测**。真实调用还要加上 AXI-Lite 寄存器写、DMA 启动/等待、PS 侧 Python 开销。
> cosim 的"985 样本共 4004.5 拍"**不能用**来当单次延迟：那个数字混进了测试台喂/排数据的拍数
> （见 `c5_fir_filter_v1.md` 第 7 节与 skill 坑 24 的补充）。

### 3.2 上板测量方法（M3/M4 照做）

1. **两条路径用同一段序列、同一份系数**（系数从 `fpga/src/fir_coeffs_q15.h` 取）：
   - 软件路径：`metrics/scripts/bench_filter_ps.py`（同脚本）；
   - 硬件路径：PYNQ `Overlay` → 把 q 序列（契约 4.6 节口径生成）送 DMA/流，
     写 `n_samples` / `reset`，轮询 `ap_done`（或读 `*_ctrl` 的 ap_vld）。
2. **包时间**：`t0=time.perf_counter()` → 触发 → 等到完成 → `t1`；**减去**纯软件侧的同一段
   序列处理时间，得到"PL 净收益"。
3. **预热 + 重复**：预热 ≥ 10 次（DMA/缓存要热身），重复 ≥ 100 次，
   报告 **min / median / p99**，不要只报均值 —— **抖动（p99−min）才是 PL 的核心卖点**。
4. **记录环境**：PS 主频/governor、是否开 CPU 亲和、DMA buffer 是否复用、
   PYNQ/内核版本 —— 一律写进 M4 报告。
5. **至少覆盖 3 种规模**：10 s / 60 s / 300 s 的序列（与 PS 基线同一组长度）。
6. 结果 JSON 存 `fpga/report/logs/`，并与第 2.2 节同一张表并列。

> 💡 若要把"PL 的确定性"讲硬：可用 PL 侧定时器（AXI Timer）或在 RTL 里数拍，
> 给出**与 PS 调度无关**的延迟分布；PS 侧则给出受 GC/GIL 影响的分布，对比一目了然。

## 4. ⚠️ 关键判读：这个 IP 的价值**不是"快"**（这份基线的最大发现）

把第 2、3 节的数字放在一起看：

| 指标（每秒 30 个新样本 = 一秒的数据） | PS（软件，**本机实测**） | PL（**推算**） | 结论 |
|---|---|---|---|
| 每样本耗时 | 1.922 µs | 0.010 µs | PL 快约 **192×**（本机口径） |
| 处理"一秒的数据"耗时 | **57.7 µs** | ≈ 0.49 µs | — |
| **占 1 秒实时预算的比例** | **0.0058%** | ≈ 0.00005% | **两者都远远够用** |
| 抖动 | 受 Python GC / GIL / 调度影响（未测，需 M4 量） | 结构确定（II=1） | **PL 的真正优势** |
| 占用 PS 主核 | 是 | 否 | 把 CPU 让给 MediaPipe / 指标 / 界面 |
| 资源代价 | 0 | LUT 4043 / FF 6174 / DSP 26 | 见 `c5_fir_filter_45hz_reserved.md` 第 6 节 |

**所以"FPGA 加速比 192×"这种说法在本 IP 上是误导性的**：30 Hz 的时间序列，PS 用 0.006% 的
CPU 时间就能算完，"跑不动"从来不是问题。**诚实的叙事应该是三条**：

1. **确定性**：PL 的延迟与抖动由结构决定（II=1），不受 GC/调度/GIL 影响 ——
   对"波形稳定性"这类质量判据，**可预期的延迟比平均更快更有价值**；
2. **CPU 释放**：滤波不占 PS 主核，把预算留给 MediaPipe、指标计算与网页服务；
3. **数据不出 PL**：ROI 统计/灰度/运动量/滤波同在一侧，避免"算一点搬一次"的往返。

> 相比之下，**像素链的三个 IP（`roi_statistic` / `rgb2gray` / `motion_quality`）的吞吐叙事是硬的**：
> 640×480×3 B×30 fps = **27.6 MB/s**（算术），逐像素在 PS 上做属于"能跑但会吃掉大量预算"，
> 而且会与 MediaPipe 抢核。**M4 报告要把这两类 IP 分开写**，不要用同一套话术。
