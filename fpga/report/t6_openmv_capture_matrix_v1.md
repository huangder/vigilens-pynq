## 0. 一句话结论

**契约帧在 OpenMV Cam H7 上"装不下"这件事，从"带宽推算"变成了"内存实测"。**

实测 `gc.mem_free()` = **308944 B**，而契约要的一帧 **640×480 RGB888 = 921600 B = 它的 3.0 倍**；
连 **640×480 RGB565（614400 B）都会直接抛 `Frame buffer overflow`**。
这是**片上内存**限制，**与接哪个口（UART/USB/SPI）无关** —— 所以它比 §3 的带宽算术更强：
带宽可以换口解决，内存不能。

**能做的最强组合（本次实测到的那一个）**：`RGB565 / QVGA / fb=1` → **均值 39.76 fps、40.01 中位**，
153600 B/帧。**帧率超过契约要求的 30 fps，但像素只有契约的 1/4（320×240 vs 640×480）**，
且是 RGB565 不是契约要的 RGB888。

**诚实边界**：本次只拿回了矩阵的**前 2 行**（原表 7 组，现表 10 组），
**JPEG 的真实压缩字节数、GRAYSCALE/VGA 的边界结果都还没拿到** —— 见 §5.2 / §6。

## 3. 逐项判读（含算术，全部只用 §2 的数字）

### 3.1 内存天花板：**这是本次最有价值的一条**

```
契约单帧        = 640 × 480 × 3        = 921,600 B
实测可用内存    = gc.mem_free()        = 308,944 B
比值            = 921,600 / 308,944    = 3.0 倍   → 装不下（差约 612 KB）
连 RGB565 都装不下：640 × 480 × 2 = 614,400 B = 308,944 B 的 1.99 倍
边界只差 1744 B：640 × 480 × 1 = 307,200 B，比 308,944 B 只小 1744 B（VGA 灰度是"擦边"）
```

**【已验证】**（真机实测 + 真机报错原文）：
`RGB565 / VGA` 抛 `RuntimeError: Frame buffer overflow, try reducing the frame size.`，
而 `RGB565 / QVGA`（153600 B）成功 —— **报错与内存算术完全吻合**。

### 3.2 官方文档那处矛盾，本次裁决了一半

OpenMV 官方产品页**自相矛盾**：描述段说 OV7725 能 "640×480 8-bit 灰度 或 640×480 RGB565 @75fps"，
而 Specs 表说 **RGB565 ≤ 320×240**。

- **【已验证】** 在**本机固件 + 本机传感器**下，`RGB565 / VGA` **不可用**（抛 overflow）。
  → 与 **Specs 表**一致。
- **【不确定】** 描述段是否另有上下文（例如只在 OV7725 + 特定固件/特定模式下成立）。
  **不下"官方文档错了"的结论** —— 只能说"我们这台在 v5 分支上不行"。

### 3.3 帧率与采样质量（`RGB565 / QVGA`）

| 指标 | 实测 | 含义 |
|---|---|---|
| 帧率均值 / 中位 | **39.76 / 40.01 fps** | 高于契约 §0 的 30 fps |
| 单帧最慢（`最慢帧` 列 = 最低瞬时帧率） | **16.08 fps**（= **62.2 ms/帧**） | 最坏采样间隔；首帧通常就是它 |
| 单帧字节 | **153600 B**（= 320×240×2，与理论值**完全相等**） | 说明实际生效的分辨率/格式**与请求一致**，没有被偷偷降级 |
| 实测吞吐 | 153600 × 39.76 = **6.11 MB/s** | 这只到"采集"，**没有考虑能不能送出去**（见 §3.4） |
| 跑完后的 `gc.mem_free()` | **307136 B**（启动时 308944 B，降了 1808 B） | **帧缓冲不占 MicroPython 堆** —— 所以"剩余内存 ≈ 308 KB"这条天花板是硬的 |

**按 `config.yaml` 的 `min_close_frames: 3` 折算**（`最短可检出闭眼 = 3 / 帧率`）：

| 用哪个帧率 | 最短可检出闭眼 | 对照正常眨眼 100~400 ms |
|---|---|---|
| 均值 39.76 fps | **75 ms** | ✅ 够用 |
| 最坏单帧 16.08 fps | **187 ms** | ⚠️ 会把 100~187 ms 的眨眼整段漏掉 |

> 也就是说：**平均值合格，最坏帧不合格**。`board/openmv/README.md` §3.4 担心的
> "低帧率系统性低估疲劳"在这台相机上**不是主要矛盾**（QVGA 有 40 fps），
> 但**最慢帧那一档**在合成"眨眼时长"统计时要留个心眼。

### 3.4 这条帧率**不能**改变"OpenMV 当不了 PL 像素源"的结论

`docs/10` §3 的结论建立在**链路带宽**上，与本次实测的**采集帧率**是两件事，两者都要过：

| 送什么给 PL | 采集侧（本次实测） | 需要带宽 | UART 上限 0.9375 MB/s（7.5 Mb/s） | 判定 |
|---|---|---|---|---|
| QVGA RGB565 @39.76 fps | ✅ 能采 | **6.11 MB/s** | 差 **6.5 倍** | ❌ 送不出去 |
| QVGA 灰度 @39.76 fps | 未测（预期同量级） | 76800 × 39.76 = **3.05 MB/s** | 差 **3.3 倍** | ❌ 送不出去 |
| QVGA 灰度 @10 fps | 需降帧率 | 76800 × 10 = **0.768 MB/s** | 占 82%，可行 | ✅ **这就是 `docs/10` §3 里"≤10 fps"的来历** |

**结论不变**：OpenMV 只能做**降规格采集源**（A 线的行为指标 / 演示画面）与
「人脸检测/追踪目标」，**当不了契约 §0 的像素源**；要满足契约只能走 MIPI CSI（Mizar-Z7020 自带该口）。

**【尚未验证】** A 线"旁路画面"（`POST /api/frame` → MJPEG，`config.yaml` 的 `video_push_hz: 8.0`）
的带宽预算要按 **JPEG 的真实压缩字节数**算，而 **JPEG 那几行本次没跑到** —— 见 §5.2。
采集侧 40 fps 对 8 fps 推送有充足余量，但**字节数未知就不能下结论**。

## 4. 这次暴露的两个问题

### 4.1 🐞 脚本里一个真机上也会犯的 bug（**已修**）

**现象**：旧版脚本在**相机探测成功**时，会打印

```
相机 API  : **探测失败** —— cannot access local variable '_CAM_API' where it is not associated with a value
```

**根因**：`main()` 的 `except` 分支里写了 `_CAM_API = None`，却没有 `global _CAM_API` ——
Python 因此把 `_CAM_API` 当成 `main()` 的**局部变量**，**成功路径**读它就抛 `UnboundLocalError`，
而这个异常**又被同一个 `try` 的 `except Exception` 抓住**，于是打印成"探测失败"。
连带的后果：`report.json` 里的 `camera_api` 会是 `null`。

**影响面**：**不影响矩阵数据本身**（`_apply()` 走的是 `global` 声明过的 `_open_camera()`，
所以失败行之外的备注列仍正确写着 `csi API`）。但它会让你以为"相机没连上"。

**怎么被发现的**：本机假模块自检 `board/openmv/offline_check.py`（新入库）——
它用假 `csi` / 假 `sensor` 在 PC 上跑真脚本，**两条分支**都验。
**证据**：把 `HEAD` 里的旧版脚本喂给同一套装置，输出确认复现了上面那行假故障
（旧版 4/14，新版 14/14×2）。

**修法**：`main()` 开头加 `global _CAM_API`（并写了注释说明为什么必须加）。
`metrics/scripts/check_all.py` 已把 `offline_check.py` 纳入回归（基线 **21 → 22**），
以后**每次跑总入口都会验一遍这个脚本**。

### 4.2 ⚠️ 矩阵只回来了 2 行（**未闭合**）

旧版 `MATRIX` 有 **7 组**，实跑只回帖了 **2 行**（`RGB565/VGA` 失败行 + `RGB565/QVGA` 成功行）。

**【不确定】** 两种可能，**都不能排除**：

1. **相机在后面的组合上卡死/重启** —— `RGB565/VGA` 已经证明这片内存会被请求爆掉，
   紧接着的 `GRAYSCALE/VGA`（307200 B）与可用内存（308944 B）**只差 1744 B**，
   属于最容易把相机拖死的"擦边"请求；卡死则后续行全部丢失。
2. **只是粘贴时截断了**（原帖只贴了前两行）。

**为什么必须查清**：如果是第 1 种，那"**擦边的大组合会搞死相机**"本身就是一条硬件事实，
必须写进硬件文档并让脚本默认分段跑；如果是第 2 种，重跑一次就完事。

**已做的加固（不依赖上面哪种结论都对）**：

- 组合**按"信息量/风险"重排**：小图 + JPEG 字节数在前，**已知会抛 overflow 的大组合放最后** ——
  就算炸，也只剩它自己没跑完。
- 每组开跑前打印 `---- [k/N] pixformat / size / fb 开始（此刻 gc.mem_free() = …）----`，
  并明确写"**这行之后没输出就是这一组把相机搞死了**" —— 下次能一眼定位。
- 新增 `MATRIX_STAGE = "auto" | "small" | "mid" | "big"`，**可分段跑**，一段炸不连累别段。
- 失败行也填 `理论B` 与 `mem_free`，让"为什么失败"直接写在表里（不再是一排 `-`）。
