## 1. 为什么这一档之前没有板上证据

`docs/37` 把 720p60 立成了 v1.5 的主档，`fpga/sim/data_motion_720p60/` 里的黄金参考也早就入库，
但**板级**只验过 640×480 档（S4 门限 5/6/7）。原因是抽取比在 `rgb2gray` 里是**编译期宏**
（`fpga/src/rgb2gray.cpp:57-61` 的 `RGB2GRAY_DECIM_NUM/DEN`），换档 = 换 IP = 重综合 bitstream，
而之前的 `board/build_bd.tcl` 只会往 `board/bitstream/system_wrapper.bit` 写，**换档会静默覆盖现行档的产物**。

这一轮做的正是补上这条链：档位开关 + 独立产物名 + 板上逐字节比对。

## 2. 做了什么

### 2.1 HLS：把 3/8 抽取编成第二个组件

```text
set "HLS_IP=rgb2gray"; set "VIGILENS_TIER=720p60"; set "HLS_COMPONENT=component_rgb2gray_720p60"; set "HLS_EXEC=1"
vitis-run --mode hls --tcl run_hls.tcl          # csim + csynth
set "HLS_COMPONENT=component_rgb2gray_720p60"; vitis-run --mode hls --tcl export_ip.tcl
```

**没有跑 cosim**：该档已有小尺寸 cosim 证据（`c6` 覆盖矩阵），而 720p 全尺寸 cosim 的代价是小时级
（参照 `roi` 720p 单帧 cosim 用了 1585 s）。真正需要 cosim 的是"接进 BD 之后那一层"，本轮用**板上逐字节**代替。

### 2.2 固件：几何改成编译期可换

`board/s4_bench/s4_bench.c` 的四个几何宏改成 `#ifndef` 包裹，可加
`-DFRAME_W=1280u -DFRAME_H=720u -DGRAY_W=480u -DGRAY_H=270u` 编 720p 档固件；
`s4_720.py` 只换常量（bitstream / 固件 / 测试向量 / 黄金参考），流程完全复用 `s4_run.py`。

### 2.3 BD：档位开关（不覆盖现行产物）

`board/build_bd.tcl` 新增 `VIGILENS_GRAY_TIER`：

| 取值 | rgb2gray IP | 产物名 |
|---|---|---|
| 不设 / `640x480` | `component_rgb2gray/hls/impl/ip`（3/5） | `system_wrapper.bit` / `.hdf` |
| `720p60` | `component_rgb2gray_720p60/hls/impl/ip`（3/8） | `system_wrapper_720p60.bit` / `.hdf` |

未知取值直接 `exit 1`；720p 档缺 `component.xml` 时打印三条重建命令并 `exit 1`（不猜、不静默降级）。

资源对比（同一顶层，`report_utilization -hierarchical`）：

| 档位 | LUT | FF | RAMB36 | DSP |
|---|---|---|---|---|
| 640×480（3/5） | 8161 | 15084 | 38 | 33 |
| 720p60（3/8） | **7791** | **14765** | 38 | **31** |

720p 档**反而更小**：`rgb2gray` 的 3/8 抽取（每 8 像素留 3）比 3/5 少一级判断，常数折叠后逻辑更省。
⚠️ 这不能说成"720p 更省资源"的普适结论 —— 同一个 IP 换个抽取比就可能反转。

### 2.4 上板

```text
python board\s4_bench\s4_720.py recm
```

`recm` = 相位 7 = 台账 BUG-037 的"**S2MM 长度留 384 B 余量 + 帧末软件停通道**"接法。

## 3. 板上实测读数（720p60 档，两轮）

```text
phase=0x00000007
cfg_w=1280   cfg_h=720   cfg_gw=480   cfg_gh=270
roi_x1_rb=0x00000500   mot_w_rb=0x000001E0
s2mm_da_rb=0x09000000  s2mm_len_rb=0x0001FBC0   (129600 + 384)
mm2s_len_rb=0x002A3000                          (1280*720*3 = 2,764,800)
mm2s_sr_after=0x00001002                        (IOC + Idle)
roi_ctrl=0x00000004  rgb_ctrl=0x00000004  mot_ctrl=0x00000004
s2mm_stopped_cr=0x00010002   s2mm_stopped_sr=0x00000000
ROI 117585600 117435290 117487576 921600 1
RGB 480 270 129600 16534331 1
MOT 16534331 129279 65373 129600 1
CMP mismatch=0 first_idx=4294967295
```

读法（每条都对得上"应该是什么"）：

- **换档真的生效了**：`cfg_gw/gh = 480/270`、`RGB` 输出尺寸 `480×270`、像素计数 `129600`
  （不是 640 档的 `384×288 = 110592`）。
- **整帧都进了链路**：`ROI ... 921600` = 1280×720，`roi_cnt` 也正好 921,600 ⇒ 没有丢像素、没有多算。
- **链尾按 BUG-037 收尾**：S2MM 目标长度比一帧多 384 B，所以它**不会自己 halt**；
  三个 IP 全部 `0x4` 后由软件写 `CR.RS=0` 停掉（`s2mm_stopped_cr=0x00010002`，SR 干净）。
- **数据是对的**：`CMP mismatch=0` —— ARM 把 DDR 里 129,600 字节硬件灰度与
  `fpga/sim/data_motion_720p60/gray.bin` 逐字节比，**一处不等都没有**。

两轮（run1 / run2，中间重新烧了 bitstream 与固件）读数**逐项相同**，包括 `ROI` 三个和、`RGB` 的
`sg=16534331`、`MOT` 的 `diff=16534331 / pix=129279 / ratio=65373`。

## 3.2 300 帧长稳 + 计时（补在 3.1 之后，2026-10-23 晚）

`long` 相位（8）= 同一帧连续 300 次，每帧都走推荐接法（软复位 → 启动三 IP →
S2MM 余量长度 → MM2S 整帧 → 等 IOC → 等三个 ap_done → 软件停 S2MM）。

| 档位 | `long_ok_frames` | `long_fails` | `fid0 → 末 fid` | tick / 帧 |
|---|---|---|---|---|
| 640×480（3/5） | **300 / 300** | 0 | 1 → 301（连续） | 3,073,959.8（`gt_ticks=922187934`） |
| 720p60（3/8） | **300 / 300** | 0 | 1 → 301（连续） | 9,217,962.2（`gt_ticks=2765388671`） |

- 两档都 `long_s2mm_sr=0`、三个 IP 的 `frame_id` 逐帧 +1（**不跳不重**）⇒ 720p 档连续 300 帧**不死锁、不丢帧**。
- 640 档今日读数 `922,187,934` 与 10-23 上午归档的 `922,187,840` 差 **94 tick**，在 S4 门限 7 记录的
  `262 tick` 极差之内 ⇒ 跨启动确定性延续。
- **比值 2.99873**：720p 的输入像素正好是 640 档的 3.0 倍（921,600 / 307,200），
  每帧耗时也随之 ×3 ⇒ 这条链**是像素率受限**，不是软件握手受限（后者会随档位不变）。这个比值不依赖计时器频率，是硬结论。
- 换算**只是推测**：若 A9 全局定时器按 333 MHz（半频，**板上无独立证据**，见 `docs/38` 对 `gt_ticks` 的说明），
  则 640 档 ≈ **9.23 ms/帧（108 fps）**、720p 档 ≈ **27.68 ms/帧（36 fps）**。
  ⇒ 若这一档要跑 **60 fps（16.67 ms/帧）**，按当前"每帧软复位 + 软件收尾"的接法**还差约 1.66 倍**；
  真正的流水线化（帧间不停通道、双缓冲）是唯一可能的补法，本轮**没有验证**。

## 4. 三个坑（都真踩了，写下来免得再花时间）

1. **`--build-id=none` 不加就崩，而且崩得很像"板子坏了"**：
   默认链接会放 36 字节 `.note.gnu.build-id` 在镜像最前面，`_start` 落在 `0x00100024`；
   而驱动是按 `rwr pc 0x00100000` 跳的 ⇒ CPU 把 build-id 当指令执行，数据中止到异常向量 `0x10`，
   结果块 `magic` 全 0、日志区一个字都不写。**症状与"固件没下载成功"完全一样**，但 `LOADED`/`PC=` 都是对的。
   `board/s4_bench/build.sh` 已固定加这个开关并在注释里写明原因。
2. **HLS 重跑会把导出的 IP 冲掉**：`component_<ip>/` 是同一个目录，`csim/csynth` 会重建 `hls/impl`，
   `component.xml` 随之消失；随后 `build_bd.tcl` 报 `找不到导出 IP 目录 …/component_fir_filter/hls/impl/ip`。
   本轮就是这样被挡了一次（FIR 127 阶那次跑完没补 `export_ip.tcl`）。**改完 HLS 必须补导出**。
3. **`board/*.rpt` 是"当前工程"的快照**：跑 720p 档会覆盖 `timing_impl.rpt` / `util_impl.rpt`，
   而这两个文件是入库的 640 档证据。本轮已先把 720 版另存、再用 `git checkout` 还原 640 版；
   720 档的数字只写在本报告里。**换档重综合后一定要检查 `git status` 里有没有 `.rpt`。**

## 5. 与契约的关系（别把这轮读成"契约升级了"）

- 生效契约仍是 **v1.1 = 640×480 @ 30 fps**；720p60 属 **v1.5 草案**（未会签），
  FIR 60 Hz / 127 阶属 **v1.6 草案**（未起草完成）。`CONTRACT_VERSION` 仍是 `v1.1`。
- 本轮证明的是 **PL 数据通路 + 3/8 抽取比在硅上成立**，不是"720p60 端到端可用"：
  时间轴（30 fps 还是 60 fps）、采集源（`docs/37` W1/W2）、Linux 侧（W7）都不在这条证据里。
