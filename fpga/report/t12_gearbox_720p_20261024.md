# t12 · 32→24 gearbox：把 720p 从 36 fps 拉到 ~108 fps（2026-10-24）

> 一句话：**t11 测出瓶颈是 MM2S 的 8 bit 流宽（3 时钟/像素），这一轮用一块自写的
> 32→24 字节重整器把它降到 1 时钟/像素 —— 板上实测每帧 tick 从 9,217,369 降到 3,073,328（3.00×），
> 720p 折算 ≈ 9.23 ms/帧 ≈ 108 fps，60 fps 终于有 1.8 倍余量；灰度结果仍与黄金参考逐字节相等。**

## 1. 为什么需要它

t11 的结论（`fpga/report/t11_streaming_720p_20261024.md`）：帧间不停通道只快 0.0064%，
真正的墙是**流宽**——`axi_dma` 的 MM2S 只能取 8/16/32/64…（24 被 IP 拒绝），
而 `roi_statistic`/`rgb2gray` 的入口是 24 bit。用 8 bit 流 + 官方 1→3 转换器时，
一个 RGB 像素要 3 拍，实测 2,764,800 B ÷ 27.68 ms = 99.9 MB/s = **1 B/时钟 = 3 时钟/像素**。

要 1 时钟/像素就必须让 MM2S 用 32 bit（4 B/拍），再在 PL 里把 4 字节重新切成 3 字节像素。
官方 `axis_dwidth_converter` 做不了 4→3（**非整数比**，它依赖 TKEEP 指出有效字节，
而 DMA 简单模式每拍 TKEEP 全 1），所以只能自己写。

## 2. RTL：`board/axis_32to24_gearbox.v`

- 16 字节小 FIFO（`mem[0:15]`、`head`/`tail` 各 4 位、`count` 5 位）。
- 入口：`s_axis_tready = (count <= DEPTH-4)`，每拍吃 4 字节（`mem[tail..tail+3] <= s_axis_tdata[31:24]…`），`tail <= tail+4`。
- 出口：`m_axis_tvalid = (count >= 3)`，每拍出 3 字节（`m_axis_tdata = {mem[h2], mem[h1], mem[h0]}`，`head <= head+3`）。
  先到的字节放在**低 8 位**，与旧 `conv_rgb(8→24)` 的字节序**完全一致** ⇒ 下游 IP 一个字都不用改。
- `m_axis_tlast = m_axis_tvalid && last_seen && (count == 3)`：最后一个像素恰好把 FIFO 清空。
- `m_axis_tuser = m_axis_tvalid && user_seen`：只在第一个像素上带帧首标记。
- 端口只有 `tdata/tvalid/tready/tlast/tuser`（不带 `tkeep/tstrb`）——**这正是它与官方转换器的区别**：
  它按字节流自己数，不看 TKEEP，所以非整数比也能成帧。
- **前提**（写在文件头）：一段传输的字节总数必须是 12 的倍数（3 字节像素 × 4 字节对齐）。
  720p：2,764,800 = 12 × 230,400 ✔；640×480：921,600 = 12 × 76,800 ✔。

## 3. 先仿真再上板（`.tmp/tb_gearbox.v`，24 B = 8 像素）

跑法：`xvlog.bat board/axis_32to24_gearbox.v .tmp/tb_gearbox.v` → `xelab.bat tb_gearbox -s sim_gb` → `xsim.bat sim_gb -runall`。
结果：`pushed_bytes=24  pixels_out=8` / `RESULT: PASS`（字节序、`tlast` 落在第 8 个像素、`tuser` 落在第 1 个像素）。

测试台刻意做成"不好过"的形态：6 拍推入、拍边界**故意跨像素**、`m_ready` 每 5 拍空一拍。

**踩过两个测试台自造 bug（都是 tb 的错，不是 RTL 的错）**：

1. `m_ready = ((got_px % 4) != 2)` —— `got_px==2` 时收端永久不 ready，直接死锁。改成按自由计数器 `cyc % 5 != 3`。
2. 推入循环里 `while (s_ready) @(posedge); @(posedge);` —— 会**二次握手**（多吞一拍）。
   改成"在 posedge 采到 ready 即算一次握手，下一个 negedge 撤 valid"。
3. 另外用 `.tmp/dbg_gearbox.v`（常输入、逐拍打印 `count/sv/sr/mv`）确认过 RTL 本身的时序是对的——
   这一步省掉了"怀疑 RTL"的一轮。

## 4. BD 改法（`board/build_bd.tcl`）

| 项 | 改前 | 改后 |
|---|---|---|
| `c_m_axis_mm2s_tdata_width` | 8 | **32** |
| `c_sg_length_width` | 26（t11 已抬） | 26（不变） |
| `conv_rgb` 实例 | `axis_dwidth_converter` 1→3 | **`axis_32to24_gearbox` 模块**（实例名仍是 `conv_rgb`） |

实例名保持不变是刻意的：下游 `connect_bd_intf_net`、时钟/复位 loop（`foreach cv [list conv_rgb conv_fir_in conv_fir_out]`）
一行都不用改，diff 只看得到"换了个实现"。

## 5. 板上读数（720p60 档，`board/bitstream/system_wrapper_720p60.bit`，sha256 `8A870B60…30FC`）

### 5.1 单帧逐字节（`python board/s4_bench/s4_720.py recm`）

```
s2mm_len_rb=0x0001FBC0   (129600 + 384 余量)
mm2s_len_rb=0x002A3000   (2,764,800)
ROI 117585600 117435290 117487576 921600 1

MOT 16534331 129279 65373 129600 1

```

与 gearbox 之前**逐项相同**（ROI 三个和、灰度字节数、运动计数都没变）⇒ 换成 32 bit 流没有改变任何数值语义。

### 5.2 300 帧长稳与计时（`python board/s4_bench/s4_720.py stream`）

```

stream_gt_ticks=921998414
stream_s2mm_sr=0x00000000
stream_cmp_first mismatch=0   stream_cmp_last mismatch=0
```

### 5.3 前后对照

| 版本 | 每帧 tick | 相对 | 折算（333 MHz 假设） |
|---|---|---|---|
| t11：8 bit 流（3 时钟/像素） | 9,217,369 | 1.00× | 27.68 ms ⇒ 36.1 fps |
| **t12：32 bit + gearbox（1 时钟/像素）** | **3,073,328** | **3.00×** | **9.23 ms ⇒ 108.3 fps** |
| 纯计算（307,200 px ÷ 100 MHz，II=1） | — | — | 3.07 ms（其余是 DMA/握手开销） |

**换算说明**：`gt_ticks` 是固件用 Zynq 全局定时器（`0xF8F00200`）读的 tick 差。
定时器频率**没有板上证据**，333 MHz 是"CPU 半频"的常见配置（【推测】）。
但**速率比不依赖这个假设**：3.00× 与"1 时钟/像素 ÷ 3 时钟/像素"完全吻合，
并且与 `2,764,800 B ÷ 9.216 ms = 300 MB/s = 3 B/时钟 @100 MHz` 自洽（PL 时钟是实测约束的 100 MHz）。

## 7. 与契约的关系

**一变都没变。**`docs/interface.md` 头部仍是 **v1.1（生效）**：640×480 @ 30 fps。
720p60 属 **v1.5 / v1.6 草案**（未会签），这轮只是把"720p60 在板上到底行不行"这个问题
从"36 fps，不行"改成"108 fps，行，且逐字节仍对"。要把它变成契约条款，仍得走会签流程。

## 8. 仍未闭合

1. **640×480 档的板上回归没做**：bitstream 已重建（§6 第 2 行），但重烧时 PS 挂死
   （`DAP status 0xF0000021`、`Cannot reset APU. Timeout waiting for PLL lock`），按 `docs/36` §5 只能断电重上电。
   要补的两条：`s4_run.py recm`（逐字节 vs `fpga/sim/data_motion/gray.bin`）与 `s4_run.py stream`（计时，预期 ≈3.07M tick/帧）。
2. **帧间不停通道 + gearbox 之外没有别的优化**：时钟抬到 ≥166 MHz、双缓冲、双路 16 bit 并联都未试
   （现在也不需要 —— 108 fps 已够 60 fps 的 1.8 倍）。
3. **没有 ILA 波形**：这轮只做数值与计时，结论都在 DDR 结果块与日志里。
4. 端到端（相机 → USB → A9 解码 → DMA → PL）仍未接（W7 的 PetaLinux 是前提）。

## 9. 复现命令

```bat
rem 1) 720p60 档 bitstream（含 gearbox）
call .tmp\build_720p60.bat            :: 等价于 set VIGILENS_GRAY_TIER=720p60 后跑 board\build_bd.tcl
rem 2) 上板：单帧逐字节 + 300 帧计时
python board\s4_bench\s4_720.py recm
python board\s4_bench\s4_720.py stream
rem 3) 640 档 bitstream（换档不设 VIGILENS_GRAY_TIER）
call .tmp\build_640_gearbox.bat
python board\s4_bench\s4_run.py recm
python board\s4_bench\s4_run.py stream
```

**这轮踩到的坑（两条，都是"脚本会静默改坏别处"）：**

1. **换档必须换组件目录**：`HLS_IP=rgb2gray VIGILENS_TIER=720p60` 忘了给 `HLS_COMPONENT`
   ⇒ `open_component -reset component_rgb2gray` 把 640 档用的默认组件重建成 3/8、`impl/ip` 一起冲掉，
   第二天 BD 校验报"找不到导出 IP 目录"。已加安全阀（`fpga/run_hls.tcl`：设了 TIER 没设 COMPONENT 直接 `exit 1`），
   台账 BUG-039 有追记。
2. **`export_ip.tcl` 要用 `vitis-run --mode hls --tcl` 跑，不能用 `vivado -mode batch`**
   —— 它调的是 `open_component`（Vitis HLS 命令），Vivado 里没有，报 `invalid command name "open_component"`。
3. **档位有两个环境变量名**：`board/build_bd.tcl` 认 **`VIGILENS_GRAY_TIER`**，
   而 `board/regmap.py`（即 `hw_sw_compare.py` / `dma_test.py` 的几何来源）和 `fpga/run_hls.tcl` 认 **`VIGILENS_TIER`**。
   实测代价：在同一个 shell 里做过档位实验后残留 `VIGILENS_TIER=720p60`，
   再跑 `hw_sw_compare.py --selftest` 会以 720p 的 `GRAY_PIXELS=129600` 去除 640 档的 `gray.bin`，
   报 `1105920 % 129600 = 69120 …否则是别的抽取比的数据` —— **看起来像数据坏了，其实是环境变量**。
   跑回归前先 `unset VIGILENS_TIER`（本轮 `check_all.py` 就是这样从 `PASS 34/FAIL 1` 回到 `PASS 35/FAIL 0` 的）。
