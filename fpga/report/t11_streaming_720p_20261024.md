# t11 —— 720p60：帧间不停通道（streaming）实测与瓶颈定位

> 日期：2026-10-24　｜　板卡：Mizar-Z7020（`xc7z020clg400-1`）　｜　链路：裸机 Cortex-A9 + `xsdb`（板上无 Linux/PYNQ）
> 上游：`fpga/report/t10_720p60_onboard_20261023.md`（720p60 档单帧与 300 帧长稳）
> 代码：`board/s4_bench/`（phase 9）、`board/build_bd.tcl`（`c_sg_length_width`）

---

## 0. 结论

| 问题 | 结论 |
|---|---|
| 帧间不停 S2MM、300 帧一次 arm，跑得通吗 | **跑得通**：`stream_ok_frames=300`、`stream_fails=0`、`stream_arms=1`、`stream_s2mm_sr=0`，第 1 帧与第 300 帧都与 `fpga/sim/data_motion_720p60/gray.bin` **逐字节相等** |
| 那它能让 720p 过 60 fps 吗 | **不能**：每帧 **9,217,369 ticks**，而逐帧停通道的旧接法是 **9,217,962 ticks** —— 只快 **0.0064%**，等于没变 |
| 真正的瓶颈是什么 | **MM2S 的流宽是 8 bit**：1 拍/时钟 ⇒ 100 MB/s ⇒ 一个 RGB 像素 3 拍（3 时钟/像素） |
| 能不能把流宽改成 24 bit | **不能**（IP 参数直接把 24 拒了）；改 32 又过不了 `conv_rgb` 的 4→3 非整数比（2026-10-19 已实测） |
| 720p 现在到底多少帧 | **≈ 36 fps**（按 333 MHz 换算 27.68 ms/帧；这个频率本轮被"字节率"独立佐证，见 §3） |
| 距离 60 fps 差多少 | **1.66×** 吞吐：需要 ≥ **166 MB/s**，现在是 100 MB/s |

> ⚠️ 这是**吞吐口径**的裸机台架（固定帧循环、无 USB、无 PS 解码）。它回答的是"PL 数据通路一帧要多久"，
> 不是"整机能不能 60 fps"。整机还差采集源（W1/W2）与 PS 侧（W7）。

## 1. 这一轮改了什么

| 项 | 旧 | 新 | 为什么 |
|---|---|---|---|
| S2MM arm 粒度 | 每帧一次（长度 = 1 帧灰度 + 384 B 余量） | **整段一次**（长度 = 300 帧 + 384 B = 38,880,384 B） | 想让通道在帧间不停 |
| `c_sg_length_width` | 23（上限 8,388,607 B） | **26**（上限 67,108,863 B） | 38,880,000 B 一帧装不下 23 位的计数器 |
| 帧末动作 | 软件停 S2MM（`CR.RS=0`，BUG-037 的接法） | **通道只在开头复位一次** | 这就是"streaming"本身 |
| MM2S | 每帧复位 + 重写 SA/LEN | 每帧只 `CR.RS=0/1` + 重写 SA/LEN（不清通道） | 排除 MM2S 的复位开销 |

固件：`board/s4_bench/s4_bench.c` 的 phase 9（`stream`），`chunk_frames = LONG_FRAMES`。

## 2. 两次上板读数

### 2.1 第一次：`c_sg_length_width=23`，每 32 帧重新 arm —— **第 33 帧 halt**

```text
stream_ok_frames=32   stream_fails=1   stream_first_fail=33   stream_fail_kind=2
stream_fail_mm2s_sr=0x00001001   stream_fail_s2mm_sr=0x00005011
stream_fail_roi_ctrl=0x00000001  stream_fail_rgb_ctrl=0x00000001  stream_fail_mot_ctrl=0x00000001
stream_arms=2
```

`0x00005011` = `DMAIntErr | IOC | Idle | Halted` ⇒ 重新 arm 时 DMA 内部报错并自停；
三个 IP 的 `CTRL` 停在 `0x1`（`ap_start=1`、`ap_done=0`）⇒ 收尾写再也拿不到应答。
这条已作为 **BUG-040** 记进 `docs/16`（缺陷，已修）。

### 2.2 第二次：`c_sg_length_width=26`，整段一次 arm —— **300/300 全过**

```text
magic=0x600D600D   loglen=1592
stream_frames=300        stream_chunk_frames=300     stream_arms=1
stream_ok_frames=300     stream_fails=0              stream_first_fail=0
stream_gt_ticks=2765210817
stream_s2mm_sr=0x00000000
stream_roi_fid=301  stream_rgb_fid=301  stream_mot_fid=301
stream_roi_cnt=921600  stream_rgb_pc=129600  stream_mot_cnt=129600
stream_cmp_first mismatch=0   stream_cmp_last mismatch=0
```

⇒ 功能上**完全成立**（含"数据只在 DDR 里紧密排列、通道从不回卷"的边界），
但**时间上没有任何收益**：

| 接法 | 300 帧总 ticks | 每帧 ticks | 每帧（@333 MHz） |
|---|---|---|---|
| 逐帧停 S2MM（t10 的 `long`，phase 8） | 2,765,388,671 | 9,217,962.2 | 27.681 ms |
| **帧间不停（phase 9）** | 2,765,210,817 | **9,217,369.4** | **27.679 ms** |
| 差 | −177,854（−0.0064%） | −592.8 | −0.002 ms |

## 3. 为什么"不停通道"等于没停 —— 瓶颈是字节率

S2MM 的 halt/restart 从来不在关键路径上：它与**下一帧的 MM2S arming** 重叠，而真正占满时间的是
"把 2,764,800 B 从 DDR 搬进 PL"这件事。按实测反推：

```text
每帧 27.679 ms  ÷  2,764,800 B/帧  =  99.9 MB/s
100 MB/s  ÷  100 MHz（契约目标时钟）  =  1.0 B/时钟
1 B/时钟  ÷  3 B/像素（RGB888）      =  3 时钟/像素
```

即 **MM2S 的 8 bit 流宽就是天花板**：一拍搬 1 字节，一个像素要 3 拍。
换到 640×480 档同样成立：`922,187,934 / 300 = 3,073,959.8 ticks = 9.23 ms`，
307,200 px × 3 B = 921,600 B ÷ 100 MB/s = 9.216 ms ✅。

**顺带得到一条独立证据**：全局定时器 `0xF8F00200` 的频率在本报告里第一次被"字节率"佐证 ——
上面等式只有取 333 MHz 才同时解释 640 档与 720p 档两个数（比值 2.99873 ≈ 3.0 也一致）。
此前它只是"按 A9 半频猜的"（`docs/37` §W6 里标注过"换算依赖未证实的定时器频率"）。

## 4. 想过、但走不通的路

| 方案 | 结果 |
|---|---|
| `c_m_axis_mm2s_tdata_width = 24`（3 B/拍，正好一像素） | **IP 直接拒绝**：`Value '24' is out of the range ... Valid values are - 8, 16, 32, 64, 128, 256, 512, 1024`（`.tmp/bd_720_w24.log`） |
| 回到 32 bit（4 B/拍） | 2026-10-19 已实测：`conv_rgb` 是 `axis_dwidth_converter`，4→3 **不是整数比**，`M_AXIS` 永远不给 `TREADY`，一帧都搬不动（见 `docs/16` BUG-035） |

**能真正过 60 fps 的三条路**（都不是"改个参数"）：

1. **自写 32→24 的 gearbox RTL**：DMA 走 32 bit（4 B/拍），PL 里把 4 B 的拍重新对齐成 3 B/像素的流
   （FIFO + 字节移位器）。入口 4 B/时钟 = 691,200 时钟/帧 = **6.9 ms**，之后受限于 IP 的 1 像素/时钟
   ⇒ 出口 3 B/时钟 ⇒ 720p ≈ **9.2 ms ≈ 108 fps** ✅（60 fps 有余量）。
   代价：新 RTL + 逐字节对拍 + 时序重跑；`conv_rgb` 退役。
2. **两路 8 bit 流并联**（两个 MM2S 通道，或一个 16 bit 通道接两个 conv）：2 B/时钟 ⇒
   2,764,800 B ÷ 200 MB/s = **13.8 ms ≈ 72 fps** ✅。
   代价：BD 里两个 DMA 通道 / 两条 S2MM / PL 侧重交织，比 ① 更重。
3. **把时钟抬到 ≥166 MHz**：1 B/时钟 × 166 MHz = 166 MB/s ⇒ 16.6 ms ✅。
   代价：现在 WNS 只有 0.788 ns（100 MHz），HLS IP 的 Fmax 是 145~147 MHz ⇒ **这条路实际上已经死了**。

⇒ 若真要 60 fps，① 或 ② 都行（① 更轻，改在 PL 侧、不碰 DMA 拓扑）；否则就**如实按 36 fps 报**（见 §5）。

## 5. 与契约的关系

- **生效契约仍是 v1.1：640×480 @ 30 fps** —— 640 档实测 9.23 ms/帧（108 fps），**余量 3.6 倍**，毫无压力。
- **720p60 只是 v1.5 草案的主档**（未会签）。本轮结论对它的影响：
  - 720p **@30 fps 完全可达**（27.68 ms < 33.3 ms）；
  - 720p **@36 fps 是当前微架构的上限**；
  - 720p **@60 fps 不可达**（差 1.66×），除非按 §4 的 ② 改数据面。
- 因此 `docs/37` 的 R1/R2 那类"PS 侧解码算力"风险要重新排序：**PL 侧已经成为更硬的约束**。

## 6. 复现命令

```bat
rem ① 编固件（两档一起，含 phase 9）
bash board/s4_bench/build.sh

rem ② 720p60 档：重建 bitstream（26 位长度）
set VIGILENS_GRAY_TIER=720p60 && call D:\Xilinx\2026.1\Vivado\bin\vivado.bat -mode batch -source build_bd.tcl

rem ③ 跑 streaming 300 帧
python board\s4_bench\s4_720.py stream
```

判据：`stream_ok_frames=300`、`stream_fails=0`、`stream_arms=1`、`stream_s2mm_sr=0x00000000`、
`stream_cmp_first/last mismatch=0`；每帧 ticks 与 `long`（phase 8）差 < 0.1%（= 没有收益）。

> ⚠️ 两个环境坑（都踩过）：`set VAR=值 &&` 会把**尾随空格**带进变量（要用 `set "VAR=值"` 或 PowerShell 先设 `$env:`）；
> `Tee-Object` 写出的日志是 UTF-16，Python 读要 `encoding='utf-16'`。

## 7. 仍未闭合

1. **真实像素源**：本轮是固定帧循环（同一份 `rgb_frames.bin` 轮着喂），没有 USB 相机、没有 PS 参与。
2. **双缓冲/流水**：即使字节率够，PL 一帧算完到下一帧开始之间还有 `ap_done` 轮询 ⇒ 实际帧率还要打折；
   本轮的 27.68 ms **只包含**"搬运 + 三个 IP 跑完"，不含软件调度。
3. **§4 的 ①/② 未做**：gearbox RTL 与双路 16 bit 流都只是方案，不是结论。
