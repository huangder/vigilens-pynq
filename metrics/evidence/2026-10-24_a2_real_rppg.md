# A2 真素材 rPPG 实测：两段素材都卡在"窗口未填满"（2026-10-24）

> **素材**：`data/raw/blink.mp4`（640×480、30.0 fps、**656 帧 / 21.87 s**）、
> `data/raw/blink_1080p_src.mp4`（1920×1080、30.053 fps、**656 帧 / 21.83 s**）。
> `data/raw/` **没有 annotations** ⇒ 本文**不做误差统计、不给准确率**，只回答两件事：
> ① 真素材上 rPPG **能不能出数**；② 出不来的话**卡在哪一步**（用 summary 的 `rppg_reject` 举证）。
> **一句话结论**：两段素材都**没有**得到任何 `vital.*` 数值，`rppg_reject = "window_not_full"`。
> 不是代码不干活 —— 素材只有 **21.87 s**，而窗口要 **900 个可见样本**（`round(30 s × 30 fps)`），
> 实测只攒到 **629 / 635** 个，**差 271 / 265 个样本 ≈ 9 s**。要出数，得先有 **≥35 s 的正脸素材**。
>
> **表述边界**：本文任何数字都只是"链路能不能走通"的证据，**不是**心率测量精度；
> 全程只按"趋势 / 辅助 / 原型"口径使用，不作医疗或健康结论。

## 1. 环境与硬约束（先钉死，免得后人"顺手改个参数"）

| 项 | 值 | 出处 |
|---|---|---|

| 标称帧率 | `fps_nominal: 30` | `config.yaml` |
| 窗口需求样本 | `round(30 × 30)` = **900** | `backend/vital.py`（`rppg_window_need`） |
| 采样率容差 | `rppg_fs_tol: 10%` | `config.yaml` / BUG-029 |
| 本文是否改过窗口 | **没有** | —— |
| 本文是否填过任何 `vital.*` 假值 | **没有** | —— |

三条**不许做**（本次遵守，后续也别做）：

1. **不许**为了"出个数字"改 `window_seconds` 或 `fps_nominal`；
2. **不许**给 `vital.*` 填假值 / 从别的素材搬数字；
3. **不许**用 `--loop` 把同一段 21.87 s 素材重复播放来"凑满 900 样本" ——
   重复内容会让 rPPG 的频谱出现人为周期峰，得到的数字**没有测量意义**。

## 4. 从 jsonl 派生的统计（去掉收尾 `done` 帧后 656 帧）

| 素材 | 可见帧（`face.visible > 0`） | 可见率 | `rppg_window_samples` / `need` | `hr_bpm` 非 null | 质量 `overall` 均值 | `pose.yaw` 中位 |
|---|---|---|---|---|---|---|
| `blink.mp4` 640×480 | **629** / 656 | **95.88%** | 629 / 900 | **0** 帧 | 0.8675 | **−34.34°** |
| `blink_1080p_src.mp4` 1920×1080 | **635** / 656 | **96.80%** | 635 / 900 | **0** 帧 | 0.8597 | **−17.94°** |

三条读法：

1. **检测没问题**：可见率 95.9% / 96.8%，丢脸帧是段首/段尾那几帧，不是检测抖动；
2. **窗口没填满**：可见样本数直接等于进窗样本数（629 / 635），离 900 差一截；
3. **两段素材都不是"正脸"**：640 版 yaw 中位 **−34.3°**（明显侧转），1080p 源 **−17.9°**（略偏）。
   即使把时长补够，`pose_yaw_max_deg = 30` 的护栏与 rPPG 的"正脸"前提也还要再核一遍。

## 5. 窗口算术：差多少、要录多久

| 项 | 640×480 | 1920×1080 |
|---|---|---|
| 已有可见样本 | 629 | 635 |
| 需要 | 900 | 900 |
| 缺口（样本） | **271** | **265** |
| 按实测 `fs_eff` 折算缺口时长 | 271 / 28.81 = **9.41 s** | 265 / 29.08 = **9.11 s** |
| 按可见率折算所需素材时长 | 900 / (0.9588 × 30.0) = **31.3 s** | 900 / (0.9680 × 30.05) = **30.9 s** |
| 建议录制时长（留姿态/质量拒答余量） | **≥35 s** | **≥35 s** |

> 所以"素材不够长"不是一句主观判断：**need 900 − 实测 629 = 271 个样本**，
> 折算 **9.4 s**，两段素材都差这 9 秒左右。按 `data/README.md` 的录制规范录 **35 s 以上**即可越过这一关。

## 6. 交叉核对：估计器本身是好的（合成基准 72 bpm）

`metrics/scripts/probe_rppg_timebase.py` 用**合成** 1.2 Hz 正弦（= 72 bpm）喂同一套估计器：

```
输入信号：1.2 Hz 正弦 = 72 bpm；窗口 need = 30s x 30fps = 900 样本；容差 rppg_fs_tol = 10%
真实采样率       旧口径(仅fid)       新口径(带ts)        fs_eff    reject        hr_conf
30.0        72.0            72.0            30.0      -             1.0
30.14       72.0            72.3            30.14     -             0.9987
13.0        166.0           None            13.0      fs_mismatch   None
8.0         None            None            8.0       fs_mismatch   None
3.7         146.0           None            3.7       fs_mismatch   None
✅ 全部档位符合验收判据（容差内报数、容差外 null）
```

**能说明什么**：窗口满 + 采样率与标称值一致时，这条链路能给出 **72.0 bpm / conf 1.0**（合成信号）。
**不能说明什么**：它**不是**真人素材的结果，**不能**据此声称"真素材也能出数" ——
真素材的下一道关是窗口样本数（本文证据）与频谱是否有主导峰（还没走到）。

## 7. 结论（按 A2 的验收口径逐条回答）

1. **【已验证】没有任何一份真素材 `vital.*` 数字**：两段素材 656 帧全部 `hr_bpm = null`（0/656），
   `rppg_reject` 均为 `window_not_full`。
2. **【已验证】不是分辨率/代码/性能问题**：1080p 源同样 656 帧、21.87 s、同样 `window_not_full`；
   1080p 只是更慢（`throughput_fps` 16.0 vs 56.8），不影响窗口样本数。
3. **【已验证】卡在素材时长**：629（或 635）个可见样本 < 900，缺口 **271 / 265 个 ≈ 9.1~9.4 s**。
4. **【已验证】两段素材的姿态也不满足"正脸"前提**：640 版 yaw 中位 −34.3°、1080p 源 −17.9°。
5. **【推测】** 补一段 ≥35 s 的正脸素材后，`window_not_full` 应当消失；届时是否出数还取决于
   频谱主导峰与质量门控（`vital_require_quality: 0.75`），**在下一次实测之前不下结论**。
6. **建议动作**（给素材录制者）：
   - 时长 **≥35 s**（31 s 是算术下限，留 4 s 余量给姿态/质量拒答）；
   - 640×480 @ 30 fps（契约尺寸；1080p 也能跑，但没必要，处理慢 3.5 倍）；
   - **正脸、别转头**（本次 640 版 yaw 中位 −34° 是反例）、光照稳定、人脸全程在框内；
   - 录完把文件放进 `data/raw/`，重跑本文两条命令，把 `rppg_reject` / `vital.hr_bpm` 贴回 `docs/38` A2。
