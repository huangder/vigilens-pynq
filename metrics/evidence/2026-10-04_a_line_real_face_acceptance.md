## 1. 复现命令

```powershell
. .\env.ps1
python backend/run_pipeline.py --source "data/raw/测试视频.mp4" --fps 30 `
    --json metrics/logs/_real3_last.json --jsonl metrics/logs/_real3_stream.jsonl `
```

`--fps 30` 是**必须的**：素材实际 30 fps，而契约 `fps_nominal=45` 只是标称值。不显式指定就等于
"按 45 fps 解释 30 fps 的素材"，眨眼率、长闭眼、哈欠去抖全部会失真（`data/README.md` 已警告过同一件事）。

## 2. BUG-006 / BUG-007（头部姿态）真实素材验收

**可比的是"结构性现象"，不是百分比**：台账里 98.1% 那组数字来自**另一段素材**（他们录的 640×480 `blink.mp4`），
与本次 720×1280 的自拍视频**不是同一段数据**，所以不能说"从 98.1% 降到 23.5%"。

| 现象 | 修前（台账 2026-09-26/27，他们的素材） | 本次实测（修后，本段素材 908 帧） |
|---|---|---|
| `roll` 范围 | **±173° ~ ±180°**（正立正面脸） | **−24.0° ~ +2.1°**（中位 −7.1°） |
| 相邻帧最大 `\|Δyaw\|` | **359.0°** | **71.2°** |
| `\|Δ\| > 90°` 的跳变次数 | 119 次（>90° 的 yaw 跳变） | **0 次**（yaw/pitch/roll 全部） |
| `tvec[2]`（脸在相机前后） | 曾解出 **−447**（镜像解） | 全程 `> 0`（求解器已拒绝负 Z） |
| `status = adjust_posture` | 618/630 = 98.1% | 213/908 = **23.5%**，且其中 9 帧是"人脸可见率 0.00"（真丢脸帧） |

**本次的姿态分布**（`_real3_metrics.csv`，908 帧）：

```
yaw  : 中位 21.12  p5 −32.05  p95 33.76  min −40.15  max 49.09
pitch: 中位  0.33  p5 −12.12  p95  9.35  min −23.05  max 14.11
roll : 中位 −7.12  p5 −12.36  p95 −0.79  min −23.99  max  2.13
```

**判断**：

- 【已验证】"物理上不可能"的现象（±180° 基准、359° 逐帧跳变、负 Z 镜像解）**全部消失**；
- 【推测】剩下的 23.5% `adjust_posture` **大概率是真实头姿**：这段是手持自拍，`yaw` 中位就有 21°，
  而 `config.yaml` 的 `pose_yaw_max_deg = 30`（占位值）；23% 的帧超过 30° 与"人略偏头讲话"相符；
- 【不确定】**有没有几度的系统性偏差**，需要规范素材 + 目视核对（`still.mp4` 应长期 ≤ 阈值、
  `turn.mp4` 必须触发 `adjust_posture`）才能定 —— 这正是 DAT-001 缺的素材。
- ⚠️ 单帧最大 `|Δyaw| = 71.2°`：可能是真实快速转头，也可能是单帧解算抖动，**规范素材上要复查**
  （台账 BUG-007 的验收要求"帧间变化连续"，71° 是否算连续由规范素材 + 标注来判）。

## 3. 【本轮新查出并已修】rPPG 拿不到样本：ROI 用了"契约尺寸"而不是帧的真实尺寸

**现象**：908 帧跑完，`rppg_window_samples = 45 / need 900` —— 窗口只填了 5%，心率永远出不来，
而 `landmark_source = mediapipe`、质量 `overall = 0.96`，看起来哪都没错。

**根因**：`run_pipeline.py` 计算额头 ROI 时传的是 **config 里的契约尺寸 640×480**，
而这一帧实际是 **720×1280**。`forehead_roi()` 会把 ROI 裁剪到 `width/height` 内，
于是人脸框（y≈570 起）整个落在 480 行以下 → **ROI 被裁成空** → 按契约 `count==0` 丢帧、不喂样本。

**实测对照**（同一段素材、逐帧统计）：

| 用哪套尺寸算 ROI | ROI 为空的帧 | rPPG 样本 |
|---|---|---|
| 契约尺寸 640×480（**修前**） | **861 / 908（94.8%）** | 45 / 900 |
| 当帧真实尺寸 720×1280（**修后**） | **0 / 908** | **900 / 900（填满）** |

**修法**：`backend/capture.py` 新增 `image_size()`（取当帧真实宽高，拿不到才退回 fallback）；
`run_pipeline.py` 用它算 ROI。回归用例：
`backend/tests/test_pipeline.py::test_roi_must_use_the_real_frame_size`（用本次实测的一帧真值钉死）。

## 4. 【本轮自我纠错】姿态护栏的阈值：像素 → 比值

BUG-006/007 的修复里我加了一道"平均重投影误差"护栏，阈值写成 `pose_reproj_max_px = 8.0`。
**实测发现这个值会毁掉姿态**：

```
真人素材 90 帧（每 10 帧取样）：平均重投影误差 中位 10.37 px  p95 14.73  max 20.04
→ 按 8.0 px 设闸，会拦掉 85/90 = 94.4% 的帧 ⇒ 姿态被清成 (0,0,0)
```

**症状很隐蔽**：我第一版报告里"yaw/pitch/roll 中位 0.00、`adjust_posture` 只有 1%"看着完美，
其实是护栏把 94% 的帧清成 0 —— **等于没在测姿态**。改用与分辨率无关的比值后重跑，
`adjust_posture` 才回到 23.5%（第 2 节），`yaw` 也才显示出真实的 21° 中位。

**改成**：`pose_reproj_max_frac`（误差 / 双眼外角间距）。实测分布：

```
误差/双眼间距: 中位 0.036  p90 0.047  p95 0.052  max 0.073
→ 取 0.25（≈ 实测最大值的 3.4 倍），只拦"明显是垃圾"的解（关键点塌陷、镜像解）
```

回归用例：`test_reproj_guard_is_resolution_independent`（同一姿态在 1×/2×/4× 分辨率下都必须被接受）。
⚠️ 0.25 仍是**占位值**（素材非规范），规范素材到位后复核。

## 5. TBD-003（左右眼 EAR 差 2 倍）→ 结论：是眨眼瞬态，不是系统性错误

| 指标 | 实测（907 帧有双眼值） |
|---|---|
| `ear_left` 中位 / `ear_right` 中位 | 0.219 / 0.236 |
| 相对差 `\|L−R\|/max` | 中位 **10.2%**，p95 56.7%，最大 88.3% |
| 相对差 >50% 的帧 | 67 / 907（7.4%） |
| 相对差 ≈2 倍（>66%）的帧 | 26 / 907（2.9%） |
| **大差异帧的 EAR 中位** | **0.030**（几乎闭眼） |
| 其余帧的 EAR 中位 | **0.231** |

**结论**：台账里"正面帧左右眼差 2 倍（0.56 vs 0.27）"是**抓到了眨眼过程中的某一帧** ——
大差异帧的 EAR 中位只有 0.030（眼睛已经闭上），而正常帧的左右差中位只有 10%。
⇒ 不属于台账"可能二（索引/公式用错）"，**不需要改 EAR 计算**；如需彻底闭单，
可在规范素材上再跑一次同样的统计（本文件已给出方法）。

## 6. rPPG 现状：窗口填满了，但仍不出数（且本素材**不该**用来判 rPPG）

修完第 3 节后：`rppg_window_samples = 900 / 900`（填满），质量 `overall = 0.96 ≥ vital_require_quality 0.75`，
但 `vital.*` 仍为 `null`。两个**已确认**的阻碍：

1. 【已验证】**冻结 FIR 系数是按 45 Hz 设计的**（`fpga/sim/data_fir/meta.txt`：`fs=45`、`taps=63`、
   `band_hz=0.70,3.50`），而本素材是 **30 fps** —— 采样率不匹配会让通带整体偏移（0.70–3.50 Hz → 约 0.47–2.33 Hz），
   这条素材**原则上前提就不成立**；
2. 【已验证】估计器还有一道**结构判据**："峰值 ±1 个频点内的能量必须占带内总能量过半"，
   本素材没过这道判据（否则会出数）。

**下一步**：用 **45 fps 规范素材**重跑；若仍不出数，再按 `backend/P4_CALIBRATION_GUIDE.md` 查
ROI 位置（BUG-011 的额头位置问题仍在）与带通参数。**在此之前不许把任何 BPM 数字写进报告**。
